# VETS motivation·Introduction 초안: 반복 실행의 행동 명세

2026-09-09. 사용자 요청에 따른 **검토용 한국어 초안 v2**. 최종 원고 문구 확정은 아니다.
[Flow 기록](flow_discussion_2026-09-09.md) §9–15와 사용자가 요청한 중심 문장을 반영한다.
v2는 시간·상태를 가진 structured control flow를 왜 생성용 명세의 표면으로 선택하는지 보강한다.
현재 위치: **① Introduction → ② System Overview → ③ Timeline IR → ④ Explorer**의 연결.

## 1. Motivation의 중심

> **개별 동작이 맞게 생성되어도, 반복 실행의 시간·상태 관계가 틀리면 자동화는 잘못 실행된다.**

필요성 문장:

> 스마트홈 자동화를 생성하려면 개별 조건과 동작에 더해, 반복되는 실행 사이의 시간·상태 관계까지 명세해야 한다.

사용자의 복합 조건 예시를 반영한 표현 선택의 중심:

> **스마트홈 자동화의 행동 명세는 무엇이 성립해야 하는지와 함께, 시간에 따라 실행이 어떻게 진행되고 상태가 이어지는지를 직접 표현해야 한다.**

Timeline의 제안 정의:

> Timeline IR is an executable behavioral specification that represents smart-home automation through structured temporal control flow and explicit state updates.

해결 방향:

> Timeline IR는 지원하는 자동화 연산과 그 조합의 실행 의미를 정의한다. 이로부터 입력별 기준 행동을 계산하고,
> 같은 명세를 DSL 생성 지침과 생성 결과의 행동 검증 기준으로 사용한다.

여기서 ‘맞는 개별 동작’은 API나 기본 연산의 적법성을 뜻한다. 각 조각이 전체 문맥의 명세를 이미 만족한다는 전제를 두는 것은 아니다.
‘전체’는 지원 단일 자동화가 선언 모델에서 만드는 관측 행동을 뜻한다. 모든 스마트홈 플랫폼/물리 세계를 포괄하는 명세라고 읽지 않는다.

## 3. Introduction 본문 초안

스마트홈 자동화 프로그램은 주기나 일정에 따라 실행을 반복하고, 센서 입력에 반응하며, 대기 중에도 필요한 상태를 유지한다. 자연어 요청을 이러한 프로그램으로 옮기려면 호출할 기기와 동작을 고르는 것에 더해, 조건을 언제 평가하고 이전 실행의 정보를 어떻게 사용할지 정해야 한다. 같은 조건과 서비스 호출을 사용하더라도 반복의 시작점, 타이머의 취소 시점, 저장값의 수명에 따라 다른 행동이 발생한다. 따라서 스마트홈 자동화의 생성에는 **반복되는 실행 사이의 시간·상태 관계를 명시하는 행동 명세**가 필요하다.

예를 들어 “방이 연속으로 5분 비어 있으면 플러그를 끈다”는 요청을 생각해 보자. 부재가 시작되면 5분을 기다린 뒤 현재 상태를 다시 확인하는 구현은, 방이 계속 비어 있는 상황에서는 요청대로 동작한다. 하지만 0분에 부재가 시작되고 4분에 사람이 돌아왔다가 4분 30초에 다시 나가면, 이 구현은 5분에 플러그를 끌 수 있다. 요청의 연속 부재 조건에 따른 시각은 9분 30초다. 센서 확인, 대기, 플러그 끄기 연산은 모두 적법하지만, 재실 중 타이머를 취소하고 다음 부재부터 다시 시작하는 관계가 보존되지 않은 것이다. 같은 이유로 반복 중 이벤트 기억을 잘못 갱신하면, 한 번 수행해야 할 호출이 이후 회차마다 다시 발생할 수도 있다. 개별 동작의 적법성이나 일부 실행 결과만으로는 이러한 차이를 확인하기 어렵다.

기존 연구는 자연어 요구를 구조화된 시간 명세로 옮기고 그 의미를 검토하거나, 사용자가 지정한 시간논리 속성을 만족하도록 자동화 규칙을 합성해 왔다. ARTEMIS는 구조화된 자연어를 거쳐 시간논리 명세를 생성하고, AutoTap은 LTL 속성에 기반하여 trigger–action 프로그램을 합성·수정한다. [ARTEMIS](https://cs.stanford.edu/people/trippel/pubs/mendoza_ICSE26.pdf), [AutoTap](https://hewj.info/papers/autotap.pdf). LTL은 실행 trace가 만족할 조건을 표현한다. 이를 반복 자동화의 구체적인 실행 기준으로 사용하려면 측정 일정, 횟수 누적, 상태 초기화와 호출 시점을 연결하는 의미도 명세 또는 실행 모델에 담아야 한다. 예를 들어 “주말 오후에 한 시간마다 측정하여 25도를 세 번 이상 넘으면 알린다”는 요청에는 측정 간격과 임계값 외에도 횟수를 누적하는 범위와 알림 이후의 실행 정책이 필요하다. 우리가 다루는 문제는 이러한 실행 결정을 명시하고, 채택한 행동을 최종 DSL 프로그램까지 보존하는 것이다. 따라서 생성용 명세는 시간 연산과 상태 갱신을 순서 및 반복 구조 안에서 직접 구성할 수 있어야 한다.

본 논문은 이를 위해 **구조화된 시간 제어 흐름과 명시적 상태 갱신으로 자동화를 표현하는 실행 가능한 행동 명세, Timeline IR**와 이를 이용하는 자동화 생성·검증 체계 **VETS**를 제시한다. Timeline IR는 제한된 타입 연산자와 조합 규칙을 통해 반복, 조건 대기, 지연, 값 읽기와 서비스 호출의 관계를 구성한다. 각 연산의 실행 규칙과 블록 사이의 제어·상태 전달 규칙은 복합 자동화의 행동을 정한다. 이 실행 의미를 사용하면, 선언 모델의 초기 상태와 외부 입력 이력이 주어졌을 때 어느 시각에 어떤 호출이 발생할지 계산할 수 있다. VETS는 자연어 요청에서 Timeline IR를 구성하여 사용자 확인을 거친 뒤, 이를 기준으로 대규모 언어 모델(LLM)이 JoI 도메인 전용 언어(DSL) 프로그램을 생성하도록 한다. Timeline IR는 생성 과정에서 따라야 할 행동과 생성 결과를 검사할 기준을 함께 제공한다.

기준 명세가 실행 가능하더라도, 별도로 생성된 DSL이 같은 행동을 수행하는지는 추가로 확인해야 한다. VETS의 **Behavioral Explorer**는 공통 초기 상태와 입력 이력에서 Timeline IR와 생성 DSL의 실행을 비교한다. 관측 대상은 서비스 호출의 시각, 대상, 동작, 인자, 횟수와 명시적 순서다. 따라서 기기 상태의 변화가 없는 추가 호출도 기준과 다른 행동으로 구별한다. 이 접근은 각 생성 결과의 의미 보존을 확인하는 translation validation의 관점을 따른다. [Translation Validation](https://link.springer.com/chapter/10.1007/BFb0054170). 지원 조건을 충족하고 시간 범위 제한 없이 인증을 완료한 경우, Explorer는 선언된 실행 모델의 모든 허용 초기 상태와 입력 이력에서 두 프로그램의 timed ACTION이 같음을 보장한다. 이 보장은 사용자 확인 명세에 대한 구현의 보존에 한정된다.

## 4. 본문 밖의 설명·범위 관리

### 사례 A의 전제

- 첫 부재 전에는 재실이며, 잘못된 구현은 대기 중 재트리거를 무시하는 경우다. 다른 재진입 정책에서는 다른 동작이 나올 수 있다.
- 0분 부재 → 4분 재실 → 4분30초 부재 → 이후 계속 부재라는 구성 사례다. 실제 관측 오류 빈도나 prior tool 비교 결과가 아니다.
- “연속”이 명시된 요구이므로 A는 자연어 모호성 자체가 아니라 명시된 관계의 구현 보존 문제를 보여준다.
- 반복·저장값을 한 사례에 모두 넣어 설명을 무겁게 만들지 않는다. 기존 B(읽은 온도를 저장하여 1분 후 알리기)는 IR 절로 유지한다.
- edge 기억 초기화나 지나치게 짧은 반복 간격은 별도 보조 그림/평가 후보다. 중복 자체를 기존 도구가 못 잡는다는 주장은 하지 않는다.

### 현재 초안에서 확정하지 않은 것

- ‘기존 LTL/TAP는 실행·전칭 검증 불가능’, ‘Timeline만 전체 행동 표현 가능’, ‘시간·상태 IR 최초’ 주장을 넣지 않았다.
- 사용자 확인은 기준을 채택하는 단계다. 이해·선택 정확성을 개선했다는 실증 주장은 없다.
- NL→IR→확인→LLM lowering→Explorer 흐름을 유지한다. 결정론적 compiler는 future work다.
- 전체 미래 trace의 열거, 내부 변수·시간의 무제약 곱집합, 모든 코드의 판정 완료를 주장하지 않는다.
- 다른 시작 앵커의 모든 cron 실행이나 여러 자동화의 중첩 실행을 이미 지원한 것으로 쓰지 않는다.
- 최신 평가 수치에 대한 audit 없이 Intro 성능 수치를 추가하지 않는다. 기존 OVLA의 수치를 새 Explorer 결과로 옮기지 않는다.

### Introduction 말미 기여 문장 후보

현재 초안은 문제와 방법의 연결을 먼저 검토하기 위한 것이다. 본문 말미에 기여 목록을 요구하면 다음 두 축으로 압축할 수 있다.

1. **실행 가능한 행동 명세:** 반복 자동화의 시간·제어·상태 전달을 명시하여 DSL 생성 지침과 입력별 기준 행동을 제공하는 Timeline IR.
2. **행동 보존 검증:** 선언 모델 아래 Timeline IR와 생성 DSL의 timed ACTION을 비교하고, 지원 경로의 관측 보존·탐색 완료 조건에 따라 인증하는 Explorer.

이는 제시할 산출물과 계약의 기술이다. 선행연구 대비 독립 novelty의 최종 문장과 평가 기여는 IR/Explorer 본문의 근거와 평가 결과를 연결한 뒤 다듬는다.

## 6. v2 설계 근거: 왜 structured temporal control flow인가?

### 6.1 사용자의 복합 자동화 예시

사용자 요청: “주말 오후에 1시간마다 온도를 재서 3번 이상 25도를 넘으면 메일로 알려줘.”
이 예시는 IR 선택 이유를 설명하는 보조 사례다. A를 Introduction 대표 사례에서 교체하기로 확정하지 않았다.

설명용 해석을 다음처럼 가정한다. 토·일 각각 12시 이상 18시 미만, 12시부터 정각 측정,
당일 오후의 비연속 누적 횟수, 세 번째 초과 관측 직후 메일 한 번, 다음 날 창에서 초기화.
이것은 사용자 의도를 확정한 결과가 아니다. 시간대와 경계 처리도 실제 모델에서 고정해야 한다.

```text
주말의 각 오후 실행 창 [12:00, 18:00)
  창 시작: count = 0, notified = false
  12시부터 1시간 간격의 각 측정 시점
    이번 온도 읽기
    25도 초과이면 count 갱신 (임계 3에서 포화 가능)
    count >= 3이고 아직 알리지 않았으면
      메일 호출
      notified = true
  창 종료: 해당 창의 반복 종료
```

**개념 구조이며 현행 IR 문법 또는 검증 완료 예제가 아니다.** anchored hourly schedule과
현행 `period`의 본문 완료 후 대기는 구별한다. 현재 cron 인증은 시작 앵커 고정 범위이므로
매 주말 여러 창의 생성·종료까지 이미 인증했다고 쓰지 않는다. 이 예시의 직접 lowering과 지원 여부는 별도 검토다.

12시부터 온도가 26, 24, 27, 28, 29도이면 위 해석은 15시에 처음 메일을 보내고 16시에 추가 호출하지 않는다.
같은 요청을 연속 3회로 해석하면 이 이력에서 16시에 처음 알린다. 구조화는 모호성을 자동 제거하지 않으며,
누적/연속, 초기화 범위, 한 번/매번 같은 선택을 명시할 자리를 제공한다.

### 6.2 LTL과 비교할 정확한 지점

- 표준 propositional LTL의 `X/U/F/G`는 trace의 순서 관계를 나타낸다. `X` 자체가 한 시간은 아니며
  일반 변수 대입·달력 스케줄러를 실행하는 문법도 아니다. 고정 시간 step, 달력/측정 사건,
  유한 상태 또는 추가 수식 등으로 의미를 제공할 수 있다. 3회 같은 고정 유한 횟수는 논리식으로도 표현 가능하다.
- `hour_tick`, `third_hot`, `mail` 같은 AP를 선언하는 것만으로는 충분하지 않다. 무엇이 올바른
  측정 시점·세 번째 초과인지, 창 밖에는 무엇을 하는지, 이후 추가 메일을 허용할지 정의해야 한다.
- `G(third_hot -> mail)`은 **이미 올바르게 정의된** `third_hot`에서의 알림 의무 일부만 보여준다.
  이 한 줄을 전체 요청의 LTL 번역인 것처럼 비교하지 않는다. 정확한 동시 호출/다음 step도 관측 모델에 의존한다.
- 도구의 숫자 변수·산술 predicate 지원, 시간논리 확장, 패턴 라이브러리, reactive synthesis가
  이 부담을 줄일 수 있다. 따라서 필연적 식 크기 폭발이나 원리적 표현 불가능성은 주장하지 않는다.
- 제안의 요점은 **어떤 실행 의미를 생성 대상 표현에 직접 제공하는가**다. Timeline에서는
  시간 연산과 상태 갱신을 순서·반복 구조에 배치하고, 라이브러리의 실행 규칙으로 전체 행동을 얻는다.
  특정 IR 구조가 실제 LLM 오류를 줄이는지는 별도 가설이다.

[NuSMV의 전이 모델과 LTL 명세 구분](https://nusmv.fbk.eu/userman/v21/nusmv_3.html),
[TSL의 데이터·제어 분리와 구현 합성](https://finkbeiner.groups.cispa.de/publications/2019-temporal-stream-logic-synthesis-beyond-the-bools/).

### 6.3 특징의 역할과 증거

| 특징 | 논문에서 설명할 기능 | 필요한 근거 |
|---|---|---|
| Structured temporal control flow | 순차 진행·대기·반복에 시간/상태 연산을 배치 | 문법과 대표 요청의 구조 매핑 |
| Domain primitives | 대기·지속·반복 등 지원 의미를 연산자로 제공 | 실제 연산 목록과 경계 규칙. 독립 count primitive 존재를 가정하지 않음 |
| Closed, typed surface | 지원 연산·인자·조합과 표현 범위를 한정 | 문법·타입·feasibility 규칙. 모든 의도 표현 또는 의미 정확성 보장은 아님 |
| Compositional semantics | 하위 블록과 조합 규칙으로 전체 의미 결정 | 상태 수명·제어 전달의 의미 규칙. 조합적 verifier라는 뜻은 아님 |
| Input determinism | 모델·초기 상태·입력이 고정되면 관측 반응을 유일하게 결정 | 동시 사건 정책 및 반응/시간 진행 조건 |
| Executable behavioral specification | 동일 명세에서 기준 timed ACTION 산출 | reference 실행 의미와 DSL 검증 연결 |

권장 명칭은 **Timeline IR**을 유지하고 첫 정의에 **structured temporal control flow and explicit state updates**를 쓴다.
control flow만 강조하면 누적값·저장값의 관계를 놓치므로 상태 갱신을 함께 명시한다.
Timeline은 미리 고정한 action 시간표가 아니라 입력에 따라 행동이 결정되는 명세다.

AST는 구조의 저장 형식이므로 “AST가 아니다”는 표현은 피한다. JoI 문법과 구현 관용구를 복제하는 대신
자동화의 행동 단위와 실행 규칙을 직접 명세한다는 설계 목표를 설명한다. 현재 backend는 JoI이며,
다른 backend 구현 없이 플랫폼 독립성·이식성이 입증되었다고 쓰지 않는다.

### 6.4 ARTEMIS에서 가져올 수 있는 근거와 우리 가설

ARTEMIS는 LLM의 NL 추론이 TL보다 강하다는 동기로 structured NL IR을 선택하고,
자신들의 설정에서 번역 성능을 평가한다. 이는 **표현 선택을 설계·평가의 대상으로 삼는 선행 근거**다.
Timeline의 control-flow 표현에서 같은 효과가 난다는 실증을 대신하지 않는다.

우리의 설계 주장: LLM은 지원 연산과 조합을 선택하고, 그 연산의 실행 의미는 미리 정의된 규칙이 제공한다.
우리의 평가 가설: 이러한 표현이 동등하게 정의된 비교 표현보다 시간·상태 관계의 생성 오류를 줄인다.
후자는 적절한 representation 비교 실험 전에는 성능 결론으로 쓰지 않는다. 이번 논의는 실험 개시 지시가 아니다.

문장 다듬기 기록: v1의 일반적인 ‘실행 가능’ 설명에서 v2의 연산·조합 선택 이유로 연결했다.
과장된 LTL 불가능성, 입증하지 않은 LLM 우수성, 현행 지원 범위 확대를 제거한 최종 문안을 위에 반영했다.
