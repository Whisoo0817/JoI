# sLM 절 분할 연구 노트 — Streaming Typed Segmentation

> 2026-08-11 논의 정리. 대상 모델: `cyankiwi/Qwen3.5-2B-AWQ-4bit` (연구 목표는 1–2B sLLM).
> 데이터: 루트의 `dataset.csv` (382개 유니크 명령어, `ir_gt` timeline JSON + JOILang gold).

## 1. 문제 정의

절이 여러 개인 복잡한 명령어를 2B 모델이 이해할 때 **정보를 누락하거나 변형**한다.
이를 줄이기 위해 명령어를 절 단위로 분할하고, 절 안에서만 분석시키는 접근을 탐색해왔다
(이전 실험: 9B attention probe로 경계 검출 93.1% top-1, 지배 head는 L3_h8).

## 2. 아이디어: 단어 단위 순차(streaming) 처리

IoT automation 명령어는 대체로 **시간 순서대로 나열**된다 — 복합 조건절(-하고/-하면) 뒤에
trigger 시 수행할 action들이 나온다. 이 temporal/sequential 특성을 이용해, 명령어를 한 번에
prefill하지 않고 **단어(어절) 단위로 앞에서부터 처리**하며 절이 완성되는 시점마다 확정(commit)한다.

예: "밤 12시 이후에 사람이 감지되면 조명을 모두 끄고 스위치도 다 꺼줘."
- "밤" → 절 미완성, 계속
- "이후에" → 유력한 절 후보
- "사람이" → 새 절 시작 = "밤 12시 이후에"를 절로 확정 (사실상 wait-1 lookahead)

### 2.1 전제 검증 (dataset.csv 382개)

- 순서를 뒤집는 구문("-기 전에") **0건**, 후행 조건절(문미 -면) **0건** → "표면 순서 = 처리 순서" 성립
- 382개 중 **264개(69%)** 가 문장 중간 단어에 절-경계 접속어미(-면/-고/-서/-거나/-는데/후에/때/자마자) 보유, 경계 표지 총 523개. 나머지는 대부분 단일 절
- **한국어 head-final 특성**: 접속어미가 절의 마지막 단어에 붙으므로, 왼쪽부터 읽으면 절이 끝나는
  바로 그 시점에 경계 신호가 나타난다 (영어는 if/when이 절 시작에 옴 → 이 방법은 한국어에 특히 유리,
  HA/영어 일반화 시에는 약점이 될 수 있음)

### 2.2 핵심 인사이트: "N번 추론"의 절반은 공짜

causal LM은 **한 번의 prefill로 이미 모든 prefix 상태를 계산**한다. causal mask 때문에 위치 t의
hidden state는 "t까지만 읽은 상태"다. 따라서:

- **경계/타입 판정**: 각 단어 위치의 hidden state에 작은 분류 head를 얹으면, 단어별 순차 추론과
  수학적으로 동일한 판정을 prefill 1회로 얻는다. 토큰 생성 없음.
- **진짜 순차 생성이 필요한 부분**: 절이 확정될 때마다 그 절의 frame을 즉시 생성하고 이어 읽는
  **읽기-쓰기 인터리브** 방식. `[명령 1..k] → [절1 frame] → [명령 k+1..m] → [절2 frame] → …`
  시퀀스가 append-only라 KV 캐시 100% 재사용(vLLM prefix caching). "파싱한 절을 문맥에 적어두고
  다음을 읽는" 구조 자체가 누락/변형 문제를 직접 공격한다.

### 2.3 지연 추정 (2B AWQ, RTX 5090, vLLM)

- head 방식: prefill 1회 + 선형 head → 수십 ms
- 단어별 판정을 API 생성으로 할 경우: 스텝당 HTTP 오버헤드 ~10–20ms 지배, 12단어 ≈ 0.3–0.5초
- 인터리브 frame 생성: 총 생성 토큰 수는 일괄 파싱과 유사 → 전체 지연 비슷
- 주의: "캐시 재사용으로 빠르다" 자체는 기존 기술(prefix caching, simultaneous MT의 wait-k)이라
  contribution이 되기 어렵다. contribution 축은 **monotonic clause-commit이 sLLM의 정보 누락을
  줄인다는 정확도 주장** + (음성 입력 시) 스트리밍 ASR과의 계산 중첩.

### 2.4 리스크

1. 2B zero-shot은 절 분리에 실패함(smoke test 확인) → 판정에 SFT 또는 head 학습 필요.
   AWQ 체크포인트는 직접 파인튜닝 불가 → bf16 원본에 LoRA 후 재양자화 경로
2. "-고" 역할 중의성: 조건 연쇄("감지되고 … -면") vs 액션 연쇄("켜고 … 꺼줘")는 뒤 문맥이 결정
   → 경계는 즉시 commit, **타입은 해소 시점까지 유예** 가능
3. 조기 확정의 비가역성 → 확신 낮으면 판정을 미루는 adaptive wait-k로 완화
4. 복합 조건 내부 경계(중첩)는 여전히 어려운 케이스

## 3. Segment 단위: "절"이 아니라 IR 프리미티브

절의 단위가 애매하다는 문제("오후 1시부터 3시까지 10분마다"는 구문/moment 어느 축으로도 못 나눔)는
**segment를 timeline IR의 head 프리미티브 인스턴스로 정의**하면 사라진다. 인벤토리는 새로 정의할
필요 없이 `ir_gt`에서 도출되며, 382개 전체에 대해 닫혀 있다:

| 구분 | 프리미티브 | 출현 횟수 (382 명령) |
|---|---|---|
| head (8) | `call` | 505 |
| | `start_at` | 382 |
| | `if` | 166 |
| | `wait` | 124 |
| | `cycle` | 109 |
| | `delay` | 52 |
| | `read` | 44 |
| | `break` | 1 |
| modifier slot (~6) | `edge` (rising 34 / none 90), `for`(sustain, 27), `until`, `period`, `cron`, `count` | |

- 실제 등장하는 **op 조합 패턴은 20가지뿐** → 구조 조립은 규칙으로 가능한 수준
- HA와 1:1 대응: `wait+edge=rising` ≈ trigger, `if` ≈ condition, `call` ≈ action, `for` ≈ HA의 `for:`,
  `cycle` ≈ time_pattern → 일반성 주장 + MTL(metric temporal logic)로 형식화 가능

### 3.1 2층 구조가 애매함을 해소하는 예

"오후 1시부터 3시까지 5분마다 밸브를 …" 의 실제 IR:
- "1시부터" → `start_at.cron = 0 13 * * *`
- "3시까지" → `cycle.until = clock.time >= 1500`
- "5분마다" → `cycle.period = 5 MIN`

세 조각이 서로 다른 op의 **슬롯**을 채운다. 시간 복합구는 통째로 하나의 SCHEDULE segment이고,
내부 분해는 segment 안의 슬롯 추출 문제다. ("까지"의 의미가 "마다" 유무에 따라 달라지므로
독립 segment로 나누면 오히려 해석 불가.)

프레이밍: "명령어는 timeline 위의 프로그램, parsing은 표면 span을 timeline op으로 컴파일하는 것."

## 4. 판정기 구현: BIO 태깅 head (토큰 생성 없음)

"유한 슬롯 중 고르기 + 어디까지 묶을지"는 여러 토큰짜리 출력이 필요 없다. **sequence labeling**으로
분해된다: 단어마다 `B-X`(타입 X segment 시작) / `I-X`(계속) 라벨을 붙이면, 경계는 "다음 단어 라벨이
B냐 I냐"로 표현된다. head 8종이면 라벨 ~17개 = 위치당 17지선다 분류 1회.

```
밤        B-SCHED     사람이    B-WAIT      조명을  B-CALL     스위치도  B-CALL
12시      I-SCHED     감지되면  I-WAIT      모두    I-CALL     다        I-CALL
이후에    I-SCHED                           끄고    I-CALL     꺼줘      I-CALL
```

- 라벨 일관성(I-X가 O 뒤에 못 옴 등)은 CRF/Viterbi로 강제 (마이크로초 단위)
- **head가 못 하는 것**: 슬롯 값 정규화("오후 1시"→cron, "10분"→`10 MIN`)와 중첩 구조 조립
  → 타입 확정 후 결정론적 규칙(현 파이프라인의 lowering/naming과 같은 성격) + 잔여만 segment별 생성
- 학습 강도 2단계: (a) 백본 동결 + 선형 head만 (AWQ 위에 바로 얹음, 수 분 학습, 타입 정보의
  선형분리성은 미검증), (b) bf16 원본에 token-classification LoRA (여전히 분류 objective, 재양자화 필요)
- 라벨은 ir_gt와 명령어 정렬(숫자·기기명·어미 단서)로 상당 부분 자동 생성 가능

## 5. "5분 이상 유지" → sustain 판정 방법론

같은 단어 "유지"가 데이터에서 두 가지로 갈린다:
- "전력이 5W 미만으로 10분 이상 **유지되면** 꺼줘" → `wait(cond, edge=none, for="10 MIN")` (조건측)
- "잠길 때마다 조명을 최대밝기로 10초 **유지하다가** 꺼줘" → `call → delay(10 SEC) → call` (액션측)

단어 사전만으로는 실패. 타입은 부착 구조가 결정하고 한국어에선 어미에 드러난다(-되면 vs -하다가). 3겹 방법론:

1. **닫힌 선택**: head 타입과 duration의 슬롯 귀속을 enum에서 고르게 하고 vLLM structured output으로 강제
2. **minimal-pair SFT**: 같은 "5분"에 프레임만 바꾼 자동 생성 쌍 —
   "5분 **후에**"→delay, "5분**마다**"→period, "5분 이상 **유지되면**"→`for`, "5분 **동안** 켜줘"→delay-괄호,
   함정 "습도가 5 **이상이면**"(값 비교). edge 판정(감지**되면**=rising vs 상태**면**=none)도 같은 틀
3. **결정론적 검증기**: "모든 숫자는 정확히 한 슬롯에 복사", "분/초/시간 단위어는 duration형 슬롯에만",
   "'마다' 있으면 period 존재", "`for`는 cond 필수" — 위반 시 재생성/AMBIGUOUS. 이 검증기가 그대로
   GRPO의 verifiable reward가 된다

## 6. Wait-k probe 실험 (2B): 오른쪽 문맥은 노이즈인가 신호인가

**가설 대립**: "causal(왼쪽만)이 temporal 명령어에서 노이즈를 줄인다" vs "이 길이(~20단어)에선 오른쪽 문맥이 신호다"

### 설계

- `cyankiwi/Qwen3.5-2B-AWQ-4bit`, CPU, hidden state 추출 (`experiments/waitk_extract.py`)
- 각 명령을 `cmd ### cmd`로 두 번 입력 (echo trick): 1번째 복사본의 단어 state = causal(왼쪽만),
  2번째 복사본 = 전체 문맥을 본 state
- 피처 = 단어 마지막 subword 토큰의 hidden state (layer 2/6/12/18/23), 로지스틱 probe,
  명령 단위 GroupKFold 5-fold (`experiments/waitk_probe.py`)
- 조건: `pos`(위치만) / `C0`(causal만) / `C1·C2·C4`(다음 1·2·4단어 state 연결) / `CF`(causal+전체) / `Fonly`(전체만)

### 결과

**과제 A — 절 경계 판정** (gap 3,037개, 접속어미 유래 라벨, majority 0.828):

| 조건 | acc / F1 (최고층) |
|---|---|
| C0 | **0.996 / 0.987** |
| C1~C4 | 0.991~0.996 (이득 없음) |
| CF / Fonly | 0.996 (동일) |

경계 신호는 완전히 국소적 — causal만으로 충분. (라벨이 어미 규칙 유래라 sanity check 성격.)

**과제 B — "-고" 절의 조건/액션 판정** (n=194, 라벨 = 뒤에 -면 존재 여부, majority 0.562):

| 조건 | acc (층별 최고) | 오류율 |
|---|---|---|
| pos | 0.758 | — |
| C0 (causal만) | 0.923 | 7.7% |
| C1 | 0.954 | 4.6% |
| C2 | 0.954 | 4.6% |
| **C4** | **0.974** | **2.6%** |
| CF (causal+전체) | 0.954 | 4.6% |
| Fonly (전체만) | 0.964 | 3.6% |

### 해석

1. **"미래 = 노이즈" 기각**: lookahead 한 단어씩 추가마다 전 층 단조 개선, k=4에서 오류 1/3로
2. **약한 버전은 성립**: 전체 문맥(CF/Fonly)은 -면 마커를 볼 수 있음에도 유계 창(C4)보다 낮다
   → 필요한 건 근처 몇 단어, 전역 문맥은 무이득 + 표현 희석
3. causal만으로도 92% → 2B가 동사 의미("감지되고"류)로 뒤에 -면이 올지 예견 → 조기 commit 기반 튼튼
4. **최적점 = causal + 소규모 lookahead 창 (wait-k, k≈2–4)** — 스트리밍 설계와 일치.
   논문 서사: "경계 판정은 국소적, 타입 판정은 k≤4 창에서 포화, 전역 문맥 무이득 → incremental 처리는
   정확도 손실 없이 가능"

### 한계

- 과제 B의 n=194 → 1%p ≈ 표본 2개. echo trick의 전체-문맥 state는 진짜 양방향 인코더와 다른 계산
- **생성 단계의 누락/변형 감소 주장은 미검증** — 절 단위 인터리브 생성 vs 일괄 생성을 2B 서버로
  직접 비교하는 것이 다음 실험

## 7. 실험 E1 — "절을 잘라주면 2B의 IR 생성이 나아지는가" (프롬프팅, 2026-08-11)

dataset.csv에서 동작(op) 4개 이상인 명령 60개(층화 표집)를 2B 서버로 파싱시키고,
절 분할 방식만 바꿔 비교. 총 561콜, 모든 방식이 동일한 문법 스펙·few-shot 3개·기기/서비스 블록을 받음.
채점기는 별도 에이전트가 적대적으로 감사(실결함 4개 수정: cron 0패딩, 연산자 공백, args 키 대소문자,
15스텝 초과 시 매칭 알고리즘 전환 버그).

| 방식 | 사실 복원율 | 누락 | 변형 | op 커버리지 | 유효 JSON |
|---|---|---|---|---|---|
| batch (한번에) | **0.369** | 0.433 | 0.198 | 0.626 | 80.0% |
| marked (경계 표시만) | 0.331 | 0.479 | 0.190 | 0.595 | 76.7% |
| interleave (절 단위 순차) | 0.321 | **0.313** | 0.366 | **0.758** | **98.3%** |

**판정: 총점은 무승부, 그러나 오류의 성격이 바뀜.**
- 절 단위 순차 처리는 **누락을 28% 줄이고** 출력이 잘려 전멸하는 실패(batch의 20%)를 거의 없앰
- 대신 되찾은 자리에 **틀린 값**이 들어감("잠궈줘"→Valve.Open, "켜고"→Off): 변형 0.198→0.366
- 절 경계 표시만 주는 것(marked)은 효과 없음 → 이득의 원천은 분할 정보가 아니라 **순차 생성**
- 결론: 절 분할이 고치는 건 **기억력**(잊어버림)이고, 병목은 **절 내부 번역 실력** →
  값 채우기는 자유 생성이 아니라 닫힌 선택(constrained decoding)이나 SFT로 풀어야 함
- 설계 결함 발견: 매 턴 전체 timeline 재출력 방식은 턴이 갈수록 붕괴(파싱 실패 7%→52%→100%).
  append-only 방식(`e1/append_arm.py`, 새 스텝만 출력 + into 3지선다)이 수정안

## 8. 스트리밍 단어별 판단 — 프롬프팅의 한계와 결정적 발견 (2026-08-11)

규칙·JSON 없이, 단어가 하나 들어올 때마다 모델이 토큰 1개(1=새 절 시작/0=계속/2=애매)로 판단하는
프로토콜(사용자 지정). `experiments/streamseg/streamseg2.py`.

**결정적 발견 — 채팅 템플릿이 판별을 죽인다.** 채팅 API로 보내면 모델이 "대화 답변" 모드로 들어가
숫자 토큰 확률이 사실상 0 (그 상태에서 guided_choice로 강제하면 무작위나 다름없음).
**raw `/v1/completions`(패턴 이어쓰기)로 바꾸면 같은 모델이 즉시 유의미한 확률**을 냄
(경계에서 P(1)=0.6~0.7, 비경계에서 P(0)=0.55~0.6). 이후 모든 판별 과제는 completion 모드 필수.

- 속도: 판단당 ~18ms (few-shot 프리픽스가 캐시에 맞음), 30개 명령 × 2변형 전체 10.8초
- 품질: 경계 54개 중 타당한 자리 30 / 근거 없는 자리 24 / 표지 있는데 놓침 58 — 신호는 있으나 불안정
- few-shot 어휘를 외우는 부작용 확인 (예시의 "거실"→경계를 어휘로 학습)
- "시간 순서대로 배열된다" 설명 추가는 **무효** (타당한 경계 동일, 근거 없는 경계만 24→38 증가)
- "애매(2)" 토큰은 few-shot에 예시를 넣어도 한 번도 안 나옴

## 9. Head 실험 — 판별을 생성이 아니라 내부 표현에서 읽기 (2026-08-11)

같은 과제를 2B의 hidden state + 로지스틱 분류기로. `experiments/head/`.

**라벨 원칙 (사용자 확정, 3원칙):**
1. "A이고 B이면" 복합조건 = **한 절로 병합** (IR의 조건 하나와 일치)
2. "3분 뒤에" 시간표현 = **독립 절** (IR의 delay 동작과 1:1)
3. 동사 없는 조각(쉼표/마침표 뒤)은 **앞 절에 붙임**, 단 "아니면/그렇지 않으면"은 절로 유지

어미 규칙 분할 → IR 동작 수와 대조 → 3원칙 적용으로 382개 명령, 단어 3,436개, 경계 489개 라벨 생성
(`head/labels.json`). 평가는 명령 단위 5조각 교차검증(같은 명령이 학습·평가에 동시 등장 불가).

| 방식 | 정밀도 | 재현율 | 명령 완전일치 |
|---|---|---|---|
| 프롬프트 판단 (§8) | ~0.56 | ~0.34 | 거의 0 |
| **head (직전+현재 단어, L2)** | **0.988** | **0.990** | **97.4%** |

부수 발견:
- **직전 단어가 결정적**: 현재 단어만 주면 F1 0.92, 직전+현재면 0.99 (어미가 앞 절 마지막 단어에 붙으므로)
- **다음 단어 미리보기 불필요**: 직전+현재+다음 = 0.987 (동일) → 단어 도착 즉시 판단 가능, 스트리밍 부합
- **얕은 층이 최적**(L2/L6): 절 경계는 초반 층의 표면 정보 → 배포 시 앞 몇 층만 계산해도 됨
- **문장부호 전부 제거(STT 모사) 실험: F1 0.990으로 동일, 완전일치 97.4% 유지.**
  경계 신호는 쉼표가 아니라 어미에 실려 있어 STT 경로에 강건. (최적 층은 L2→L6으로 한 층 깊어짐)
- 남은 오류 ~2%는 무작위가 아니라 표본 부족 유형에 집중: 진행형 "-고 있-"(30곳 vs -고 경계 135곳의
  불균형), "-는데"(8곳), "그렇지 않으면", "다시/시간표현 주변"

**한계**: 이 수치는 "같은 스타일의 처음 보는 명령"에 대한 것. 382개가 같은 팀 작성이라
실사용 말투 일반화는 별도 검증 필요(신규 작성 테스트셋 30~50개).

## 12. 파이프라인 설계 확정 (2026-08-12 논의)


이름은 "Skill"이 아니라 **"Service"** — Joi 플랫폼의 핵심 기여가 service-oriented 특성이므로.
segment의 정의 = "**service 사용 1회**"가 될 조각 (value 읽기 / action 호출 / Clock류 시간 / 제어).

**관통 원칙 2개:**

2. 환경(이 집 기기)은 가중치에 굽지 않고 런타임 조인으로. 단 **전역 service 사전(55종)은 환경이
   아니므로** 어느 단계든 사용 가능 — 1단계의 환경 무지 원칙과 충돌하지 않음

## 13. 절 타입 인벤토리 (871개 절 전수 매핑, `head/clause_types.json`)

9가족/14세부로 100% 커버: 행동 470(마지막 358/-고 101/-서·-다가 5/생략형 6) · 상태조건 177(+또는-연쇄 6)

- 절≠동작 1:1인 타입은 3개뿐: 때마다(cycle+wait), 확인해서(read+cycle), 주기(cron 또는 cycle)
  → 타입 자체가 "동작 묶음 템플릿"이라 조립이 단순해짐
- 생략형("에어컨을 냉방으로,")은 이웃 절에서 동사·대상 상속 — 예: "꺼줘"는 앞 절에서 Valve 상속 후
  일반 후보 {Off,Close} ∩ Valve 기능 = **{Close} 확정** (판단 없이 조회 2번)
- **복합조건 병합 정책 개정**: 어미(-고/-거나)만 보고 무조건 병합하지 않고, **value(값 읽기)끼리
  연쇄면 묶고 action(기능 호출)이 섞이면 가름**. 판단 피처 = 형태("-져 있-") + 전역 사전(센서류는
  기능이 없음), 정답 라벨은 ir_gt에서 직접(그 절의 앵커가 gold의 한 조건식 안에 있는가) — 규칙 순환 없음.
  주의: "같은 service끼리 병합"은 오답 — 복합조건은 서로 다른 service를 자주 걸침(온도+습도)

## 14. 2단계 Service Mapping 설계

조각마다 판단 4개로 분해: ① 세부 타입(9지선다, head) ② service category(검색+선택)
③ 기능/값 이름(카테고리 조회로 보기 축소 후 선택) ④ 숫자·문자열(판단 금지, 원문 복사만).

**카테고리 검색 구성** (일반 임베딩 단독은 비추 — tool retrieval 문헌 앵커: Gorilla/ToolLLM):
```
후보 텍스트 확장 (카테고리 설명 + ir_gt에서 자동 수집한 한국어 동의어)   ← 승부처 1
  → 키워드+임베딩 하이브리드(BGE-M3급)로 top 3~5                    ← 재현율 담당
  → 2B가 최종 선택 (hidden state+투영 학습 or completion 1토큰 선택)  ← 승부처 2, 기존 재료 재활용
```

**질의 단위 결정:**
- 문장 통짜 임베딩 금지 — 벡터가 여러 기기로 당겨져 희석됨. **segment별 질의** (ablation 논문거리)
- 병합된 복합조건 절은 **값 표현 단위**로 한 칸 더 내려 질의 ("온도가 28도 이상" / "습도가 70% 이상")
- **절 임베딩은 절만 떼어 단독 재인코딩** (확정): causal이라 절 마지막 토큰에 앞 절 내용이 섞이는
  오염을 원천 제거. 절 ~10토큰 = 수 ms. **양방향 attention 전환은 기각** — mask만 풀면 학습 분포
  이탈로 오히려 나빠지고(LLM2Vec의 교훈: 적응 학습 필요), 스트리밍 서사를 깨며, 실측상 이득도
  없음(다음 단어 무이득, echo 전역 문맥은 유계 창보다 나쁨)

**미정:** 기능 다중 후보({Close,Lock})의 3단계 전달 규약(개수·점수) / 1:다 조각의 스케치 표기 /
2단계 평가 지표(조각 단위 타입·category·기능 3중 정확도 + 명령 완전일치 제안 상태) /
타입 세분화를 1단계에서 할지 2단계로 미룰지

## 15. 절 사이 관계 & IR Assembly — 상자 규칙

절끼리의 관계는 5종뿐: 순차 / 범위(조건 우산) / 분기(아니면) / 소속(반복 안) / 어휘 상속.
관계 결정은 학습이 아니라 **타입 열 위의 상자(스택) 규칙**으로 환원:

```
스케줄·때마다·조건 절 → 상자를 연다 (새 조건은 기존 조건 상자를 닫고 새로 연다)
행동·기다리기 절     → 가장 안쪽 열린 상자에 순서대로 담는다
"아니면" 절          → 직전 조건 상자의 반대쪽 칸(else)으로
"멈춰" 절            → 가장 안쪽 반복을 닫는다
```

성립 근거: 어순=실행순서(역순 구문 0/382) + op 조합 20패턴. **알려진 예외 1개**: 명사화 반복
"A하고 B하는 걸 N마다 반복해줘" — "-고"가 명사화("-는 것/걸") 내부라 절 경계가 아님. 1차 방어는
분할 단계의 명사화 가드(올바로 자르면 예외 소멸), 2차 방어는 상자 기계의 wrap-last 연산(직전 물건들을
반복 상자로 재포장 — 국소 되돌림). 검증 실험: gold 타입 열 → 상자 규칙 → 382개 gold IR 구조와
전수 비교 (TODO).

## 16. 검증/피드백 설계 (채택 2건)

검증 대상이 이동했다: 구 체계는 IR↔code(trace equivalence, 아래층끼리) + 사용자 IR 승인.
승인이 사라진 지금 위험은 명령↔IR 사이(카테고리 오판, 조립 누락)이고, **segment가 있어야
명령↔IR 검증이 기계적으로 가능**해진다(문장 통짜로는 조각 단위 회계 불가).

**채택 1 — Segment–IR 쌍방 회계**: 모든 segment는 IR 노드에 소비(잔여=누락), 모든 IR 노드는
segment에서 유래(잔여=환각), 숫자·enum은 그대로 복사(불일치=변형). E1 채점기의 런타임 전환.
실패가 "몇 번째 조각"으로 국소화됨.

**채택 2 — 타입별 행동 의무 + simulator v2 FSM 모델체킹**: 각 segment 타입이 최종 산출물이
만족해야 할 성질을 생성하고, joi 코드에서 뽑은 유한 상태 모델을 그 성질들로 검사:
조건 절 → "X 실행 경로는 모두 가드 통과" / 기다리기 → "N분 시간 전이 존재" / 때마다 →
"wait 포함 순환 존재" / 아니면 → "두 분기 존재+상호배타" / 멈춰 → "순환에 탈출 조건".
의무 실패 = 해당 segment 지목 → 그 조각만 재판단(전체 재생성 불필요). 구현 주의: 검증기는
생성 경로의 검색 결과를 재사용하지 말고 자체 사전으로 독립 재대조할 것(공통 원인 실패 방지).
(pass/fail 신호는 추후 GRPO의 verifiable reward로 재사용 가능)

## 17. 논문 기여 프레이밍 (경계 실험 총괄)

baseline 표 현황: B0 프롬프트 일괄 분할(정성 실패만, **수치화 필요**) / B1 attention 무학습
(정확일치 32%, 9B) / B2 attention+로지스틱(top-1 93.1%, 9B, 구라벨) / B3 채팅 모드 프롬프팅
(무작위 — 템플릿이 원인) / B4 completion 프롬프팅(정밀 0.56/재현 0.34) / **ours: head 0.988/0.990,
완전일치 97.4%, 문장부호 무의존**.

기여 주장은 probe(교과서 기법)가 아니라 세 곳에: ① **단위 정의** — segment를 구문적 절이 아닌
"service 사용 1회"로 정의, 닫힌 인벤토리를 실데이터로 실증(9가족 100%, 20패턴) ② **판별 방식
전환의 실증** — 같은 모델·과제에서 생성 판단(0.56/0.34) vs 표현 읽기(0.99/0.99), 비용 ~0
③ **스트리밍 성립 조건의 언어·도메인 분석** — 시간 단조성(역순 0/382) + head-final 회고 표지
(lookahead 무이득 실측). wait-k는 simultaneous MT에서 빌린 개념 — 인용하고, **k의 실측값**
(경계 k≈0~1 포화, 역할 k≤4, 전역 무이득)과 그 언어적 설명을 기여로 쓴다. 궁극의 주장은
파이프라인 전체의 끝단 비교(유한 선택 연쇄 vs 일괄 생성)로 완성됨.

## 22. 그래프 정식화 & 층별 프로빙 — abnormal 4종 (2026-08-18, `experiments/graph/`)

**정식화 전환**: 조립 출력을 "트리 + 텍스트 순서"에서 **범위 트리 + 범위 안 부분순서**로. 텍스트 순서는 prior, abnormal 절은 간선을 추가:

- `synth_pairs.py`: 정상 355의 gold 배치에서 최소쌍 합성 + gold 그래프(parent/role/anchor/exec) 자동 부여 — post 77 · after 149 · before 149 · before0 3 · filler 355 · **event 160**(같은 기기·다른 동작 방해자: "X를 켜고 N분 뒤 X를 꺼줘. X를 (켜고|끄고) 나서 D" — 어휘 중복으로는 못 고름). 총 1,248문, `pairs.json`.

**발견**
1. "깊은 층에 관계·참조가 있다" 가설 **기각**. 범위·방향·선행사·필러 모두 **L2~L12에서 최고**, L23은 일관되게 최저(다음 토큰 예측 쪽으로 표현이 재편). 경계(L2)·타입(L6)과 **같은 prefill의 같은 얕은 층**에서 관계까지 선형 판독 가능 → head 여러 개를 얕은 층 하나에 얹는 설계가 정당화됨.
2. 사건 동일성: 참조 절 "X를 끄고 나서"가 "X를 켜고"가 아니라 "X를 꺼줘"를 가리킨다는 판별이 얕은 층 쌍 로지스틱으로 0.975 (cos·어휘는 우연 수준) — 표현이 **개체(기기)가 아니라 사건(동작)** 을 구별. 도메인 참조는 사건 참조라는 주장의 근거.
3. 방향(before/after)은 참조 절이 아니라 **뒤따르는 행동 절 D의 표현**에서 1.0 판독 — causal 문맥이 "이 행동은 앞 사건보다 먼저"를 D 위치에 이미 실어 나름 → 스트리밍에서 D 절 끝에서 재배열 확정 가능(지연 0절).
4. 조건 후치의 뒤→앞 부모도 0.98 — 후치는 "표현이 없어서"가 아니라 "조립 규칙이 단조성을 가정해서" 실패했던 것.
- 주의: after/before의 선행사 항목은 앵커가 항상 마지막 "…줘" 절이라(명사화 가능 조건) 자명 → 보고에서 제외, event 종류만 유효. 합성 템플릿 안 결과이므로 자연 발화 확대 필요.

다음: 이 얕은 층 표현으로 **타입 조건부·기호 앵커 간선 스코어러 + IR 문법 제약 선형화**(vanilla biaffine 대조), 지표 = 범위 부모·앵커·실행 순열 일치.

## 23. 그래프 파서 — 역할·범위 부모·앵커 head + 문법 제약 선형화 (`graph/parse.py`)

L6 절 끝 표현(PCA256) 위 로지스틱 3개 + 결정론적 선형화. 데이터 pairs.json 1,233문(정상 355 + abnormal 878), 명령 단위 5-fold. 타입은 gold(§20 G/G 조건과 동일).
- 역할 head(8: scope/cont/wait/act/delay/ref/filler/time) → 필러 탈락·참조 절 식별·범위 머리 식별.

**읽기**
- abnormal 4종은 사실상 전부 해결(≈1.0). 규칙 조립기(§20)는 이들에서 0. 반대로 정상은 규칙 1.0 vs 파서 0.918 — 잔여는 중첩 범위(외/내 범위 선택), gold의 wait/if 흔들림, "N분마다 ~해줘"처럼 한 절이 범위 머리이자 행동인 경우(역할 1개로 못 담음).

- 위치 prior(+P)가 +1.4pp, 타입 조건부(+T)는 +0.1pp: 표현이 이미 타입을 담고 있어 명시 타입은 거의 무이득. "타입 조건부 biaffine" 주장은 약함 → prior·기호 앵커·문법 제약이 진짜 기여.
