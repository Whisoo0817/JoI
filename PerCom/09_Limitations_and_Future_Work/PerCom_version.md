# Limitations and Future Work — PerCom working draft

VETS proves neither that an LLM interpreted a natural-language request correctly nor that a user understood and confirmed the intended behavior. Its technical claim starts from a confirmed Timeline and binding plan. The current evaluation therefore cannot establish usability, explanation quality, or NL-to-Timeline accuracy.

The certificate is relative to a declared execution model and supported interpreters. Inputs follow typed domains and a default 100 ms change grid, internal deadlines follow the modeled timing rules, and physical-device, network, and unmodeled platform effects are outside the trace relation. JoI is the only implemented backend. The current binding contract rejects multiple distinct selectors for the same service-method pair, and the current verifier excludes parallel Timeline branches, overlapping cron instances, and multi-automation execution. Resource exhaustion or an unfinished search yields no equivalence certificate.

VETS also relies on trusted preparation and execution components. The current soundness argument is a manual proof about the declared algorithms and their preconditions rather than a machine-checked proof of the Python implementation. The exact bounded evaluator and Explorer share portions of the one-step execution machinery; E2 must therefore expose the remaining common-mode risk and use independent semantic checks where possible.

A deterministic Timeline-to-JoI compiler is an important alternative that we do not compare in this work. Such a compiler could remove one source of generation variability, but it would still require a faithful implementation and validation of its source and target semantics. Evaluating compiler-based lowering against the present LLM-based pipeline remains future work.

One future direction is specification-centered maintenance. A user could edit and reconfirm a stored Timeline, regenerate or revise its linked implementation, and re-run validation before deploying the new version. This workflow requires explicit version links among the IR, binding, code, and runtime contract; changing an operator alone does not update deployed behavior.

A second direction is a multi-automation Explorer that executes verified IRs under shared time, sensor, and state models to detect opposite commands, duplicates, short-interval overwrites, periodic conflicts, oscillations, and causal interference. The combined explorer could prioritize existing IRs whose bindings or state dependencies overlap with a newly registered IR and merge cron, period, delay, and sustained-wait boundaries to search for the first conflict. This remains future work: dependency filtering must state what interactions it may miss, and physical causality between actions and sensor conditions requires an additional environment model.

We do not evaluate Home Assistant as a backend. If time permits, an imperative openHAB rules or scripting path could provide a narrowly scoped second-backend study, but it would require its own semantics adapter and evaluation. Without that implementation, VETS makes no multi-platform or smart-home-wide generality claim.
