# Limitations and Future Work · Conclusion 작성 계획

작성일: 2026-09-18
범위: 두 절의 구조와 주장 범위를 정하는 간단한 독립 작성 계획. 새로운 결과 감사나 전체 논문 구성 변경은 포함하지 않는다.

## 1. 구성 결정

- Evaluation 다음에 **Limitations and Future Work**, 그 다음에 **Conclusion**을 별도 절로 둔다.
- 한계·향후 과제는 영어 약 220–280단어, 3문단을 목표로 한다. 결론은 약 100–130단어, 1문단으로 쓴다. 이는 편집 목표이며 학회 규정으로 제시하지 않는다.
- 표, 그림, 수식, 문단별 소제목은 추가하지 않는다. 실제 페이지 수는 작성 후 조판에서 확인한다.
- 한계는 독자가 결과를 어디까지 받아들여야 하는지 설명한다. 결론은 문제, 해결 방법, 확인한 결과, 기여를 묶는다.
- 미래 연구는 현재 한계와 연결되는 방향만 남긴다. 기능 제안 목록으로 만들지 않는다.

## 2. Limitations and Future Work: 문단별 설계

### 문단 1 — 무엇을 검증하며, 무엇은 별도 문제인가 (약 60–75단어)

**독자에게 남길 내용:** 확인된 Timeline IR과 구현의 행동 일치를 보장하는 것과, 자연어 의도 또는 실제 기기 동작을 보장하는 것은 다르다.

- 확인된 IR을 기준으로 행동과 발생 시각을 비교한다는 점에서 시작한다.
- 사용자가 요청을 제대로 표현·확인했는지와 실제 환경의 기기·통신 효과는 현재 평가 범위 밖이라고 짧게 연결한다.
- 센서 격자, clock 규칙, binding 제약을 다시 설명하지 않는다. 실행 모델의 정의는 앞 절에 맡긴다.
- 사용자 의도 확인과 실제 환경 검증이 추가로 필요하다는 정도로 끝낸다. 구체적인 사용자 연구 설계까지 제안하지 않는다.

근거: [Section 6](../06_Code_Generation_and_Behavioral_Validation/PerCom_version.md)의 보장 조건과 [Evaluation](../08_Evaluation/PerCom_version.md)의 E3 범위 설명.

### 문단 2 — 현재 구현의 범위와 가능한 확장 (약 80–100단어)

**독자에게 남길 내용:** IR로 표현할 수 있는 동작이라도 Explorer가 항상 검사를 완료하는 것은 아니다.

- 현재 구현은 JoI를 대상으로 하며, 지원하지 않는 연산이나 탐색 비용 때문에 결론을 내리지 못하는 경우가 있음을 설명한다.
- 여러 자동화가 함께 실행될 때의 상호작용은 현재 검사 밖이라는 점을 덧붙인다.
- 다른 실행 환경 및 자동화 간 상호작용으로의 확장을 향후 과제로 연결한다. 충돌 종류나 탐색 알고리즘은 나열하지 않는다.
- **직접 컴파일하는 대안은 1–2문장으로 다룬다.** Timeline IR에서 JoI 코드를 직접 생성하는 컴파일러도 가능한 설계이며 현재 LLM 기반 생성 방식과 비교하지 않았다고 명시한다. 어느 쪽이 더 우수하거나 검증이 반드시 필요한지는 이 결과만으로 단정하지 않는다.

근거: Section 6의 지원·완료 조건, Evaluation의 E2 미확정 결과와 E4 시간 초과, 기존 [handoff](HANDOFF.md)의 컴파일러 비교 미실시 기록.

### 문단 3 — 실험 결과를 일반화할 수 있는 범위 (약 80–105단어)

**독자에게 남길 내용:** 현재 결과는 유용한 사례별 증거이며 모든 요청, 구현, 환경을 포괄하는 정확도 추정은 아니다.

- E1의 해석·기대 행동은 작성 과정의 판단에 의존하고 모든 사례가 독립 검토된 것은 아니라는 한계를 간단히 남긴다. 이는 사례 수와 별개의 한계다.
- E2의 별도 구현과 입력 검사는 구현 오류를 찾는 근거이지만, 유한한 입력 검사로 모든 입력에서의 정확성을 입증하지는 않는다고 쓴다.
- E3는 연구진이 구성한 JoI용 명령어 집합, E4는 한 프로그램 틀에서 만든 변형이라는 범위를 연결한다.
- 마지막에 더 다양한 사례·플랫폼에서의 평가가 필요하다고 정리한다.
- E4의 서로 다른 실행 부하 조건은 해당 실험 본문에 유지한다. 이 절에서 CPU·worker 설정을 다시 나열하지 않고, 결론에서도 공정한 조건의 속도 향상으로 바꾸어 말하지 않는다.

근거: Evaluation의 각 실험 정의와 해석, [E2 결과 기록](../08_Evaluation/E2_fidelity/extension60/RESULT_KO.md), [E3 검수 기록](../08_Evaluation/E3_EDITORIAL_REVIEW_KO.md).

## 3. Conclusion: 한 문단의 문장 순서

1. **문제와 제안:** 생성 코드가 사용자가 확인한 시간·조건 동작을 보존하는지 검사하는 VETS를 제시했다.
2. **방법:** Timeline IR로 기대 동작을 명시하고, Explorer가 허용된 공통 입력 아래 IR과 코드의 행동 및 발생 시각을 비교한다.
3. **결과:** 검사가 완료되면 선언된 실행 모델 안에서 행동 일치를 보장하고, 차이가 있으면 이를 보여주는 입력을 제공한다. 미완료 검사를 성공으로 취급하지 않는다.
4. **평가 근거:** 기본안은 E3의 **382개 생성 후보에서 68개 행동 불일치를 찾아 구체 실행으로 확인했다**는 결과 하나만 사용한다. 이는 Explorer의 구체 실행 확인이며 E2의 별도 구현 검증과 혼동하지 않는다. 숫자를 줄여야 한다면 정성적 요약으로 바꾸되 새 성능 주장을 넣지 않는다.
5. **기여:** 사용자가 확인한 동작을 생성 코드의 검사 기준으로 사용한다는 기여로 끝낸다. 미래 과제나 모든 실험 수치를 반복하지 않는다.

결론의 실험 문장은 최신 결과와 기록을 다시 대조한 뒤 확정한다. 이 계획 자체를 새로운 실험 검증으로 취급하지 않는다.

## 5. 주장·중복 검수 기준

- E1의 92건 표현 성공과 Explorer의 검증 가능 범위를 구분한다.
- E2의 관찰된 모순 없음은 검증기 정확도 100%라는 뜻이 아니다.
- E3의 동등 판정 비율은 자연어 이해 정확도가 아니다. 한 번 수정한 결과는 반례 피드백만의 인과적 효과로 주장하지 않는다.
- E4 결과를 동일 부하 조건의 속도 향상이나 모든 프로그램 구조에서의 확장성으로 일반화하지 않는다.
- 사용자 평가, 실제 기기 배포, 여러 플랫폼 지원, 자동화 간 충돌 검사를 완료한 것처럼 쓰지 않는다.
- 알려진 한계를 추상적인 “추가 연구가 필요하다”로만 대체하지 않는다. 다만 같은 제약을 두 절에서 반복하지 않는다.
- 이 두 절에는 새로운 선행연구 비교나 신규 인용을 계획하지 않는다. 직접 컴파일러는 가능한 대안으로만 언급하며 우열을 주장하지 않는다.
