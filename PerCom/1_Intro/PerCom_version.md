# Introduction — PerCom working draft

Large language models are making smart-home automation accessible to users who do not write platform code. A user can describe a desired behavior in natural language and obtain a program for a platform-specific automation language. Generation, however, creates a second problem: the produced program may be syntactically valid, use the right devices and services, and execute without error while still implementing a different behavior.

This risk is acute for **reactive-temporal automation implemented as imperative code**. The requested behavior may depend on when a condition is sampled, whether a timer resets after an interruption, which sensor value survives a delay, or how state changes across repeated executions. These decisions are often distributed across variables, timers, and control flow rather than represented by one dedicated construct. As a result, two programs with different syntax can implement the same behavior, while code that closely resembles the request can diverge on a boundary history.

Consider the request “when the room has been continuously vacant for five minutes, turn off the plug once.” A correct implementation restarts the five-minute interval whenever occupancy returns. An implementation that waits five minutes after the first vacant event and then checks only the current state appears correct while the room remains vacant. It fails when vacancy begins at 0 minutes, occupancy returns at 4 minutes, and vacancy resumes at 4.5 minutes: the implementation can turn the plug off at 5 minutes, whereas the confirmed sustained condition permits the action only at 9.5 minutes. Syntax checks, nominal execution, and a single ordinary test do not expose this difference.

To evaluate whether an LLM judge can serve as a gate for generated code, we asked three judges to assess rewrites of 52 programs that all three had accepted in at least two of three identical asks, where the checker of Section~\ref{sec:explorer} proves each rewrite behaviorally equivalent to its source. The local judge (Qwen3.5-9B) returned the same verdict across all three asks for every one of the 217 programs submitted, yet it rejected the rewrite in 16 of 17 cases that halve and gate the periodic schedule and in 10 of 11 cases that write out a counted loop. In contrast, the two hosted judges (GPT-5.4-mini and Claude-Sonnet-5) rejected rewrites no more often than they contradicted themselves, returning inconsistent verdicts on 36 and 21 of the same 217 programs before any rewrite. Consequently, neither kind of judge provides the property that a deployment gate requires, namely that programs with equal behavior receive equal verdicts (Table~\ref{tab:judge}).

Existing work offers valuable ways to structure natural-language requirements, define temporal properties, execute trigger-action programs, and verify automation models. These approaches establish that formalization and model checking are feasible; our problem begins after a user has selected a particular behavior. We ask whether a separately generated imperative implementation preserves that confirmed behavior, including the timing, target, arguments, multiplicity, and explicit order of observable actions.

We present **VETS**, which places a user-confirmed Timeline and binding plan between natural-language authoring and JoI code generation. Timeline is a per-automation executable behavioral specification for the supported JoI scope. Its operational semantics derive the reference ACTION trace for a given initial state and timed input history. The same confirmed specification guides LLM lowering, but the lowering is not trusted: Behavioral Explorer executes the Timeline reference and generated JoI through their semantic interpreters under a shared model and explores their reachable product states on demand. It returns an equivalence certificate only when the applicable search path completes, a replayable witness when it finds a trace difference, and a non-certifying outcome for unsupported or incomplete checks.

This paper makes three contributions. First, it defines Timeline and its binding contract as an executable reference that connects user confirmation, reactive-temporal semantics, and generation of imperative automation code. Second, it formulates implementation preservation as equality of timed observable ACTION traces and develops an on-the-fly product exploration procedure with explicit completion and trust conditions. Third, it characterizes the supported behavior boundary, validation fidelity, application to generated JoI candidates, and exploration cost through E1–E4. The guarantee begins from a correctly confirmed specification; natural-language interpretation, user comprehension, physical-device correctness, and additional platform backends remain outside its scope.
