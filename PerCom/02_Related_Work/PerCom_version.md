# Related Work — PerCom working draft

> 2026-09-18: 기존 연구를 검사 기준별로 묶고 가까운 연구와의 비교를 보강했다. 컴파일러 대안은 Future Work에 유지하며, Overleaf 본문은 변경 표시 없는 최종 텍스트다.

**Property-based verification.** AutoTap~\cite{autotap} synthesizes or repairs trigger-action programming (TAP) rules to satisfy user-selected linear temporal logic (LTL) safety templates. TAPInspector~\cite{tapinspector} model-checks timing-aware rule sets for safety and liveness violations, and TAPFixer~\cite{tapfixer} repairs these violations. Soteria~\cite{soteria} extracts state models from application code for property checking, while iRuler~\cite{iruler} analyzes inter-rule vulnerabilities. HAWatcher~\cite{hawatcher} monitors deployed automations against mined invariants. These studies check selected properties or invariants. VETS checks whether an implementation preserves a confirmed reference's action trace, including additional or missing actions and differences in timing.

**Checks for generated programs.** Existing checks address several aspects of generated automations. For execution feasibility, DS-IA~\cite{dsia} checks device grounding, Giudici et al.~\cite{giudici2025} measure JSON validity through framework acceptance, and IoTGPT~\cite{iotgpt} detects API violations and runtime errors. Other checks enforce particular constraints: AutoIoT~\cite{autoiot_maude} checks inter-rule conflicts, TaskSense~\cite{tasksense} checks a plan's dependency structure alongside an LLM-based solvability assessment, and AgentSpec~\cite{agentspec} enforces trigger-predicate rules at runtime. GPIoT~\cite{gpiot} evaluates generated signal-processing and ML algorithm code with execution tests. These checks provide evidence about feasibility, constraint satisfaction, or behavior on tested inputs. VETS's acceptance condition requires preservation of the specified actions and timing for every input history allowed by its execution model, with incomplete exploration left uncertified.

**Reactive-temporal specifications and lowering.** AwareAuto~\cite{awareauto} provides a close example of making proposed behavior explicit before execution. It builds reactive-temporal rules with event/state modes, delays, branches, and sequencing, presents them for user confirmation, and lowers them to executable JSON. Thus, both workflows use an explicit behavioral representation that the user can review. For a temporal mechanism supplied as a platform primitive, the engine implements that mechanism. In JoI, generated variables and conditionals can implement edge detection or sustained conditions, so the implementation itself must preserve their timing and state updates. VETS checks this correspondence against the confirmed IR. This comparison concerns where temporal behavior is implemented and how its preservation is checked; it does not imply a general expressive-power advantage over rule languages.

**Intent and execution assessment.** Other systems assess correspondence with requests or task goals. ChatIoT~\cite{chatiot} uses an LLM evaluator to assess format compliance and request satisfaction. LACE~\cite{lace} back-translates access-control policies into natural language and uses a natural language inference model to assess equivalence with the request; it separately checks policy conflicts with a satisfiability modulo theories (SMT) solver. SimuHome~\cite{simuhome} assesses agents against benchmark goal states and required tool calls in a simulator. These references differ from VETS's confirmed executable specification. VETS assumes that this specification captures the user's intent and checks the subsequent implementation against it. Its guarantee therefore concerns specification preservation within the execution model, not correctness of the initial natural-language interpretation or physical task completion.

## 이전 편집 기록 (2026-09-18 축약 전, 논문 본문 아님)

- R1은 분류 문장만 남겼다. R2–R7의 문단 순서와 개별 연구 소개 순서를 보존했다. R8은 현재 positioning으로 다시 썼다.
- 굵게 표시는 대응 SenSys 문단과의 내용 변경을 뜻한다. 삭제만 일어난 자리에는 굵게 표시할 새 단어가 없으며, 삭제 내용은 비교표에 기록했다.
- R2의 fixed reference, R3의 모든 oracle이 사전 제공된다는 일반화, R4의 slot/mechanism 오류 가시성 단정, R5의 fixed/hand-written 일반화를 수정했다.
- CodeT의 생성 테스트, Self-Debug의 테스트 없는 설정, TaskSense의 두 검사 역할, AgentSpec의 규칙 생성, Giudici et al.의 JSON validity 평가를 해당 소개 절에서 수정했다. GPIoT의 pass@k는 평가 지표이므로 execution test 자체의 이름으로 쓰지 않았다. IoTGPT의 intent mismatch 부재라는 넓은 단정도 삭제했다.
- R6의 rendering 비교와 검사 수준에 대한 서열화, R7의 자기 인증 비판·18 agents·과거 §3 참조를 제거했다. LACE의 NLI 의미 판정과 별도 SMT conflict 검사는 구분했다.
- R1·R4·R6·R8은 NL → Timeline IR → imperative DSL의 생성·검증 파이프라인을 반영한다. Timeline IR은 LLM 코드 생성의 기준이며, 같은 확정 명세의 실행 의미로 생성 결과의 timed action 보존을 검사한다. `separately generated`를 제거하여 코드가 IR과 무관하게 생성된다는 오해를 피했다.
- R8은 AwareAuto의 자동화 생성과 TAPInspector/Soteria의 property 검사를 받아, 중간 행동 명세가 생성과 검증에 쓰이는 관계로 마무리한다. 생성 정확도·성공률 향상, model checking의 표현력 한계, Explorer의 도구 간 성능 우위를 주장하지 않는다. 사용자 의도에 맞게 확정된 IR은 전제이며 확인 UI는 기여가 아니다.
- 신규 논문·인용 키는 추가하지 않았다. 기존 조사 기록과 별도 references.bib는 보존했다.
