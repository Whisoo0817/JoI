# Related Work — PerCom working draft

> SenSys R1–R8의 문단 순서를 유지한 수정본. 굵게 표시된 단어·구절은 대응하는 SenSys 문단에서 수정·추가한 부분이며, 새로 쓴 문장은 전체를 굵게 표시했다. 삭제한 내용과 수정 이유는 [문단 비교표](RELATED_WORK_FLOW_COMPARISON.md)에 기록했다. 인용은 SenSys의 `docs/refs.bib` 키만 사용한다.

We organize prior work by **how automations are generated and** the reference each system checks against.

**Property-based verification of automations.** A rich body of work verifies **automation rules and applications** with formal techniques. AutoTap~\cite{autotap} synthesizes or repairs TAP rules, modeled as transition systems, so that they satisfy LTL safety property templates chosen by the user. TAPInspector~\cite{tapinspector} model-checks timing-aware rule sets for safety and liveness violations and TAPFixer~\cite{tapfixer} repairs such violations; related analyses uncover inter-rule and security vulnerabilities~\cite{iruler,soteria}; and HAWatcher~\cite{hawatcher} monitors deployed automations against mined invariants at runtime. **Soteria, in particular, extracts state models from application code for property checking. These systems analyze or synthesize automations against selected properties or monitor their execution against mined invariants.**

**Executable checks for generated code provide another form of reference.** GPIoT~\cite{gpiot} generates signal-processing and ML algorithm code from natural-language requirements using an on-device fine-tuned SLM and **evaluates** the result with execution tests. Outside IoT, text-to-SQL **evaluation compares** a generated query against the denotation of a gold query~\cite{spider}, and CodeT~\cite{codet} **uses generated unit tests to select code candidates.** Self-Debug~\cite{selfdebug} **uses execution feedback and code explanations, including in settings without unit tests. The reference may be supplied by a benchmark or constructed during generation.**

LLM-generated reactive automations: **from intended behavior to code. Generating reactive-temporal code requires translating the intended behavior in a natural-language request into an implementation whose actions depend on changing inputs and time. An explicit behavioral specification can guide this translation and provide a reference for checking the result.** TAP rules do carry temporal behavior, including triggers, stays-for durations, and cron-style schedules, but **when a mechanism is provided as** a platform primitive, the author fills slots and the engine implements the mechanism. In reactive-temporal code such as JoI scripts, **edge detection, sustained conditions, or counting can instead be implemented in the generated code:** the author, here an LLM, must realize **each** mechanism as an idiom built from persistent variables, conditions, and per-tick execution. **Lowering bugs can therefore arise in the state updates and control flow that implement these mechanisms.**

Some systems in this regime do check LLM output deterministically. AutoIoT~\cite{autoiot_maude} checks LLM-generated rules against four inter-rule conflict types using Maude rewriting logic. DS-IA~\cite{dsia} checks the device-grounding feasibility of a command with a deterministic cascade and rejects infeasible commands fail-closed before execution. TaskSense~\cite{tasksense} translates a sensing query into an executable tool-calling DAG, screens it with an LLM-based solvability check, and then deterministically checks that the plan's dependency graph is a subgraph of the toolset grammar. **These checks assess task solvability and plan structure, respectively.** AgentSpec~\cite{agentspec} enforces trigger-predicate safety rules on LLM agents at runtime through a DSL. **Its rules can also be generated by an LLM for user review. These checks address conflicts, command feasibility, plan structure, and runtime constraints.**

Generation systems themselves **also assess output validity and request satisfaction.** ChatIoT~\cite{chatiot} translates natural language into Home Assistant automations with multiple LLM agents and has a separate ``Evaluator'' agent assess format compliance and request satisfaction; Giudici et al.~\cite{giudici2025} **measure JSON validity by checking whether the framework accepts a generated routine**; and IoTGPT~\cite{iotgpt} catches API violations and runtime errors in a virtual SmartThings environment. AwareAuto~\cite{awareauto} builds a confirmable reactive-temporal rule with event/state modes, delays, branches, and sequencing, presents it to the user in a panel, and lowers it to executable JSON. **These systems assess request satisfaction and execution feasibility, but do not establish that imperative code generated from an executable behavioral specification preserves that specification's timed action traces.**

**Other systems assess intent consistency or task completion more directly.** LACE~\cite{lace} back-translates a generated access-control policy into natural language with deterministic templates and judges semantic equivalence against the original request with a fine-tuned **natural language inference (NLI)** model. **It separately checks policy conflicts using satisfiability modulo theories (SMT).** SimuHome~\cite{simuhome} judges agent behavior against goal states **and required tool calls** in a time-accelerated simulator. **Its goals are defined by the benchmark,** and it evaluates agents rather than gating deployment.

**Prior work provides reactive-temporal representations for generating automation rules, as in AwareAuto~\cite{awareauto}, and verifies rule or application models against specified properties, as in TAPInspector~\cite{tapinspector} and Soteria~\cite{soteria}. In VETS, Timeline IR mediates the translation from natural-language requests to imperative reactive-temporal DSL code by making the intended event, state, and temporal relationships explicit. Once confirmed, the IR guides LLM code generation and, through its deterministic operational semantics, provides the executable reference for checking whether the generated implementation preserves its timed action traces under the declared execution model.**

편집 메모 (논문 본문 아님):

- R1은 분류 문장만 남겼다. R2–R7의 문단 순서와 개별 연구 소개 순서를 보존했다. R8은 현재 positioning으로 다시 썼다.
- 굵게 표시는 대응 SenSys 문단과의 내용 변경을 뜻한다. 삭제만 일어난 자리에는 굵게 표시할 새 단어가 없으며, 삭제 내용은 비교표에 기록했다.
- R2의 fixed reference, R3의 모든 oracle이 사전 제공된다는 일반화, R4의 slot/mechanism 오류 가시성 단정, R5의 fixed/hand-written 일반화를 수정했다.
- CodeT의 생성 테스트, Self-Debug의 테스트 없는 설정, TaskSense의 두 검사 역할, AgentSpec의 규칙 생성, Giudici et al.의 JSON validity 평가를 해당 소개 절에서 수정했다. GPIoT의 pass@k는 평가 지표이므로 execution test 자체의 이름으로 쓰지 않았다. IoTGPT의 intent mismatch 부재라는 넓은 단정도 삭제했다.
- R6의 rendering 비교와 검사 수준에 대한 서열화, R7의 자기 인증 비판·18 agents·과거 §3 참조를 제거했다. LACE의 NLI 의미 판정과 별도 SMT conflict 검사는 구분했다.
- R1·R4·R6·R8은 NL → Timeline IR → imperative DSL의 생성·검증 파이프라인을 반영한다. Timeline IR은 LLM 코드 생성의 기준이며, 같은 확정 명세의 실행 의미로 생성 결과의 timed action 보존을 검사한다. `separately generated`를 제거하여 코드가 IR과 무관하게 생성된다는 오해를 피했다.
- R8은 AwareAuto의 자동화 생성과 TAPInspector/Soteria의 property 검사를 받아, 중간 행동 명세가 생성과 검증에 쓰이는 관계로 마무리한다. 생성 정확도·성공률 향상, model checking의 표현력 한계, Explorer의 도구 간 성능 우위를 주장하지 않는다. 사용자 의도에 맞게 확정된 IR은 전제이며 확인 UI는 기여가 아니다.
- 신규 논문·인용 키는 추가하지 않았다. 기존 조사 기록과 별도 references.bib는 보존했다.
