# Related Work — PerCom working draft

> 작업 범위: 짧은 도입(P0)과 네 문헌 묶음(P1–P4). 굵게 표시된 단어·구절만 SenSys 원문에서 수정·추가한 부분이다. 삭제·이동은 [문단 비교표](RELATED_WORK_FLOW_COMPARISON.md)에 기록했다. 신규 인용 키는 [references.bib](references.bib), 기존 키는 `docs/refs.bib`에 있다.

We organize prior work by **the artifact under analysis and** the reference each system checks against.

**Property and conflict verification**. A rich body of work verifies **automation behavior against specified properties using** formal techniques. AutoTap~\cite{autotap} synthesizes or repairs TAP rules, modeled as transition systems, so that they satisfy LTL safety property templates chosen by the user. TAPInspector~\cite{tapinspector} model-checks timing-aware rule sets for safety and liveness violations, and TAPFixer~\cite{tapfixer} repairs such violations. **IoTSan~\cite{iotsan} translates IoT app code into Promela models and uses Spin to detect safety violations arising from app interactions and device or communication failures. Related** analyses uncover inter-rule and security vulnerabilities~\cite{iruler,soteria}. AutoIoT~\cite{autoiot_maude} checks LLM-generated rules against four inter-rule conflict types using Maude rewriting logic. HAWatcher~\cite{hawatcher} monitors deployed automations against mined invariants at runtime. **These systems check automations against selected properties, conflict definitions, or invariants**.

**Evaluation of generated code and policies**. GPIoT~\cite{gpiot} generates signal-processing and ML algorithm code from natural-language requirements and **evaluates** the result with execution tests. ChatIoT~\cite{chatiot} translates natural language into Home Assistant automations with multiple LLM agents and has a separate ``Evaluator'' agent assess format compliance and request satisfaction. LACE~\cite{lace} back-translates a generated access-control policy into natural language with deterministic templates and judges semantic equivalence against the original request with a fine-tuned **natural language inference (NLI)** model. **LACE also checks conflicts using satisfiability modulo theories (SMT), separately from its model-based intent assessment. Model-based assessments of request satisfaction do not by themselves establish that generated code preserves the intended execution behavior. For LLM-based code evaluation, Moon et al.~\cite{moon2026cover} show that semantically equivalent code can receive different scores under surface variations. Our motivation experiment (§3) further examines the consistency of LLM-based judgments for reactive-temporal automation code**.

**Intent formalization and confirmation**. AwareAuto~\cite{awareauto} builds a confirmable reactive-temporal rule with event/state modes, delays, branches, and sequencing, presents it to the user in a panel, and lowers it to executable JSON. **For temporal-logic specifications, nl2spec~\cite{nl2spec} lets users revise mappings between natural-language fragments and subformulas, while ARTEMIS~\cite{artemis} uses distinguishing traces to help users assess candidate formalizations. These approaches support the construction and confirmation of specifications. VETS assumes that the confirmed Timeline IR captures the intended behavior and focuses on verifying whether the generated implementation preserves that behavior**.

**Implementation behavior preservation. AutoTap, TAPInspector, and IoTSan synthesize or analyze automations against specified properties. VETS verifies whether an independently generated imperative implementation preserves the timed action traces of a confirmed executable specification under the declared execution model. When an automation platform provides a** temporal **mechanism as a primitive**, the engine implements **that** mechanism. In **our JoI setting, the LLM must realize mechanisms** such as edge detection, sustained conditions, or counting as **idioms** built from persistent variables, conditions, and per-tick execution. **To check these imperative implementations, Behavioral Explorer jointly explores IR and JoI execution states through their semantic interpreters and compares timed action traces under a shared input and time model. A deterministic Timeline-to-JoI compiler is another possible implementation path that we do not evaluate here.**

편집 메모 (논문 본문 아님):

- P0는 SenSys R1의 분류 문장만 남겼다. reference 확보·authoring으로 기여를 유도하는 배경은 삭제하고 Intro의 문제 설명을 반복하지 않는다.
- P1은 R2의 개별 연구 설명을 유지하고 R5의 AutoIoT를 합쳤다. HAWatcher도 같은 문단에서 runtime 사례로 소개한다. 첫 문장은 TAP에 한정하지 않고 property 기반 자동화 검증으로 시작한다. 마지막은 기존 연구의 검증 기준만 정리하며 VETS 비교 문장은 삭제했다. Model checking으로 행동 동등성을 검사할 수 없다는 뜻이 아니다.
- P2는 R3의 GPIoT, R6의 ChatIoT, R7의 LACE 설명을 재사용했다. 실행 테스트와 모델 판정을 구별하며 LACE의 NLI 의미 일치 판정과 별도 SMT 충돌 검사도 구분한다. Moon et al.의 결과를 LACE·ChatIoT에 대한 직접 평가로 쓰지 않는다. §3 실험은 조사 범위만 예고하고 결과·수치는 반복하지 않는다.
- P3는 AwareAuto 설명을 보존하고 nl2spec·ARTEMIS를 함께 배치했다. 사용자 의도의 명세화·확인은 인접 연구로 인정하며 올바르게 확정된 IR은 VETS의 전제다. AwareAuto의 panel은 해당 연구의 기능 설명이므로 유지하고, 렌더링 방식의 우열 비교는 삭제했다.
- P4는 AutoTap·TAPInspector·IoTSan의 속성 기반 합성·분석과 VETS의 명세–구현 행동 보존을 대비한다. IoTSan의 모델 변환·검사 설명은 P1에 추가했다. Murphy et al.의 합성과 translation validation은 이번 흐름에서 제외했다. R4의 primitive/idiom 설명은 이 문단에서 재사용한다. DSL을 목표로 한다는 사실만을 차별점으로 삼지 않고 별도 생성된 imperative 구현의 의미 보존을 설명한다. 검사 원리 자체의 최초성은 주장하지 않으며 compiler는 미평가 대안으로 인정한다.
- CodeT/Self-Debug, DS-IA, TaskSense, Giudici et al., IoTGPT, AgentSpec, SimuHome의 개별 설명은 분량과 초점 때문에 이번 초안에서 제외했다. 기능 부재나 열등함의 근거가 아니다. CASPER·Req2LTL·VIGIL 및 synchronous compiler validation은 후속 인용 선정 후보로 HANDOFF에 남긴다.
- 각 묶음은 연구의 비교 목적에 따른 배치다. 한 시스템이 모델 판정·형식 검사·사용자 확인을 함께 지원할 수 있으므로 상호 배타적인 기능 분류로 읽지 않는다.
- 사용자 확인은 전제이며 렌더링·사용성·on-device·분야 전체의 최초성은 차별화 근거로 사용하지 않는다. 세미콜론의 마침표 전환 등 문장부호 정리만으로는 볼드를 추가하지 않았다.
