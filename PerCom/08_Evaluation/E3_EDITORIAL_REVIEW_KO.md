# E3 제출 원고 검수 — 2026-09-18

범위: PerCom 본회의 제출을 목표로 한 E3의 주장, 실험 설명, 결과 해석, 재현성 검토. 전체 논문의 게재 가능성 판정이나 새 실험 결과 감사는 아니다. 본문과 최신 실행 기록을 대조하고, 별도 맥락의 검토자에게도 검토를 맡겼다.

## 참고한 논문과 적용 범위

- [SEAL: Semantically Encoding Activity Labels for Context-Aware Human Activity Recognition, PerCom 2025](https://web.cs.wpi.edu/~kmlee/pubs/ge25percom.pdf), IV절: 평가 데이터셋을 명시하고 상세 데이터·설정은 공개 저장소로 연결한다. 우리에게 적용할 편집 원칙은 핵심 실험 정의는 본문에, 재현 세부는 접근 가능한 자료에 두는 것이다. 활동 인식의 비교 실험 구성을 우리 검증기에 그대로 요구하는 것은 아니다.
- [AutoIOT, MobiCom 2025](https://www4.comp.polyu.edu.hk/~csyqzheng/papers/AutoIOT_MobiCom2025.pdf), 5·6.1·6.4절: 응용·데이터셋, 지표, 구성요소 제거 실험을 구분한다. 우리도 시스템 적용 결과와 특정 반례 피드백의 추가 효과를 구분해야 한다. 다른 논문의 모든 설정이나 실험을 모방할 필요는 없다.

두 사례에서 도출한 편집 판단이며, 모든 PerCom 논문의 공통 형식이나 학회 의무 규정이라는 뜻은 아니다.

## 우선순위 높은 판단

### 1. Repair의 관찰 결과와 반례 자체의 효과를 구분 — 첫 문장 수정 완료

현재 본문의 36/68은 반례를 포함한 수정 절차를 한 번 적용한 결과다. 이것만으로 반례 때문에 성공률이 높아졌다고 말할 수 없다. 수정 프롬프트에는 IR 정보, 규칙, 예제도 포함된다.

기록에는 같은 68건의 반례 없는 비교 결과 31/68도 있다. paired 결과는 둘 다 성공 26, 반례 있을 때만 성공 10, 없을 때만 성공 5, 둘 다 실패 27이며 기록된 McNemar exact p는 약 0.30이다. 유의하지 않다는 사실은 두 방법이 동등하다는 증명도 아니다.

본문이 수정 절차의 적용 결과만 보고한다면 36/68과 한 차례 수정이라는 설명으로 한정한다. 반례의 추가 효과를 기여로 주장하려면 비교 결과와 불확실성을 함께 보고해야 한다. 현재 대조군을 본문에서 제외하는 작성 범위를 유지하면서, E3 첫 문장의 “반례가 도움이 되는지 평가”를 “반례를 제공해 한 번 수정한 뒤 재검사”로 바로잡았다.

근거: `E3_application/feedback/RESULTS_E3_FEEDBACK_2026-09-16.md`, `RESULTS_E3_FEEDBACK_ABLATION_2026-09-16.md`.

### 2. 382건의 성격은 필요, 388→382의 작업 이력은 본문 필수 아님

독자는 382건이 외부 수집 요청인지, 연구진이 구성한 개발 사례인지, 어떤 동작을 포함하는지 알아야 한다. E1의 외부 요청 92건이나 E2의 Gemma 후보와 자동으로 같은 모집단으로 이해하게 해서는 안 된다.

현재 기록상 개발 중 다뤄진 사례이며 IR/binding을 기준으로 한 평가다. 요청 출처·구성 방식·분할 여부를 원자료에서 확정한 뒤 본문에 짧게 명시해야 한다. 아직 확인하지 않은 무작위 선정·대표성·독립 평가셋은 주장하지 않는다. timeout/on_timeout은 평가 범위 밖이다. 388과 6을 되살릴 필요 없이 기능 범위를 설명할 수 있다. 63 재생성·319 재사용의 상세 이력은 재현 문서로 이동 가능하나, 독립적인 신규 평가셋인 것처럼 서술하면 안 된다.

### 3. 설정은 삭제보다 배치가 문제 — 예산 문장 오류 수정 완료

- CPU·Python 버전: E3의 결과 문단에 나열할 필요는 없다. 그러나 시간 한도로 미확정을 결정하므로 재현 설정에는 필요하고, E4 비용 설명과도 연결해야 한다.
- FP8·temperature·토큰 한도·thinking: E3 첫 문단에서 빼도 된다. 정확한 모델 식별자와 프롬프트·생성 설정은 제출용 부록 또는 재현 자료에 남겨야 한다. 로컬 기록만 있다고 독자가 접근 가능한 것은 아니다.
- SMT: 이름만 넣는 것은 독해를 방해한다. 판정 중단 조건 자체는 재현 정보에 필요하다. 특히 내부 질의 제한과 프로세스 제한은 다르다.
- 직전 편집의 “각 코드 20초”는 실제 설정을 잘못 단순화했다. `explorer/eval/frozen_contract.py:339`와 실행 프로토콜은 기본 20초에 기기 선택 조합 수를 곱한다. 영문·한글·TeX를 기본 한도와 확대 규칙으로 수정했다.

### 4. E3와 E2의 역할을 분명히 할 것

E2는 별도로 구현한 실행기와 비교하는 검사다. E3는 생성 후보에 Explorer를 적용한 결과이며, 68건의 확인은 Explorer의 구체 실행 재생이다. 두 검사를 같은 독립 검증으로 표현하지 않는다. 309/382는 이 후보 집합의 동등 판정 비율이지 검증기의 정확도나 자연어 요청 이해 정확도가 아니다.

### 5. 예시는 유지하되 측정 결과를 먼저 설명할 것

멀티탭 사례는 시간 차이를 검출한다는 기여를 보여주므로 가치가 있다. 카운터 구현의 긴 설명은 필요 없다. 본문에서는 “30초 동안 움직임이 없으면 꺼야 하지만 생성 코드는 29초에 껐으며, Explorer가 이 1초 차이를 검출했다” 정도로 충분하다. 세부 코드·카운터 동작은 사례 자료에 둘 수 있다.

전체 오류를 이 사례 하나로 일반화하지 않는다. 오류 유형별 분포를 주장하려면 현재 감사 라벨과 개별 근거를 확인해야 한다.

### 6. 표는 개수보다 역할을 기준으로 정리할 것

생성 코드 판정(분모 382)과 1회 수정 결과(분모 68)는 구분해야 한다. 현재의 별도 두 표는 합리적이다. 페이지가 부족하면 하나의 표에서 패널과 분모를 명확히 분리할 수 있다. 수정 성공 36만 남기지 말고 불일치 26·검사 중단 5·생성 실패 1도 유지한다. 반례 없는 효과 비교를 주장하지 않는 한 해당 비교표를 무조건 추가할 필요는 없다.

## 다음 편집의 기준

각 문단을 목적 → 필요한 실험 정의 → 결과 → 결과가 뜻하는 바의 순서로 점검한다. 단어를 줄인 뒤에는 빠진 조건 때문에 주장이 강해지거나 달라지지 않았는지 확인한다. 새 숫자는 원자료·분모·중단 조건과 대조한다. 설정을 본문에서 뺄 때는 재현 자료의 실제 위치와 제출 시 접근 경로를 확인한다. 논문에 없는 독자의 배경지식을 가정하지 않는다.
