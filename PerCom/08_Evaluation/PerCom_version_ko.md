# 평가 — PerCom 검토용 한글 초안

> 같은 폴더의 `PerCom_version.md`를 기준으로 2026-09-18에 E1 번역과 표를 갱신했다. 원문의 표·수치·실험 조건과 한계를 유지했다. 현재 논문에서는 7절이며, 자료 폴더명은 `08_Evaluation`을 유지한다.

상태: 2026-09-18 E1을 범위 내 92건 전체 평가로 갱신. 사용자 검토 전. E1–E4에 각각 표 하나를 배치한다. 반례는 수정에 필요한 행동 차이 정보로만 사용하며, 대조군 비교나 인과적 개선 주장은 본문에 넣지 않는다. 근거와 검증 메모는 `DRAFT_NOTES.md`를 참조한다.

평가는 네 가지 질문을 다룬다. Timeline IR은 외부에서 수집한 자동화 요청을 표현할 수 있는가(E1)? Explorer의 판정은 별도로 구현한 기준 실행기를 통한 검사 결과와 일치하는가(E2)? 생성 코드에는 어떤 오류가 나타나는가(E3)? 자동화의 규모와 시간 설정에 따라 검증 비용은 어떻게 달라지는가(E4)?

**평가 설정.** 모든 코드 평가는 JoI와 5·6절의 실행 모델을 사용한다. E1은 표현 가능성과 기준 실행을, E2는 판정의 타당성을, E3는 생성된 후보 코드를, E4는 검사 완료 여부와 비용을 평가한다. 지원 범위 밖이라 검사가 거절된 경우, 탐색을 완료하지 못한 경우, 오류가 발생한 경우도 각 평가의 전체 건수에 포함한다. LLM을 이용한 생성과 행동 검증은 분리한다.

## Timeline IR의 표현 적합성

E1은 Timeline IR의 연산자들을 조합해 외부에서 수집한 자동화 요청을 표현할 수 있는지 평가한다. 네 종류의 출처에서 요청 100건을 수집했다(표 E1). 저자 한 명이 반응형·시간 기반 자동화라는 연구 범위에 해당하는지 검토한 결과, 92건은 범위 내, 여섯 건은 해석이 모호한 요청, 두 건은 범위 밖으로 분류했다. 범위 내 92건 모두를 IR로 표현하고 실행해 보았다.

각 요청은 IR로 표현하기 전에 구체적인 동작 해석과 예상 액션 및 발생 시각을 기록했다. 처음 20건의 해석은 저자가 검토했고, 나머지 72건은 LLM 에이전트가 앞선 사례를 참고해 정했다. 에이전트가 예상 트레이스도 작성했으므로, 요청 의도를 서로 독립적으로 판단한 것은 아니다. 기준 IR 실행기에서 입력 이력을 재생한 뒤 액션과 발생 시각을 비교했으며, 같은 시각의 액션들은 순서를 구분하지 않고 비교했다. 결과는 최종 IR 기준으로 보고하고, 실패한 시도는 실험 기록에 보존했다.

최종 IR 92건은 입력 이력 294개 모두에서 예상 트레이스를 재현했다(표 E1). 이 사례들은 여러 연산자를 함께 사용한다. 문 열림 알림은 문이 일정 시간 동안 계속 열려 있는지 기다린 뒤 알림을 반복한다. 차고 알림은 반복 점검 안에 점멸 반복을 넣고, 저장해 둔 조명 설정을 복원한다. 스프링클러는 저장한 시각, 조건식, 반복을 조합해 어느 시점에서든 직전 48시간의 급수 시간을 10분 이내로 제한한다. 별도로 수행한 추가 점검용 입력 이력 17개도 모두 일치했으며, 표의 이력 수에는 포함하지 않았다.

이 결과는 기록한 해석과 가정을 전제로 한다. 예를 들어 평균 계산은 정해진 개수의 값을 사용하고, 점멸 요청은 구체적인 점멸 패턴을 정했으며, 서로 독립적인 자동화는 별도 Timeline으로 표현했다. 스프링클러는 1초 단위로 시간을 다루고 실행 전에는 급수 이력이 없다고 가정했다. 따라서 이 결과는 준비한 입력 이력에서의 표현과 실행을 보여준다. 모든 입력에서의 정확성이나 모든 연산자 조합의 포괄, 모든 IR에 대한 Explorer의 검증 지원을 입증하는 것은 아니다.

## 검증 판정의 타당성

Explorer의 판정을 평가하기 위해, Explorer 코드를 보지 않고 명세만으로 구현한 Timeline 실행기와 JoI 인터프리터를 기준으로 비교했다. 이 기준 실행기는 사용 전에 E1의 초기 요청 20건에 대한 트레이스 53개와 JoI 의미 규칙 확인 사례 15개를 재현했다. 평가 대상은 그 초기 요구사항 20건에 대한 올바른 구현 21개와 결함을 하나씩 넣은 변형 81개, 그리고 요청 388건으로 구성된 개발용 데이터에서 표본으로 뽑은 유효한 생성 후보 38개다. 결함은 액션 누락, 시점, 조건식, 저장값, 순서, 반복 등을 포함한 12개 유형에 걸쳐 있다. 기준 실행기는 입력 이력 48,990개에서 두 프로그램을 비교하고 Explorer가 반환한 반례도 재생했다. Explorer에는 IR–코드 쌍마다 120초, 상태 400,000개, 전이 2,000,000개의 한도를 적용했다. 실행 의미를 보존하면서 반복되는 시간·상태 탐색을 줄인 결과, 기존 판정은 바뀌지 않았고 같은 한도에서 추가로 26쌍의 판정을 완료했다.

## 생성 코드 검증

생성 후보를 평가하기 위해, 자연어에서 호출할 기능과 대상 선택자를 추론하는 과정을 거치지 않고 확정된 IR과 바인딩을 Qwen3.5-9B-FP8에 제공했다. 생성 설정은 temperature 0.1, 최대 512토큰, thinking 비활성화였다. 평가 대상은 원본 요청 388건에서 타임아웃 처리 요청 여섯 건을 제외한 382건이다. 여기에는 입력과 호출 이름의 접두부(service prefix)를 바로잡은 뒤 다시 생성한 후보 63개와 바이트 단위로 동일하게 재사용한 후보 319개가 포함된다. 평가는 Intel Core i9-11900K Linux 호스트에서 Python 3.12.11로 실행했다. 프로세스 시간 한도는 20초, 상태 한도는 200,000개, 전이 한도는 500,000개, SMT 질의당 시간 한도는 1초였다.

Explorer는 후보 377개에 대해 동등 또는 불일치 판정을 내렸다(표 E3). 이 수치는 검사 완료율을 나타내며 정확도 추정치는 아니다. 불일치 68건은 모두 Explorer의 구체적인 입력 재생으로 확인했다. 예를 들어, 움직임이 없는 상태가 30초간 지속되면 멀티탭을 끄라는 요청이 있다. 생성 코드는 최초 조건 평가 시점부터 카운터를 증가시키고 이후 매초 증가시켰으므로, 29초에 카운터가 30에 도달해 멀티탭을 껐다. 그 시점에 IR은 액션을 내지 않는다. 지원 범위 밖 사례는 이진 반환값 대입(binary return assignment), 범위가 제한되지 않은 온도 산술 연산, 큰 조도 입력 범위와 관련돼 있었다. 결론을 내리지 못한 두 사례는 모두 SMT 질의 시간 한도에 도달했다. 익숙한 과제와 재생성·재사용 후보가 섞인 이 결과는 탐색적 평가이며, 확정된 IR과 바인딩을 기준으로 한다. 자연어 의도 해석의 정확도나 실제 기기 동작을 측정한 결과는 아니다.

**코드 수정을 위한 반례.** 반례는 불일치가 발생한 입력 이력과 기대 액션, 실제 액션을 제공하여 코드 수정을 돕는다. IR과 바인딩을 고정한 채, 불일치 후보마다 같은 모델에 수정 요청을 한 번 허용했다. 수정 생성에는 temperature 0과 최대 4,096토큰을 적용하고, 수정된 코드를 다시 검사했다. 68건의 결과는 동등 36건, 불일치 26건, 검사 시간 초과 다섯 건, 모델 컨텍스트 오류 한 건이었다.

## 검증 비용과 규모

자동화 규모가 커질 때 검증 비용이 어떻게 달라지는지 평가하기 위해, 하나의 매개변수화된 프로그램 유형에서 동등한 IR–코드 쌍 30개를 생성했다. 불리언 센서 수(1–7개), 순차적인 대기–호출 단계 수(1–6개), 대기 시간(100밀리초–4시간), 반복 횟수(1–200회)를 각각 바꾸거나 조합해서 바꿨다. 각 프로그램은 회당 120초 한도에서 세 번 실행했다. 비교 기준은 timer zone을 비활성화하되 같은 의미 실행기, 다음 이벤트 시각으로의 이동, 정확히 일치하는 상태의 재사용은 유지한다. 두 방식 모두 동등 판정을 내리려면 탐색을 완료해야 한다. Explorer는 한 번에 하나씩 실행했고, 비교 기준은 8코어 호스트에서 작업 네 개를 동시에 실행했다. 따라서 보고한 시간은 이 실행 설정에서의 결과이며, 같은 부하에서 측정한 속도 향상 비율이 아니다.

| --- | ---: | ---: |

기본 설정은 센서 2개, 2단계, 대기 2분, 반복 5회다. 각 행은 명시된 매개변수만 바꾼다. 시간은 세 번의 실행 중 가장 오래 걸린 값이다. 세 번 모두 검사를 완료한 경우에만 해당 프로그램의 판정을 완료한 것으로 센다.

Explorer는 프로그램 28개의 판정을 완료했으며, 그중 19개는 1초 미만, 28개 모두는 21초 이내에 완료했다(표 E4). 완료된 Explorer 실행의 최대 메모리 사용량은 44 MiB 미만이었다. 대기 시간을 바꾼 실험에서 검증 시간은 0.05–0.35초였다. 센서 수가 늘어나면 각 단계에서 검사하는 입력 조합이 증가했다. 센서가 7개인 사례는 상태 52개를 유지했지만, IR과 코드를 함께 진행하는 전이 31,832개를 탐색했다. 완료하지 못한 두 프로그램은 센서 6개 또는 7개, 6단계, 반복 50회 또는 100회를 조합한 경우였다. 둘 다 지원 범위 밖이라 거절된 것이 아니라 할당된 자원을 소진했다. 이 측정은 해당 합성 프로그램 유형의 검사 완료 여부와 비용을 보여주며, 판정의 정확성이나 임의의 생성 코드에 대한 비용을 나타내지는 않는다.
