# Related Work and Positioning — 한글 검토본

> 같은 폴더의 [main.md](main.md)와 `overleaf-paper/main.tex`의 해당 절을 번역했다. SenSys의 검증 기준에 따른 논리 순서를 유지하면서 중복 설명을 줄이고, 주요 연구의 비교를 표로 정리했다.

가정용 자동화의 검증이 처음부터 해결되지 않은 문제였던 것은 아니다. 사용자가 규칙을 직접 작성할 때는 그 규칙 자체가 분석 대상이었으며, 형식 기법으로 정해진 속성을 만족하는지 검사할 수 있었다. 실행 가능한 테스트를 제공하는 도메인에서 코드를 생성할 때는 테스트가 오라클 역할을 했다. 두 경우 모두 검증을 시작하기 전에 검사 가능한 기준이 존재했다. LLM 기반 authoring은 사용자를 직접 작성하는 사람에서 요청하는 사람으로 바꾼다. 이 변화는 요청과 이를 구현하는 결과물을 분리하며, 생성된 코드가 사용자가 요청한 구체적인 동작을 구현하는지라는 추가 질문을 제기한다. 따라서 각 시스템이 무엇을 기준으로 검사하는지에 따라 기존 연구를 정리한다. Table 1은 대표 시스템의 프로그램 표현, 검사 기준, 방법을 비교한다.

**검증 기준이 이미 존재하는 경우.** TAP 규칙을 형식 기법으로 검증하는 연구는 폭넓게 이루어져 왔다. AutoTap~\cite{autotap}은 사용자 지정 LTL 안전 속성을 만족하도록 TAP 규칙을 합성하거나 수정한다. TAPInspector~\cite{tapinspector}는 시간 정보를 고려한 규칙 집합의 안전·활성 속성 위반을 모델 검사하고, TAPFixer~\cite{tapfixer}는 이러한 위반을 수정한다. 관련 분석은 규칙 간 취약점과 보안 취약점을 찾아내며~\cite{iruler,soteria}, HAWatcher~\cite{hawatcher}는 추출한 불변식을 기준으로 배포된 자동화를 모니터링한다. 이들 시스템은 시간적 동작과 규칙 상호작용을 포함한 자동화 동작의 속성을 검사한다.

대상 도메인이 실행 가능한 오라클을 제공하는 코드 생성에서도 기준을 사용할 수 있다. GPIoT~\cite{gpiot}는 자연어 요구사항으로부터 신호 처리 및 ML 알고리즘 코드를 생성하고, 실행 테스트로 생성 코드를 평가한다. IoT 밖에서는 text-to-SQL이 정답 쿼리의 실행 결과를 기준으로 생성 쿼리를 평가한다~\cite{spider}. 이러한 평가에서는 테스트 사례나 정답 결과가 기준을 제공한다.

**LLM이 생성하는 반응형 자동화.** 이 경우 의도한 동작은 사용자의 요청에 담겨 있으며, 앞으로의 동작 시퀀스에 정답을 부여한 테스트 집합이 미리 주어지지 않는다. TAP 규칙도 트리거, 지속 시간, 스케줄을 비롯한 시간적 동작을 표현한다. 그러나 JOI 스크립트에서는 에지 감지, 조건의 지속, 횟수 세기 등의 메커니즘을 영속 변수, 조건문, tick마다의 실행으로 구현해야 한다. 일부 시스템은 LLM 출력을 결정적으로 검사한다. AutoIoT~\cite{autoiot_maude}는 Maude 재작성 논리를 사용하여 생성 규칙의 네 가지 규칙 간 충돌 유형을 검사한다. 다른 시스템은 요청을 더 직접적으로 평가한다. ChatIoT~\cite{chatiot}는 자연어를 Home Assistant 자동화로 변환하고, LLM Evaluator로 형식 준수와 요청 충족 여부를 평가한다. AwareAuto~\cite{awareauto}는 이벤트·상태 모드, 지연, 분기, 순서를 포함하는 반응형·시간 기반 규칙을 구성하고, 사용자가 수정할 수 있도록 제시한 뒤 실행 가능한 JSON으로 변환한다. 이 과정은 규칙 개선과 배포 가능성을 지원하지만, 규칙과 구현 사이의 별도 trace 동등성 검사는 포함하지 않는다.

**요청을 기준으로 검사하는 경우.** LACE~\cite{lace}는 생성된 접근 제어 정책을 자연어로 역변환하고 NLI 모델로 원래 요청과의 의미적 동등성을 판단하며, 정책 간 충돌은 SMT 솔버로 별도 검사한다. 따라서 요청 부합성 판단은 정책의 의미를 다루고, 형식 검사는 정책 간 충돌을 다룬다.

LACE와 AwareAuto는 서로 다른 측면에서 가깝다. LACE는 생성된 결과물을 사용자의 요청과 대조하고, AwareAuto는 반응형·시간 기반 표현을 구성한다. VETS는 Timeline IR을 사용하여 요청된 자동화의 시간적 제어 흐름을 명시하고, 생성된 JOI 코드를 위한 실행 가능한 기준을 제공한다. Behavioral Explorer는 허용된 모든 입력 시퀀스에 대해 코드가 IR의 timed action trace를 보존하는지 검사한다. 그 보장은 확정된 IR이 의도한 자동화를 담고 있다는 가정 아래, 정해진 입력값 범위와 실행 규칙 안에서 IR과 코드가 부합하는지에 관한 것이다. 생성과 검증을 결합하는 것 자체를 신규성으로 주장하는 것은 아니며, 본 연구는 생성된 반응형·시간 기반 자동화 코드에 대한 이러한 행동 검사에 초점을 둔다.

**Table 1. 검사 대상, 기준, 방법에 따른 대표 시스템 비교.** 각 행은 명시된 검사를 요약하며, 해당 시스템의 모든 구성 요소나 평가 지표를 나열하지 않는다.

| 시스템 | 검사 대상 | 검사 기준 | 방법 |
|---|---|---|---|
| AutoTap~\cite{autotap} | TAP 프로그램 | 사용자 지정 LTL 안전 속성 | 오토마타 기반 합성·수정 |
| TAPInspector~\cite{tapinspector} | 시간 정보를 포함한 TAP 규칙 | 안전·활성 속성 | 모델 검사(NuSMV) |
| GPIoT~\cite{gpiot} | 생성된 IoT 알고리즘 코드 | 사람이 작성한 테스트 사례 | 실행 테스트(오프라인 평가) |
| AutoIoT~\cite{autoiot_maude} | 생성된 TAP 규칙의 모델 | 네 가지 충돌 정의 | Maude 상태 공간 탐색 |
| ChatIoT~\cite{chatiot} | 생성된 TAP 표현 | 사용자 요청, 맥락, 형식 요구사항 | LLM Evaluator |
| AwareAuto~\cite{awareauto} | 반응형·시간 기반 규칙과 기기 인터페이스에 연결된 JSON | 사용자 의도와 기기 인터페이스 | 사용자 수정 및 배포 검사 |
| LACE~\cite{lace} | 생성된 접근 제어 정책 | 사용자 요청과 정책 충돌 정의 | 의미 판단에 NLI, 충돌 검사에 SMT |
| **VETS** | **반응형·시간 기반 JOI 코드** | **Timeline IR로 명시된 사용자의 의도한 동작** | **Timed action trace 동등성 검사** |
