# 코드 생성과 행동 검증

그림 3처럼 LLM은 확정된 Timeline IR에 명시된 실행 순서와 시간 조건을 지침으로 삼고, 기기 바인딩을 적용해 JOI 코드를 생성한다. Behavioral Explorer는 정해진 입력값 범위와 실행 규칙 아래에서, 허용된 모든 초기 상태와 입력 시퀀스에 대해 IR과 생성 코드가 같은 timed action trace를 만드는지 검사한다. **생성된 결과물마다 기준과의 행동 보존을 확인하는 이 구조는 translation validation 접근을 따른다~\cite{translationvalidation}.**

## 같은 입력에서 행동 비교하기

**검사는 같은 입력에 대한 두 프로그램의 행동을 비교하고, 그때 남겨진 값이 이후 행동에 미치는 영향까지 확인하는 과정이다. Explorer는 각 프로그램의 의미를 실행하는 인터프리터로 다음 행동과 상태를 계산한다. 여기서 상태는 현재 실행 위치, 저장값과 타이머 등 이후 행동을 결정하는 정보를 뜻한다. 두 인터프리터는 같은 외부 입력값과 논리 시각을 제공받되, 각자의 실행 규칙에 따라 상태를 별도로 유지한다.**

각 인터프리터는 실행 중 발생한 기기 명령과 그 시각을 기록하여 timed action trace를 만든다. Explorer는 각 시각의 명령 대상, 메서드, 인자, 횟수와 순서를 비교한다. 내부 변수 대입이나 제어 단계가 서로 같을 필요는 없다. 1절의 온도 예시에서, 온도가 높은 동안 코드가 On() 명령을 추가로 내보내면 두 실행 모두 에어컨이 켜진 상태를 유지하더라도 불일치다. 명령이 누락되거나 늦게 발생하는 경우도 불일치로 판단한다.

이 비교를 위해 Explorer는 검사 전에 기기 바인딩, 시작 시각, 허용되는 초기 상태와 입력값 범위를 설정한다. 센서값과 기기 상태 등의 입력은 일정한 갱신 시점마다 바뀔 수 있으며, 다음 갱신까지 유지된다. **입력 갱신, 대기 만료, 코드의 주기적인 재실행처럼 어느 한쪽 프로그램의 실행에라도 영향을 줄 수 있는 시점을 고려한다. 그 사이에 행동이나 이후 실행에 영향을 주는 변화가 없음을 확인할 수 있으면 중간 시점을 생략하고 다음 관련 시점으로 이동한다. 이는 실제 시간을 기다리지 않고 논리 시각을 이동하는 것으로, 경과 시간과 명령 발생 시각은 보존한다.**

## 가능한 실행 탐색하기

입력 시퀀스 하나에서 timed action trace가 일치한다고 해서 동등성이 성립하는 것은 아니다. **지속 조건을 확인하는 간단한 예로 “문이 30초 연속 열리면 알림을 보낸다”는 자동화를 생각해 보자. 문 닫힘이 대기 만료보다 먼저, 동시에, 또는 나중에 발생하는 경우에 따라 행동이 달라진다. 만료 전에 닫혔다가 다시 열리면 30초를 새로 기다려야 한다. IR은 대기를 초기화하더라도 생성 코드가 이전에 기다린 시간을 남겨 두면 알림이 너무 일찍 발생할 수 있다. 따라서 이벤트의 순서와 함께, 각 이벤트를 처리한 뒤 남는 상태까지 확인해야 한다.**

**Explorer는 허용된 초기 상태에서 시작하여 가능한 다음 입력마다 두 실행을 진행하고 명령을 비교한다. 그 결과로 도달한 상태가 이미 검사한 상태와 같으면 이후 검사를 재사용하고, 아직 검사하지 않은 상태이면 검사 대상에 추가한다~\cite{modelchecking}. 문이 닫힌 뒤 두 프로그램 모두 이전과 같은 대기 상태로 돌아오는 경우가 재사용의 예다. 이 과정을 반복하여 문 닫힘과 재열림이 여러 번 이어지는 경우까지 검사한다.**

모든 입력값과 반복 회차를 하나씩 펼치면 검사 비용이 커질 수 있다. Explorer는 비교하는 행동을 보존할 수 있는 경우에 탐색량을 줄인다. 입력값이 조건 판단에만 사용되는 경우, 양쪽 프로그램의 모든 조건에서 판단 결과가 같은 값끼리 묶는다. 예를 들어 IR은 온도가 22도를 넘는지 검사하고 코드는 25도를 넘는지 검사한다면, 22도 이하, 22도 초과 25도 이하, 25도 초과를 구분해야 한다. 가운데 구간에서 두 조건의 차이가 드러난다. 입력값이 기기 명령의 인자나 다른 계산에도 사용된다면, 값에 따라 명령의 내용이나 이후 동작이 달라질 수 있으므로 실제 값의 차이까지 검사한다.

**시간에 대해서도, 경과 시간만 다른 많은 상태를 하나씩 검사하는 비용을 줄일 수 있다. Explorer는 지원되는 경우 여러 시간 값을 관계식으로 함께 표현하고, 그 범위 전체의 후속 행동을 검사한다. 이 표현은 시간 검증에서 사용되어 온 변수 간 차이 제약을 활용한다~\cite{bengtsson2004timed}. 앞의 예시에서는 아직 30초가 지나지 않은 여러 대기 상태를 함께 다루면서도, 문 닫힘에 따른 초기화와 정확한 만료 시점을 보존해야 한다.**

**이때 두 프로그램의 서로 다른 시간 표현을 연결해야 한다.** IR 실행기는 타이머로 대기 시간을 관리한다. JOI 코드는 같은 대기를 주기적인 실행 횟수를 세거나, 시작 시각을 저장한 뒤 현재 시각과의 차이를 계산하는 방식으로 구현할 수 있다. **예를 들어 카운터를 사용하는 코드에서는 시작값과 증가·초기화 시점을 확인하여 IR의 경과 시간과 카운터 사이의 관계를 유지한다. 이러한 관계로 묶인 상태에서 가능한 입력별 명령과 후속 상태를 검사한다. 새로 도달한 상태를 포함하도록 표현 범위를 넓힌 경우에는 넓어진 범위의 후속 행동을 다시 검사한다~\cite{cousot1977}.**

## 판정과 피드백

Explorer는 초기화부터 입력 시퀀스를 재생하여 timed action trace의 차이를 확인한 경우에만 불일치를 보고한다. 이때 초기 환경, 해당 입력 시퀀스, 기대 액션과 실제 액션을 반환한다. LLM은 이 근거로 코드를 수정할 수 있으며, Explorer는 같은 IR과 바인딩을 기준으로 수정본을 검사한다.

동등 판정에는 완료된 검사가 필요하다. 종료하는 모든 가능한 경로에서는 timed action trace가 일치해야 한다. 종료 없이 반복되는 자동화에서는 가능한 모든 다음 실행이 이미 검사한 범위의 상태로 이어지고, 액션과 발생 시각이 일치해야 한다. 여러 상태를 묶어 검사할 때도 표현된 상태 전체에서 이 조건들이 성립해야 한다. 지원하지 않는 연산, 실행 오류, 검사 예산 소진은 미인증으로 남으며 배포를 승인하지 않는다.

VETS는 Explorer를 Python으로 구현하고, 산술식 비교에는 수식과 조건을 분석하는 도구인 Z3~\cite{z3}를 사용한다. 검사는 LLM 호출 없이 의미 인터프리터로 수행한다. 동등성 보장은 파싱, 의미 해석과 Z3의 분석 결과가 올바르다는 가정 아래, 정해진 입력값 범위와 실행 규칙 안에서 적용된다. 확정된 IR이 사용자의 의도를 담는지까지 입증하는 것은 아니다.
