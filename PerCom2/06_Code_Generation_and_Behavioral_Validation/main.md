# Code Generation and Behavioral Validation

As shown in Figure 3, the LLM generates JOI code using the execution order and timing conditions specified in the confirmed Timeline IR as guidance and applying the device binding. Behavioral Explorer checks whether the IR and generated code produce the same timed action trace for every allowed initial state and timed input sequence within the specified input ranges and execution rules.

## Comparing Behavior under Shared Inputs

Checking compares the two programs' behavior under the same inputs and tracks how values retained from one reaction affect later behavior. Explorer uses a semantic interpreter for each program to compute its next actions and state. A state comprises the execution position, stored values, timers, and other information that determines subsequent behavior. Both interpreters receive the same external input values and logical time, while maintaining separate states according to their own execution rules.

Each interpreter records the device commands it issues, together with their times, to form a timed action trace. Explorer compares the target, method, arguments, number, and order of commands at each time. Internal assignments and control steps need not match. In the temperature example from Section 1, an extra On() command while the temperature remains high exposes a mismatch even though the air conditioner stays on in both executions. A missing or delayed command also produces a mismatch.

To make this comparison meaningful, Explorer sets the device binding, start time, allowed initial states, and input ranges before checking. Inputs such as sensor values and device states may change at regular update times and remain constant between updates. Explorer considers input updates, timer deadlines, and periodic code executions that can affect either program. When it can establish that no intervening change affects actions or subsequent execution, it skips intermediate time points and advances to the next relevant event. This advances logical time without waiting in real time, while preserving elapsed time and action timestamps.

## Exploring Possible Executions

Matching timed action traces for one timed input sequence does not establish equivalence. Consider a simple sustained-condition automation: send a notification if a door remains open for 30 seconds. Behavior depends on whether the door closes before, at, or after the deadline. If it closes before the deadline and then reopens, the wait must restart. Even if the IR resets its wait, generated code that retains the previous elapsed time may notify too early. Checking must therefore account for both event order and the state retained after each event.

Starting from the allowed initial states, Explorer considers each possible next input, advances both executions, and compares their commands. If the resulting state matches one already checked, Explorer reuses the subsequent checks; otherwise, it adds the new state to the remaining work. Returning both programs to a previously checked waiting state after the door closes is one example of reuse. Repeating this process covers sequences in which the door closes and reopens multiple times.

Enumerating every input value and every repetition can be expensive. Explorer reduces this work where it can preserve the behavior being compared. When input values are used only to evaluate conditions, Explorer groups values that produce the same result for every condition in both programs. For example, if the IR tests whether temperature exceeds 22 degrees and the code tests whether it exceeds 25, exploration must distinguish values at or below 22, above 22 through 25, and above 25. The middle group exposes the difference. If an input value is also used as an action argument or in another computation, Explorer checks differences in the actual values because they can change the action arguments or subsequent behavior.

For time, Explorer can also reduce the cost of checking many states that differ only in elapsed time. Where supported, it represents multiple time values together through relations and checks successor behavior over the entire represented range. In the example above, it can jointly represent waiting states before the 30-second deadline while preserving resets on door closure and the exact deadline.

This requires relating the two programs' different representations of time. The IR interpreter uses timers to manage waits. JOI code can implement the same wait by counting periodic executions or by saving a start time and computing the difference from the current time. For code using a counter, Explorer checks its initialization, increments, and resets to maintain the relation between the counter and elapsed time in the IR. It checks commands and successor states for each possible input over the states represented by these relations. If the represented range is enlarged to include a newly reached state, Explorer rechecks successor behavior over that enlarged range.

## Verdicts and Feedback

Explorer reports a divergence only after replaying a timed input sequence from initialization and confirming a difference in the timed action traces. It returns the initial environment, that input sequence, and expected and actual actions. The LLM can use this evidence to revise the code; Explorer checks the revision against the same IR and binding.

Equivalence requires a completed check. All possible terminating paths must have matching timed action traces. For automations that repeat without terminating, every possible continuation must lead to states already covered by the check, with matching actions and timing. When states are grouped, these conditions must hold for all represented states. Unsupported operations, execution errors, or exhausted checking budgets leave the pair uncertified and do not authorize deployment.

VETS implements Explorer in Python and uses Z3, a tool for reasoning about expressions and constraints, to compare arithmetic expressions. Checking uses semantic interpreters without LLM calls. The equivalence guarantee applies within the specified input ranges and execution rules, assuming correct parsing, interpretation, and Z3 results. It does not establish that the confirmed IR captures the user's intent.
