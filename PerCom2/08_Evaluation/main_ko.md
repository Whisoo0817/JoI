# 평가 — PerCom 검토용 한글 초안

> 같은 폴더의 `PerCom_version.md`를 기준으로 2026-09-18에 E1 번역과 표를 갱신했다. 원문의 표·수치·실험 조건과 한계를 유지했다. 현재 논문에서는 7절이며, 자료 폴더명은 `08_Evaluation`을 유지한다.

상태: 2026-09-18 E1을 범위 내 92건 전체 평가로 갱신. 사용자 검토 전. E2는 구성 표와 판정 분포 그림으로 제시한다. 반례는 수정에 필요한 행동 차이 정보로만 사용하며, 대조군 비교나 인과적 개선 주장은 본문에 넣지 않는다. 근거와 검증 메모는 `DRAFT_NOTES.md`를 참조한다.

평가는 네 가지 질문을 다룬다. Timeline IR은 외부에서 수집한 자동화 요청을 표현할 수 있는가(E1)? Explorer의 판정은 별도로 구현한 기준 실행기를 통한 검사 결과와 일치하는가(E2)? 생성 코드에는 어떤 오류가 나타나는가(E3)? 자동화의 규모와 시간 설정에 따라 검증 비용은 어떻게 달라지는가(E4)?

**평가 설정.** 모든 코드 평가는 JOI와 5·6절의 실행 모델을 사용한다. E1은 표현 가능성과 기준 실행을, E2는 판정의 타당성을, E3는 생성된 후보 코드를, E4는 검사 완료 여부와 비용을 평가한다. 지원 범위 밖이라 검사가 거절된 경우, 탐색을 완료하지 못한 경우, 오류가 발생한 경우도 각 평가의 전체 건수에 포함한다. LLM을 이용한 생성과 행동 검증은 분리한다.

## Timeline IR의 표현 적합성

E1은 Timeline IR의 연산자들을 조합해 외부에서 수집한 자동화 요청을 표현할 수 있는지 평가한다. 네 종류의 출처에서 요청 100건을 수집했다(표 E1). 저자 한 명이 반응형·시간 기반 자동화라는 연구 범위에 해당하는지 검토한 결과, 92건은 범위 내, 여섯 건은 해석이 모호한 요청, 두 건은 범위 밖으로 분류했다. 범위 내 92건 모두를 IR로 표현하고 실행해 보았다.

평가 사례에는 지속 조건, 중첩 반복, 이전 상태 복원, 실행 이력에 따른 시간 제한을 조합해야 하는 경우가 포함된다. 예를 들어 차고 알림은 점멸과 대기를 반복하면서 문이 닫히면 중단하고 조명을 원래 상태로 복원해야 한다. 스프링클러 사례는 여러 급수 구간을 추적해 어느 시점에서든 직전 48시간의 총 급수 시간을 10분 이내로 제한한다.

각 요청은 IR로 표현하기 전에 구체적인 동작 해석과 예상 액션 및 발생 시각을 기록했다. 기준 IR 실행기에서 입력 이력을 재생한 뒤 액션과 발생 시각을 비교했으며, 같은 시각의 액션들은 순서를 구분하지 않고 비교했다. 결과는 최종 IR 기준으로 보고하고, 실패한 시도는 실험 기록에 보존했다.

**표 E1. 요청 출처별 Timeline IR 실행 결과.**

| 요청 출처               |     수집 건수 |    평가 건수 | 정확히 재현한 입력 이력 |
| ----------------------- | ------------: | -----------: | ----------------------: |
| 공식 플랫폼 예제        |            25 |           25 |                   97/97 |
| 연구 논문의 예제        |            26 |           24 |                   74/74 |
| 공개된 연구 참여자 응답 |            24 |           20 |                   58/58 |
| 커뮤니티 요청           |            25 |           23 |                   65/65 |
| **합계**          | **100** | **92** |       **294/294** |

최종 IR 92건은 입력 이력 294개 모두에서 예상 트레이스를 재현했다(표 E1). 별도로 수행한 추가 점검용 입력 이력 17개도 모두 일치했으며, 표의 이력 수에는 포함하지 않았다.

평가에서는 각 요청의 의미와 실행 조건을 구체화한 뒤 IR로 표현하고 실행했다. 결과는 이러한 조건 아래에서 Timeline IR이 평가 대상의 동작을 표현하고, 시험한 입력 이력에서 예상 트레이스를 재현했음을 보여준다. 모든 가능한 입력이나 요청에 대한 정확성을 입증하는 것은 아니며, Explorer의 검증 지원 여부는 별도로 평가한다.

## 검증 판정의 타당성

Explorer의 판정을 평가하기 위해 총 200개의 IR–JOI 코드 쌍을 구성했다(표 E2a). E1 요청 중 20건을 사용해 올바른 구현과 결함을 하나씩 넣은 변형으로 150쌍을 만들고, 요청 388건으로 구성된 개발용 데이터에서 표본으로 뽑은 유효한 LLM 생성 후보 50개를 추가했다. 결함은 액션 누락, 시점, 조건식, 저장값, 순서, 반복 등을 포함한 12개 유형에 걸쳐 있다.

**표 E2a. 평가 대상의 구성.**

| 구성 | IR–코드 쌍 수 |
| --- | ---: |
| E1 요청 20건에서 직접 만든 올바른 구현과 결함 변형 | 150 |
| 표본으로 뽑은 LLM 생성 후보 | 50 |
| 전체 | 200 |

Explorer의 동등·불일치 판정이 두 프로그램을 별도로 실행한 결과와 일치하는지 검사했다. 이를 위해 Explorer 코드를 참조하지 않고 언어 명세에 따라 Timeline IR 실행기와 JOI 인터프리터를 구현했다.

테스트 입력은 우리가 작성한 스크립트로 생성했다. 스크립트는 IR의 조건과 대기 시간, 기존 E1 테스트 상황을 바탕으로 센서 값과 그 값이 바뀌는 시각을 정했다. 조건의 경계값 주변과 대기 시간이 끝나기 직전·정확히 그 시점·직후의 변화를 포함했으며, 입력 생성에 Explorer의 판정은 사용하지 않았다. 이렇게 만든 동일한 입력을 두 기준 실행기에 넣고 출력 행동과 발생 시각을 비교했다. 또한 Explorer가 반례로 제시한 입력도 실행해 실제로 차이가 발생하는지 확인했다.

불일치 판정에서는 해당 기기 선택과 반례 입력에서 실제 차이가 나는지 확인했다. 동등 판정에서는 허용되는 기기 선택에 대해 준비한 입력 이력 모두에서 결과가 일치하는지 확인했다. 후자는 시험한 입력에 대한 근거이며, 모든 가능한 입력에서의 동등성을 증명하지는 않는다. Explorer 탐색에는 120초, 상태 400,000개, 전이 2,000,000개의 한도를 적용했다.

**그림 E2. IR–JOI 코드 200쌍에 대한 Explorer 판정 분포.**

![Explorer 판정 분포: 동등 64건(32.0%), 불일치 119건(59.5%), 시간 초과 8건(4.0%), 지원 범위 밖 9건(4.5%).](../../PerCom/08_Evaluation/figures/e2_verdicts.png)

시간 초과와 지원 범위 밖 사례는 미확정으로 남았다. 동등 또는 불일치 판정 183건 중 기준 검사와 모순되는 결과는 없었다.

판정 183건 중 기준 검사와 모순되는 결과는 없었다(그림 E2). Explorer가 불일치로 판정한 119쌍 모두에서 별도 실행기로 행동 또는 발생 시각의 차이를 확인했다. 행동 차이가 관찰된 결함 변형 중 11건은 미확정으로 남았고, 동등하다고 승인한 경우는 없었다. 미확정 17쌍 중 8쌍은 시간 한도를 넘었고, 9쌍은 지원 범위 밖의 산술식이나 입력값을 다뤄야 했다. 같은 요청에서 만든 결함 변형들은 서로 관련된 사례이므로 독립 표본으로 취급하지 않는다.

## 생성 코드 검증

E3에서는 LLM이 생성한 JOI 코드를 주어진 Timeline IR과 비교해 검사하고, 불일치 코드에 반례를 제공해 한 번 수정한 뒤 다시 검사했다. JOI 허브용으로 구성한 스마트홈 명령어 데이터셋에서 382건을 평가했다. 각 명령어의 확정된 IR과 기기 연결 정보를 Qwen3.5-9B에 제공해 JOI 코드를 생성했다. 기본 검사 시간 한도는 20초이며, 여러 기기 선택 조합을 검사하는 경우 조합 수에 비례해 한도를 늘렸다.

**표 E3. 생성된 JOI 후보의 검증 결과.**

| 결과                  | 후보 수 |    비율 |
| --------------------- | ------: | ------: |
| 동등                  |     309 |  80.89% |
| 불일치(재생으로 확인) |      68 |  17.80% |
| 지원 범위 밖          |       3 |   0.79% |
| 결론을 내리지 못함    |       2 |   0.52% |
| 전체                  |     382 | 100.00% |

Explorer는 후보 377개에 대해 동등 또는 불일치 판정을 내렸다(표 E3). 이 수치는 검사 완료율을 나타내며 정확도 추정치는 아니다. 불일치 68건은 모두 Explorer의 구체적인 입력 재생으로 확인했다. 예를 들어, “움직임이 없는 상태가 30초 동안 계속되면 멀티탭을 끈다”는 요청을 검사했다. 생성 코드는 움직임이 없음을 처음 확인한 순간부터 이미 1초가 지난 것으로 세고, 이후 매초 값을 1씩 늘렸다. 따라서 실제로는 29초만 지났는데 30초가 지났다고 판단해 멀티탭을 껐다. Explorer는 IR이 요구한 시점보다 1초 일찍 끄는 이 차이를 찾아냈다. 지원 범위 밖 사례는 이진 반환값 대입(binary return assignment), 범위가 제한되지 않은 온도 산술 연산, 큰 조도 입력 범위와 관련돼 있었다. 결론을 내리지 못한 두 사례는 내부 조건 검사 단계에서 시간 한도에 도달했다. 이 결과는 확정된 IR과 기기 연결 정보를 기준으로 한 탐색적 평가다. 자연어 의도 해석의 정확도나 실제 기기 동작을 측정한 결과는 아니다.

**코드 수정을 위한 반례.** 불일치 판정을 받은 코드 68개에 대해, 반례에 담긴 입력 상황과 IR이 요구한 행동, 코드가 출력한 행동을 같은 모델에 제공하고 한 번씩 수정을 요청했다. IR과 기기 연결 정보는 고정했다. 수정된 코드를 다시 검사한 결과, 36개(52.9%)가 동등 판정을 받았고 26개는 불일치로 남았다. 나머지는 검사 시간 초과 5개와 모델 컨텍스트 오류로 인한 수정 생성 실패 1개였다.

## 검증 비용과 규모

E4는 자동화의 규모와 시간 설정이 달라질 때 행동 검사를 완료하는 데 얼마나 걸리는지 평가한다. 하나의 프로그램 틀에서 불리언 센서 수(1–7개), 순차적인 대기–호출 단계 수(1–6개), 대기 시간(100밀리초–4시간), 반복 횟수(1–200회)를 각각 바꾸거나 조합해 동등한 IR–JOI 코드 쌍 30개를 생성했다.

비교 방법으로 **명시적 상태 탐색(explicit-state exploration)**을 사용했다. 이 방법은 구체적인 타이머 값을 포함한 실행 상태를 개별적으로 추적한다. Explorer는 가능한 타이머 값들을 제약식으로 묶어서 다룰 수 있다. 두 방법은 같은 인터프리터를 사용하며, 다음 관련 이벤트 시점으로 이동하고 이미 방문한 동일 상태를 재사용한다. 동등 판정을 내리려면 두 방법 모두 탐색을 완료해야 한다. 각 프로그램은 방법별로 세 번씩 실행했고, 회당 시간 한도는 120초였다. Explorer는 한 번에 하나씩 실행했고, 비교 방법은 8코어 호스트에서 작업 네 개를 동시에 실행했다. 따라서 측정값은 각 실행 설정에서의 결과이며, 동일한 부하에서의 속도 향상 비율을 나타내지는 않는다.

**그림 E4. 검사 시간에 따른 누적 판정 완료 프로그램 수.**

![전체 30개 중 Explorer는 28개, 명시적 상태 탐색은 12개를 완료했다. Explorer는 24개를 5초 이내에 완료했다.](../../PerCom/08_Evaluation/E4_cost/figs/e4_cumulative.png)

시간 축은 로그 눈금이다. 세 번 모두 검사를 완료한 프로그램만 완료 건수에 포함하며, 시간은 세 번 중 가장 오래 걸린 값이다. 미완료 프로그램도 전체 30개에 포함한다.

Explorer는 전체 30개 중 28개의 검사를 완료했고, 명시적 상태 탐색은 12개를 완료했다(그림 E4). Explorer는 24개를 5초 이내에, 완료한 28개 모두를 21초 이내에 처리했다. 대기 시간을 100밀리초에서 4시간까지 바꾼 실험에서 Explorer의 검사 시간은 0.05–0.35초였다. 완료하지 못한 두 프로그램의 설정은 각각 센서 6개·6단계·50회 반복과 센서 7개·6단계·100회 반복이었으며, 둘 다 시간 한도에 도달했다. 이 결과는 시험한 프로그램 유형에서의 검사 완료 범위와 비용을 보여주며, 다른 구조의 프로그램에서는 비용이 달라질 수 있다.
