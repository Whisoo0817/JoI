# Timeline IR

Timeline IR makes an automation's temporal control flow explicit along a time axis. Schedules, waits, and delays determine when execution proceeds; sequences, branches, and cycles determine how it proceeds. Once confirmed by the user, the IR guides code generation and provides an executable behavioral reference for checking the generated JOI code.

**Operators and structure.** Structurally, an IR is a tree of JSON steps, each identified by an `op` field. A `timeline` begins with `start_at`, which sets the start time, and executes its steps in order. The `if` branches and `cycle` bodies contain further sequences. The primitive operators also include `wait` for a condition, an observed edge, or a sustained condition; `delay` for a duration; `read` for saving a value; and `call` for invoking a device service. A sustained wait resets its timer if the condition becomes false. A cycle waits for its `period` after each completed iteration and can use a count or an `until` condition to stop; `break` exits the enclosing cycle. One timeline has no parallel branches. The confirmed binding identifies the concrete devices referenced by the IR.

The example in Figure 4 starts with the door closed; `Contact` is true when closed, and `Switch` is bound to the entrance light. The IR in Figure 4(a) waits for the door-opening event, turns on the light, and enters a cycle. The body issues the reminder “Please close the door” and waits until the door closes or 30 seconds elapse. If the door remains open when the wait times out, the next iteration issues another reminder. When the door closes, the wait ends and the `until` condition terminates the cycle. The `call` following the `cycle` (line 15) then turns off the light. The cycle is thus an intermediate part of the control flow, with execution continuing to the subsequent step after it ends. Figure 4(b) expresses this control flow in plain language.

Figure 4(c) shows how this control flow progresses along the time axis as the door state changes. When the door opens at second 10, the IR turns on the light and issues the first reminder. The door remains open, so reminders follow at seconds 40 and 70. When the door closes at second 85, execution exits the cycle and turns off the light without waiting for the timeout at second 100. Elapsed time advances execution to the next iteration, whereas door closure advances it to the step after the cycle.

**Executable reference.** The IR interpreter retains the execution position, stored values, and timers. At each relevant time, it executes steps until waiting or termination, recording issued commands and their times as a timed action trace. When an input update coincides with a timer deadline, it applies the new input first. With the IR, binding, and execution rules fixed, the same initial state and timed input sequence determine the same commands, in the same order and at the same times. This input-determinism assumes error-free execution with finitely many steps in each finite time interval. Section 6 uses this expected trace to check the generated code across allowed inputs.

**Presenting the IR.** Users can inspect the JSON directly or review a plain-language rendering such as Figure 4(b). A time-axis view such as Figure 4(c) illustrates behavior under selected inputs. This structure could be extended to let users change input values or their timing and inspect the resulting behavior, or to generate explanations with an LLM. These extensions and their effects on user understanding are not evaluated here. Across presentation methods, the confirmed IR remains the specification, and we assume that it captures the user's intended behavior.
