# Introduction — 한글 검토본

> 같은 폴더의 [main.md](main.md)와 `overleaf-paper/main.tex`의 Introduction을 번역했다. SenSys의 Why this is hard 문단을 복원하고, 예제와 기존 검사 설명을 축약했으며, LLM judge 설명을 기존 검사 문단에 통합했다. 2페이지 첫 번째 column이라는 분량 목표보다 논리 흐름을 우선해 연결 설명을 보완했다. 추가 피드백을 반영하고 영문과 LaTeX에 동기화했다.

사물인터넷(Internet of Things, IoT) 자동화는 대규모 언어 모델(large language model, LLM) 기반 코드 생성으로 나아가고 있다~\cite{gpiot,awareauto}. 사용자가 원하는 동작을 자연어로 설명하면, LLM은 이를 플랫폼이 실행할 수 있는 반응형 규칙으로 변환한다. 그러나 이 과정의 마지막 단계인 *생성된 코드가 배포해도 올바른지를 판단하는 일*에는 결정적 검증 관문이 없다. 빠져 있는 것은 코드를 대조할 기준이다. 자연어 요청에는 의도가 담겨 있지만, 자동화된 검사를 위한 엄밀한 기준으로 사용할 수 있는 형태는 아니다.

**왜 어려운가:** 핵심 어려움은 검증 가능한 기준 명세가 없다는 데서 비롯된다. 대상 자동화는 본질적으로 *반응형·시간 기반(reactive-temporal)*이다. 비동기 이벤트와 조건부 트리거에 의해 실행되므로 *반응형*이며, 스케줄, 주기적 실행, 상태의 지속 시간(예: “N분 이상 지속되면”)을 통해 동작이 시간에 걸쳐 전개되므로 *시간 기반*이다. 타이머, 카운터, 여러 단계에 걸친 상태에 의해 동작하므로, 자동화의 올바른 동작은 단일 시점이 아니라 전체 시간 흐름에 걸쳐 평가해야 한다. 또한 우리가 다루는 환경에서는 이러한 시간적 동작을 변수 갱신과 조건문으로 구현한 명령형(imperative) 코드가 배포된다. 그 정확성을 검증하는 데에는 두 가지 핵심 어려움이 있다. 첫째, 요청별 테스트 오라클이 미리 주어지지 않는다. 정답 실행 결과나 입출력 테스트 집합을 제공하는 text-to-SQL(Structured Query Language) 또는 일반적인 프로그래밍 벤치마크와 달리~\cite{spider,humaneval}, 반응형 자동화의 출력은 앞으로 발생할 환경과의 상호작용 시퀀스다. 따라서 검증에 사용할 행동 기준을 요청으로부터 구성해야 한다. 둘째, 구문적 차이가 평가를 어렵게 한다. 동일한 사용자 의도는 구문이 서로 다르면서도 행동은 동등한 여러 구현으로 표현될 수 있다. 따라서 생성된 프로그램을 하나의 기준 텍스트와 일치하는지 검사하는 방식은 건전하지도 완전하지도 않다. 정확성을 판단하려면 정적인 구문이나 출력의 단일 순간을 분석하는 대신, 시간에 따른 프로그램의 의미적 동작을 추론해야 한다.

**예제:** 사용자가 “온도가 25°C를 넘어설 때마다 에어컨을 켜라”라고 요청한다고 하자. 우리는 “넘어설 때”를 상승 에지에 반응하는 의도로 해석한다. 즉, 온도가 높은 동안 계속 켜는 것이 아니라, 임계값을 위로 통과할 때마다 한 번씩 에어컨을 켜야 한다. Figure~\ref{fig:idiom}은 대상 플랫폼의 자동화 도메인 특화 언어(domain-specific language, DSL)인 JOI로 작성한 세 가지 코드 변환 결과를 보여준다. 세 구현은 모두 1초의 tick 주기로 실행된다. 구현 (a)는 이전 측정값과 현재 측정값을 비교하여 임계값 통과를 감지하고, (b)는 동작이 발생하면 설정되고 온도가 임계값 아래로 내려가면 초기화되는 플래그를 사용한다. 두 구현은 구문상 거의 공통점이 없지만 동일하게 동작한다. 구현 (c)는 자연어 요청과 문면상 유사하지만, 주기적으로 실행하면 온도가 임계값을 초과하는 동안 매 tick마다 잘못 재실행된다. On() 명령이 반복되어도 에어컨의 눈에 보이는 상태는 같으므로, 사용자는 문제를 알아차리지 못할 수 있다. 이것이 우리 시스템이 다루는 중요한 실패 유형이다. **배포된 코드가 사용자가 의도한 행동 명세(user's intended behavioral specification)에서 드러나지 않게 벗어나는 것이다.**

**기존 검사의 한계.** 기존 IoT 자동화 검증은 안전 속성, 규칙 간 충돌, 보안 정책과 같이 미리 정의된 기준을 검사한다~\cite{autotap,iotsan,iotguard}. 이러한 검사는 자동화가 선택된 속성을 만족하는지를 판단하지만, 그 자체로 사용자가 요청한 구체적인 동작을 구현했는지까지 판단하지는 않는다. 별도의 LLM에게 요청과 코드의 일치 여부를 판단하게 할 수도 있지만, 우리의 실험에서는 행동을 보존하는 시간적 재작성에도 판정이 달라졌다(§3). 따라서 요청한 행동을 명시하는 검증 기준과, 코드가 그 기준에 부합하는지 일관되게 검사하는 방법이 필요하다.

**VETS.** 이러한 문제를 다루기 위해 VETS를 제안한다. 핵심 아이디어는 authoring 단계에서 *부재한 기준 명세를 도출*하고, 이후 이를 결정적 검증의 기준으로 사용하는 것이다. VETS는 요청된 자동화를 Timeline IR이라는 중간 표현(intermediate representation, IR)으로 나타낸다. 이 표현은 LLM이 코드로 구현할 행동 구조를 명시하고, 생성된 JOI 코드를 검사하는 실행 가능한 기준이 된다.

Timeline IR은 실행 순서와 시간 조건을 명시하여 자동화의 시간적 제어 흐름(temporal control flow)을 드러낸다(§5). 따라서 이벤트를 기다린 뒤 동작을 수행하고, 일정한 지연을 두고 종료 조건이 충족될 때까지 반복하는 자동화를 명확하게 표현할 수 있다. 초기 상태와 입력값 및 그 변화 시각을 나타내는 입력 시퀀스(timed input sequence)가 주어지면, IR의 실행 의미론은 기기 명령과 발생 시각으로 이루어진 기대 timed action trace를 결정한다.

Behavioral Explorer는 허용된 모든 초기 상태와 입력 시퀀스에 대해 IR과 생성된 JOI 코드의 timed action trace가 같은지 검사한다(§6). 정해진 입력값 범위와 실행 규칙 안에서 검사가 완료된 경우에만 동등성을 인증하고, 확인된 불일치에는 실행 가능한 반례를 제공한다. 지원하지 않거나 완료하지 못한 검사는 미확정으로 남는다.

**범위와 가정.** 사용자는 authoring 단계에서 IR을 명세로 확정하며, 우리는 이 IR이 의도한 자동화를 담는다고 가정한다. 사용자의 IR 오류 식별 능력은 평가하지 않는다. VETS는 이후 코드 생성 과정에서 발생하는 상태·타이머·경계 오류를 검사하며, 그 보장은 확정된 IR에 대한 생성 코드의 부합성에 한정된다.

**로컬 생성과 검증.** 본 연구는 자동화 요청과 기기 정보가 생성과 검증 과정에서 외부 서비스에 노출되지 않는 환경을 전제로 한다. VETS는 이 전제에 맞춰 로컬 언어 모델로 Timeline IR과 JOI 코드를 생성하고, 행동 검증도 로컬에서 별도의 LLM 호출 없이 수행한다.

**기여.** 본 연구의 기여는 다음과 같다.

- **C1. Timeline IR:** 자동화의 실행 순서와 시간 조건을 명시하는 실행 가능한 중간 표현을 제안한다. 실행 의미론은 주어진 초기 상태와 입력 시퀀스에 대한 기대 동작을 정의하여, 생성된 JOI 코드의 행동 검증 기준을 제공한다.
- **C2. Behavioral Explorer:** 같은 입력 시퀀스 아래에서 Timeline IR과 생성된 JOI 코드를 함께 탐색하고 timed action trace를 비교하는 결정적 검사기를 제안한다. 확인된 불일치에는 실행 가능한 반례를 제공하며, 정해진 입력값 범위와 실행 규칙 안에서 탐색이 완료된 경우에만 동등성을 인증한다.
- **C3. 로컬 구현:** 로컬 LLM 기반 authoring과 LLM 호출 없는 결정적 행동 검증을 결합한 파이프라인을 구현한다. 생성 코드 평가에서 시도한 검사 379건의 검증 프로세스 시간은 중앙값 62ms, 95번째 백분위수 158ms였으며, 프로세스 시작과 준비 시간을 포함한다.
