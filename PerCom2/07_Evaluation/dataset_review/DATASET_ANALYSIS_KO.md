# PerCom 데이터셋 설명과 평가 근거 개선안

작성일: 2026-09-19. 대상: E1 외부 요구 100건과 E3 JOI 과제 382건. 본문 수정안이 아니라, 저장소 근거와 관련 논문을 대조한 분석이다. 현재 원고·실험 결과는 변경하지 않았다.

> **저자 확인에 따른 정정(2026-09-19):** 382건은 저자가 JOI 플랫폼에서 사용하기 위해 직접 작성했다. E1 후속 72건도 저자가 직접 검토했다. 이전 분석의 “제작 경위 불명확”과 “72건 사람 검토 미수행” 판단은 잘못된 문서 기록에 기초한 것으로 철회한다.

**권고: Evaluation 앞부분에 두 데이터셋의 출처·구축·역할을 설명하는 공통 절을 두고, 본문에는 출처/선별 표와 행동/복잡도 표를, 부록에는 유형 정의·해석 사례를, 공개 artifact에는 항목별 원문부터 평가 입력까지의 연결을 제공한다.** SenSys의 24개 유형표는 유용하지만 이것만으로 출처, 선택 편향, 정답의 신뢰성을 설명할 수 없다. 저자 작성 382건과 저자 검토를 거친 외부 요구 corpus의 서로 다른 구축 과정을 논문에 명확히 기술하는 것이 우선이다.

## 1. 교수님 지적을 어떻게 해석해야 하는가

독자가 확인해야 하는 것은 다음 여섯 가지다.

| 질문 | 필요한 근거 |
|---|---|
| 어디서 가져왔는가? | 논문/플랫폼/공개 연구자료/게시물 이름, 원문 위치, 항목별 연결 |
| 왜 이것들을 골랐는가? | 평가 목적, 후보 범위, 선정·제외·중복 기준, 수집 종료 기준 |
| 어떤 데이터인가? | 실제 사용자 작성, 연구자가 준 과제, 공식 예제, 연구자 정규화, 자체 제작을 구분 |
| 무엇이 어렵고 얼마나 다양한가? | 행동 유형, 시간 의미, 상태 기억, 제어 구조, 연산자 조합 및 구조 크기 |
| 정답은 누가 어떻게 정했는가? | 원문→해석/가정→IR/binding→기대 행동 이력의 연결과 검토자 |
| 무엇을 결론낼 수 있는가? | 모집단 대표성, 개발 중 사용 여부, 도구 의존, 결과 적용 범위 |

데이터 개수와 성공률만 있으면 이 질문들에 답할 수 없다. 출처를 추가하는 것과 좋은 평가 데이터셋으로 정당화하는 것은 별도의 작업이다.

## 2. 저장소에서 확인한 사실

### 2.1 E1의 100건: 출처 없는 데이터는 아니지만 설명과 추적 경로가 원고에서 빠져 있다

근거: [corpus_100.csv](../../../PerCom/08_Evaluation/E1_adequacy/breadth/corpus_100.csv), [수집 프로토콜](../../../PerCom/08_Evaluation/E1_adequacy/breadth/E1_CORPUS_PROTOCOL.md), [기존 출처 감사](../../../PerCom/08_Evaluation/E1_adequacy/breadth/audit/PROVENANCE_AUDIT.md).

현재 데이터의 실체는 **여러 출처에서 목적에 맞게 선정한 외부 자동화 요구 corpus**이다. 외부의 단일 표준 benchmark에서 무작위로 뽑은 100개가 아니다. 프로토콜은 실제 스마트홈 요청 빈도를 추정하지 않는다고 명시한다.

| 출처 유형 | 수집 | 범위 내 | 실제 구성 |
|---|---:|---:|---|
| 공식 플랫폼 예제 | 25 | 25 | Google Home scripted automation 예제 22, Home Assistant blueprint/문서 3 |
| 연구 논문 자료 | 26 | 24 | Ur et al. CHI 2014 12, Huang & Cakmak UbiComp 2015 10, TAPInspector 2, AutoTap 과제 1, Brackenbury et al. CHI 2019 1 |
| 공개 연구의 참가자 작성 응답 | 24 | 20 | AutoTap User Study 1에 연결되는 24개 응답 문장. 한 seed는 논문 URL을 쓰지만 공개 Excel의 행·열도 locator에 기록 |
| 커뮤니티 자료 | 25 | 23 | Home Assistant Community 게시물 25. 사용자 요청과 커뮤니티 예제가 혼합됨 |
| 합계 | **100** | **92** | 모호함 6, 범위 밖 2도 corpus에 보존 |

여기서 **24개 응답은 24명의 참가자를 뜻하지 않는다.** 연구 출처 26건 역시 26편의 논문이 아니다. 네 출처 유형이 비슷한 크기여도 각 유형 내부의 독립된 출처 수는 작다. 특히 공식 예제는 Google Home, 참가자 응답은 AutoTap, 커뮤니티는 Home Assistant에 집중된다. 이 구성을 숨기지 않고 명시하는 것이 좋다.

수집 기록상 처음에는 출처 유형별 25건을 목표로 했고, 출처 감사에서 한 사례를 재분류하여 25/26/24/25가 됐다. 균형을 맞추기 위해 사례를 추가하거나 빼지는 않았다. 12건은 기존 사례이고 88건은 추가 수집이다. 후보 로그 150건은 최종 100건과 출처별 수집 상한을 넘은 AutoTap 응답 50건으로 구성된다. 따라서 “150개를 무작위 수집하고 품질이 나쁜 50개를 제외했다”는 설명은 틀리다.

최종 `text_form`은 다음과 같다. 이들은 CSV의 텍스트 취급 태그이며, 모두 원문 직접 인용이라는 뜻이 아니다.

| 텍스트 취급 | n |
|---|---:|
| 공식 설명 또는 구조화된 예제에서 추출 | 24 |
| 공개 연구자료의 원문 | 23 |
| 연구자가 원래 동작을 정리한 문장 | 23 |
| 논문의 과제/예제 원문 | 18 |
| 저장소에서 출처를 대조한 seed 발췌 | 12 |

**여전히 필요한 것:** 어떤 검색어와 페이지 범위를 살폈는지, 각 출처 안에서 왜 해당 사례들을 우선 골랐는지, 수집 상한에 도달하기 전의 순서를 복원할 수 있는지. 현재 프로토콜은 목적 표집과 종료 규칙을 설명하지만 검색 전체를 재현할 수 있는 체계적 문헌 수집 로그는 아니다. 복원되지 않는 부분은 사후에 선정 기준을 만들지 말고 기록 한계로 남긴다.

### 2.2 382건: 저자가 JOI 플랫폼에서 사용하기 위해 직접 작성한 과제

현재 `dataset.csv`는 388행이고, E3는 IR 안에 `timeout`/`on_timeout`이 있는 C26의 6건을 제외한 382건이다. [E3_SCOPE.md](../../../PerCom/08_Evaluation/E3_application/E3_SCOPE.md)는 이 범위 결정을 2026-09-15 저자 결정으로 기록한다. 이것을 최초 데이터셋 구축 당시부터 정한 기준이라고 소급해서 설명하면 안 된다.

**저자가 2026-09-19 대화에서 382건을 JOI 플랫폼에서 사용하기 위해 직접 만들었다고 확인했다.** 따라서 출처는 저자 직접 작성이며, 논문에는 author-authored automation commands for use on the JOI platform으로 설명할 수 있다. CSV에 작성자 필드가 없다는 이유로 이 확인을 미확인 상태로 취급하지 않는다. 남은 설명 과제는 작성 사실을 복원하는 것이 아니라, 어떤 사용 상황과 행동 패턴을 담았는지, 24개 유형의 구성과 선정 이유를 독자에게 전달하는 것이다.

[최종 E3 기록](../../../PerCom/08_Evaluation/E3_application/E3_QWEN_382_FINAL_2026-09-15.md)과 실행 프로토콜은 개발 과정에서 결과를 이미 관찰한 사례이고 일부 후보를 재생성했음을 기록한다. 이 평가 사용 이력은 요청의 작성 출처와 별개다. 이전 기록의 mixed-provenance를 382개 요청의 작성자가 불명확하다는 의미로 사용하지 않는다. 저자 직접 작성 사실이 새 과제에 대한 held-out 평가를 뜻하는 것은 아니므로, familiar-task/exploratory라는 평가 범위는 유지한다.

또한 최종 기록은 다섯 사례에서 자연어의 “모든” 기기와 단일 기기로 확정된 binding 사이의 차이를 명시한다. E3의 실제 평가 단위는 **확정된 IR와 binding을 기준으로 하는 코드 생성·검사 과제**이다. NL에서 시작한 사용자 의도 보존 정확도까지 이 결과가 입증하는 것은 아니다.

### 2.3 E1 후속 72건도 저자가 직접 검토했다

[후속 72건 결과](../../../PerCom/08_Evaluation/E1_adequacy/breadth/extension72_plan/RESULT_KO.md)의 “저자 검토를 거치지 않았다”는 기록은 저자의 2026-09-19 확인으로 정정했다. 에이전트가 해석·기대 행동·IR의 초안을 작성한 이력과 저자가 72건을 직접 검토한 사실을 함께 기술한다.

현재 최종 집계는 92건·294/294 이력 일치이며 초기 실패와 후속 수정도 보존되어 있다. 기존 20건과 추가 72건 모두 저자 검토를 거친 것으로 설명한다. **72건에 대한 사람 검토를 미완료 과제로 다시 제안하지 않는다.** 검토 방식은 확인된 대로 저자 검토라고 쓰며, 별도의 제2검토자나 코더 간 일치도 같은 절차를 덧붙이지 않는다.

## 3. SenSys 설명에서 유지할 것과 보완할 것

[SenSys 원문](../../../docs/ovla0606.tex)의 Dataset 문단은 382개, reactive idiom, 참조 IR의 값 수준 검토, 부록 유형표를 연결한다. 부록의 C01–C25 중 C04를 제외한 24개 패턴별 수량은 현재 382건의 구성과 맞는다.

하지만 다음 이유로 그대로 복원하는 것만으로 충분하지 않다.

1. 본문의 “24 device/service categories”와 부록의 “structurally distinct reactive pattern”은 분류 축이 다르다. 실제 C01–C25 표는 기기 종류보다 **자동화 패턴**에 해당한다. 둘을 분리해야 한다.
2. “IR schema에 맞춰 구성하지 않았다”는 주장은 생성·수정 시점과 개발 사용 이력이 있어야 검증 가능하다. 문장만으로 독립성을 입증할 수 없다.
3. 유형별 n은 어떤 예제를 담았는지 보여주지만, 어디서 왔고 왜 그 n이 되었는지 설명하지 않는다.
4. 24개 범주는 trigger, 구조, 시간, selector를 서로 다른 층위에서 섞는다. C23처럼 여러 요소를 조합한 범주도 있어 단순한 난이도 순서가 아니다.
5. E1의 검토 절차는 SenSys 문장에서 가져오기보다, 기존 20건과 후속 72건 모두 저자가 검토했다는 실제 기록에 맞춰 설명한다.

기존 24개 패턴표는 부록의 legacy taxonomy로 유지하고, 본문에는 두 데이터셋을 비교할 수 있는 다중 레이블 행동 분류와 구조 통계를 추가하는 것이 적절하다.

## 4. 유사 논문에서 배울 방법

대상은 센서/IoT 시스템, 스마트홈 명령 benchmark, 요구 표현 체계 평가를 골라 비교했다. 여섯 논문의 원문에서 데이터 구성 관련 절을 확인한 목적 지향 검토이며, 모든 관련 논문을 포괄하는 systematic review는 아니다. 아래 마지막 열은 원문 사실에서 도출한 **우리 논문에 대한 제안**이다.

| 논문·확인 위치 | 원문에서 확인한 데이터 설명 방식 | 우리에게 유용한 점과 한계 |
|---|---|---|
| [AutoTap, ICSE 2019](https://homes.cs.washington.edu/~jessejm/data/ZhangICSE2019.pdf), §III | 모집·설문·제외 과정을 기술. 71명의 자유서술 응답을 7개 template로 코딩하며 모호함/범위 밖을 구분. 예제 노출 여부별 분포와 두 코더의 검토를 보고 | E1의 실제 요구·해석·선별을 설명하는 가장 가까운 선례. AutoTap 원자료 자체도 관찰된 배포 로그가 아니라 유도된 응답임을 밝혀야 함. 그들의 2인 검토를 우리 절차로 가져와 주장할 수 없음 |
| [Dwyer et al., ICSE 1999](https://www.cs.colostate.edu/~france/CS614/Readings/Readings2011/PropPatterns2p411-dwyer.pdf), §3, Tables/Figs. 1, 4–6 | 35개 이상 출처의 555개 명세에 source·requirement·pattern·scope를 기록. 미매칭 44개를 보존하고 저자 측 304개/외부 251개의 분포를 비교 | 출처와 패턴을 함께 공개하고 자체 자료와 외부 자료를 구분하는 좋은 선례. 패턴 체계도 수집 과정에서 보완되므로 이 논문을 held-out 증거로 쓰면 안 됨 |
| [TaskSense, SenSys 2025](https://yanzhenyu.com/assets/pdf/TaskSense-SenSys25.pdf), §6.2, Table 2 | 네 데이터셋의 센서 modality, 도구 수, seed example 수, query 수를 비교. 원래 센서 데이터와 별도 query 구성을 구분하며 설문/척도 기반 질의와 추가 작성 질의를 설명 | 서로 다른 데이터셋이 평가에서 맡는 역할을 표로 구분하는 본문 구성에 적합. 센서 자료가 공개됐다는 사실과 평가 query의 출처를 별도로 밝히는 점이 중요 |
| [GPIoT, SenSys 2025](https://arxiv.org/html/2503.00686v1#S4.SS1.SSS3), §4.1.1–4.1.3 | TDD/CGD 구축 경로를 설명하고 IoTBench 100개 표본, 수작업 검사 및 테스트케이스, tuning에서의 제외를 명시 | 100이라는 숫자보다 모체·선정·정답·학습 분리 설명이 중요하다는 선례. 우리 100건의 표본 수를 정당화해 주는 근거는 아니며, 익숙한 E3 과제에 같은 독립성 주장을 적용할 수 없음 |
| [HomeBench, ACL 2025](https://aclanthology.org/2025.acl-long.597.pdf), §3.2–3.4, Table 2 | 가상 기기/환경과 명령 생성 과정을 분리. 유효성×단일/다중 기기 유형, 유형별 명령 수·길이·조작 기기 수, 10% 검토 절차를 기술 | 유형·구조 통계·생성 방법을 한 묶음으로 제시하는 데 적합. 합성 분포를 실제 사용자 빈도로 해석하면 안 되고, 문장 길이나 기기 수만으로 우리의 시간 의미 복잡도를 설명할 수 없음 |
| [SimuHome, ICLR 2026 판본에 대응하는 arXiv v3](https://arxiv.org/html/2509.24282v3), §4.1–4.2 | 여섯 query type×가능/불가능의 12범주에 50개씩 600 episode. 초기 상태·구조화된 목표·필수 행동·질의를 구분. 목표에서 질의를 생성하고 두 검토자가 전체를 확인 | 평가 단위를 명확히 정의하고 목표/질의 정합성을 확인하는 방식이 유용. 우리 E1은 외부 요청에서 출발하므로 IR에서 역생성한 요청으로 대체하면 외부 적합성이라는 목적이 바뀜 |

우리에게 가장 적합한 조합은 **AutoTap/Dwyer의 출처와 의미 분류 + TaskSense의 데이터셋 역할 비교 + HomeBench/SimuHome의 구축·구조·검토 설명**이다. 특정 논문의 표본 개수나 taxonomy를 그대로 가져올 필요는 없다.

## 5. 지금 바로 제시할 수 있는 구성 통계

아래 수치는 [audit_dataset_structure.py](audit_dataset_structure.py)가 기존 데이터를 읽어 계산하며 [dataset_structure.json](dataset_structure.json)에 저장된다. E3의 `dataset.csv` SHA-256은 최종 실행 프로토콜의 입력 해시와 일치한다. IR 통계는 CSV를 추측해 연결하지 않고 최종 382건 manifest의 실제 payload에서 계산했다.

### 5.1 E1: 최종 저자 R/B 코딩, 분모 92

| 행동 요소 | 건수 |
|---|---:|
| R1 즉시 반응 | 65 |
| R2 지연 후 호출 | 14 |
| R3 지속 조건과 reset | 13 |
| R4 사건 한 번/재무장 | 3 |
| R5 저장값이 나중 호출에 사용 | 8 |
| R6 순차·분기 | 23 |
| R7 조건까지 주기적 반복 | 5 |
| R8 고정 횟수 반복 | 3 |
| R9 시계 앵커·시간대 조건 | 28 |
| R10 정해진 시각과 사건의 경쟁 | 2 |

경계 요소는 B1 취소/재시작 6, B2 독립 흐름/여러 인스턴스 5, B3 이벤트 기억/look-back 2, B4 가변 간격 0, B5 중첩 반복 1이다. 한 요청에 여러 태그를 부여하므로 합은 92가 아니다. 이는 **요구의 행동 태그**이며 IR 연산자 발생 횟수가 아니다. B4=0이므로 별도 boundary probe 결과를 이 corpus의 빈도로 합치면 안 된다.

CSV의 trigger/temporal/control/memory class 열은 별도로 존재하지만, 이번 분석에서는 최종 저자 코딩으로 명시된 `rb_adjudicated`만 사용했다. `depth_status`에는 이전 20건 단계의 표기도 남아 있으므로 현재 평가 완료 수를 그 열에서 산출하면 안 된다.

### 5.2 E3: 최종 확정 IR 382개에 연산자가 한 번 이상 나타나는 건수

| 연산자/구조 | 건수 |
|---|---:|
| `start_at`, `call` | 각각 382 |
| `if` | 150 |
| `wait` | 125 |
| `cycle` | 108 |
| `delay` | 52 |
| `read` | 34 |
| `break` | 1 |
| `wait`에 지속시간 `for`가 있음 | 27 |
| 명시적 rising-edge `wait` | 34 |
| cron 앵커 | 43 |
| `wait`와 `cycle`이 함께 있음 | 54 |
| `delay`와 `cycle`이 함께 있음 | 7 |

마지막 두 행은 같은 IR 내 공존이다. 반드시 직접 인접하거나 특정 중첩 관계라는 뜻은 아니다. `wait`와 `cycle`로 조합한 반복 반응을 명시적 rising-edge 수와 동일하게 취급하지 않는다.

| 구조량 | 실제 값 | 해석 주의 |
|---|---|---|
| IR 연산자 노드 수 | 최소 2, 중앙값 3, 최대 8 | 작은 문법 구조도 시간·반복 때문에 실행은 복잡할 수 있음 |
| `if`/`cycle` 중첩 깊이 | 깊이 0: 166, 1: 172, 2: 31, 3: 13 | root timeline을 세지 않은 정의. 확정된 구조적 깊이이지 경험적 난이도가 아님 |
| 정적 `call` 노드 수 | 1개: 265, 2개: 112, 3개: 5 | 실제 실행 호출 횟수와 다름. loop 또는 all-selector가 확장할 수 있음 |

**해석:** 24개 패턴을 담았다는 사실만으로 모든 새 연산자·복잡한 조합을 충분히 시험했다고 할 수 없다. 이 최종 E3 manifest에는 명시적 `timer`/`let` 연산자가 나타나지 않는다. 이들의 평가는 E1/E2의 실제 해당 사례로 연결해야 한다. 반대로 구문이 짧다는 이유로 시간 의미까지 쉽다고 단정하지 않는다.

## 6. 최선의 본문·부록·artifact 구성

### 6.1 본문: Dataset construction and characterization

Evaluation 시작 부분에 공통 절을 두고 다음 순서로 설명한다. 지면 계획으로는 2–4개 문단과 작은 표 2개, 대략 반 페이지에서 한 페이지를 우선 배정한다. 실제 분량은 템플릿에 맞춰 조정한다.

1. **역할과 단위.** E1은 외부의 한 자동화 요구가 평가 단위다. 하나의 요구가 여러 독립 Timeline으로 구현되어도 요구 수는 하나다. E3는 확정된 IR/binding에 대한 생성 코드 과제다. 100과 382를 합쳐 독립적인 사용자 요청 482개를 시험했다고 표현하지 않는다.
2. **출처와 선정.** 위 E1 출처 표, 목적 표집, 100 종료 기준, 92/6/2를 설명한다. E3는 제작 경위와 388→382 범위 제한, 개발 중 사용을 설명한다.
3. **구성과 구조.** 공통 행동 태그와 주요 조합/크기 분포를 비교한다. 정답 검토 절차를 함께 명시한다.
4. **평가 범위.** E1은 기록된 해석하의 외부 요구 적합성, E3는 고정된 입력 과제에서 코드 검사·수정 결과다. 모집단 대표성과 NL→IR 정확도는 여기서 추정하지 않는다.

**본문 표 A: Corpus provenance and role.** 행은 E1 네 출처 유형 + E3 자체 구성 과제, 열은 Source / Retained / Evaluated / Construction / Role 정도로 간결하게 둔다. E1의 다수 출처는 각주에 정확한 논문/공식 문서를 인용한다.

**본문 표 B: Behavioral and structural characteristics.** 두 데이터셋에 같은 정의로 코딩한 행동축의 빈도를 나란히 둔다. 현재 E1 R/B와 E3 연산자 통계는 단위가 다르므로 그대로 같은 행에서 비교하지 않는다. 검토를 거쳐 공통 행동축을 적용하기 전에는 두 panel로 분리하여 정의를 표시한다.

E2 200쌍과 E4 합성 30개 프로그램도 각각 정답 판정 시험과 규모/비용 시험이라는 역할을 한 문장으로 연결한다. 이들을 자연어 요청 corpus의 표본 수에 더하지 않는다.

### 6.2 공통 분류는 기기 종류보다 행동 의미를 중심에 둔다

| 분류 축 | 기록할 값의 예 | 필요한 이유 |
|---|---|---|
| 반응 의미 | 즉시 실행, 상태 만족 대기, 상승/하강 사건, 재무장 | 비슷한 문장도 실행 시점과 횟수가 다름 |
| 시간 조건 | 일정, 고정 지연, 지속 조건/reset, 주기, deadline/경쟁 | 논문의 explicit temporal control flow와 직접 연결 |
| 제어 조합 | 순차, 조건 분기, bounded/unbounded loop, 취소/재시작, 독립 흐름 | 단일 연산자 존재만으로 설명되지 않는 조합을 드러냄 |
| 기억/값 의존 | 없음, snapshot, counter, look-back, aggregate | 같은 시점의 값과 과거 값의 구분이 필요한지 설명 |
| 대상/행동 규모 | 참조 입력 수, 정적 행동 수, 서비스 수, 실제 binding 대상 수 | 기기 다양성과 구조 복잡도를 구분 |
| 구조 크기 | IR 노드 수, 분기/반복 중첩 깊이, 연산자 조합 | 재현 가능한 구조량 제공 |

각 축은 다중 레이블을 허용하고 분모와 정의를 공개한다. “쉬움/보통/어려움”이라는 임의 합산 점수는 우선 만들지 않는 것을 권한다. 복잡도는 구조량으로 보고하고, 어렵다는 주장은 이후 그룹별 검사 시간·미판정·불일치와 실제로 연결될 때 제한적으로 한다. 불일치율은 생성 모델의 취약성도 반영하므로 곧바로 과제 자체의 난이도로 보지 않는다.

주요 조합, 예를 들어 지속 조건→지연 시퀀스, trigger→주기 반복, snapshot→대기→비교를 별도로 집계한다. 희귀하거나 0건인 구조도 표에 남긴다. 사례나 패턴별 분포가 크게 다르면 전체 평균과 함께 그룹별 분모를 보여준다.

### 6.3 부록과 공개 artifact

**부록:** 24개 legacy 패턴표, 공통 태그 정의, 선정·제외 기준, 모호함 6건/범위 밖 2건의 이유, 3–4개 대표 사례의 원출처→연구자 해석→IR 조합을 제시한다. 단순 사례뿐 아니라 원문 보충 가정, 독립 흐름 분해, backend 위임 사례도 포함한다.

**항목별 artifact 필드:** `case_id`, 원출처 유형/제목/URL/locator/접근일/원본 버전, 원문, 정규화문, 변환 이유, 포함 여부와 이유, 의미상 중복/템플릿 family, 행동 태그, IR/binding, 기대 trace, 검토자 역할·시점, 개발 중 사용 이력, 평가 버전/hash.

외부 출처인 경우 원문 URL 하나로 끝내지 않고 논문의 표·행, 공개 Excel의 sheet·cell, 커뮤니티의 post ID/편집 시각을 남긴다. `dev`/`master` URL은 가능한 commit permalink로 고정한다. 자체 제작 사례에는 허구의 외부 출처를 붙이지 말고 생성/작성 과정과 최초 버전을 기록한다. 382건과 100건 사이의 의미상 중복도 확인해야 하며, 현재는 두 집합의 독립성을 확인한 상태가 아니다.

공개 raw trace와 script는 실행 재현성에, 원문·가정·사람 검토는 평가 기준의 타당성에 기여한다. 하나로 다른 하나를 대체할 수 없다.

## 7. 무엇부터 해야 하는가

| 우선순위 | 작업 | 완료 기준 |
|---|---|---|
| 1 | E1의 저장된 출처/선정 절차를 본문으로 옮기고 모집단 대표성 주장을 제한 | 독자가 논문만 보고 100개가 무엇이며 왜 92개를 실행했는지 이해 |
| 1 | E3의 저자 직접 작성 사실과 JOI 사용 목적을 본문에 기술 | 24개 행동 패턴의 구성·선정 이유와 평가 사용 이력을 설명 |
| 1 | E1 후속 72건까지 완료된 저자 검토를 문서와 본문에 반영 | 에이전트 초안 작성과 저자 검토를 구분하여 기록. 미검토라는 잘못된 서술 제거 |

| 2 | 382건 결과를 구조/패턴 그룹별로 보조 집계 | 전체 382 분모와 REFUSED/UNKNOWN 보존, 작은 집단의 우열을 과장하지 않음 |
| 3 | 더 강한 외적 타당성이 필요하면 새 외부 과제를 고정해 E3 보완 | 평가 전에 출처·해석·reference·선정 기준을 고정하고 outcome을 보고 교체하지 않음 |

1·2는 현재 피드백에 대응하는 핵심이다. 3은 “새로운 외부 요청에도 잘 작동한다”는 주장을 유지하려는 경우 가치가 커진다. 기존 382건의 설명을 풍부하게 하는 것만으로 held-out 증거가 생기지는 않는다. 기존 100건을 E3에 추가하더라도 이미 해석·개발에 사용했다면 새 holdout이라고 부를 수 없다.

**표본 수의 정당화:** 100건을 통계적 검정력이나 포화로 정당화한 기록은 없다. 목적 표집과 수집 상한이라는 실제 과정을 설명하고 주장 범위를 맞춘다. 다른 논문도 100개를 썼다는 이유는 충분하지 않다. 목적이 대표적 빈도/성공률 추정으로 바뀌면 별도의 모집단·표집 설계가 필요하다.

## 8. 교수님께 설명할 핵심

> 현재 100건은 공식 예제, 논문 자료, 공개 참가자 응답, 커뮤니티 게시물에서 목적 표집한 외부 요구 corpus입니다. 범위 내 기존 20건과 후속 72건 모두 저자가 검토했습니다. 382건은 저자가 JOI 플랫폼에서 사용하기 위해 직접 작성한 과제입니다. 이 두 구축 경로와 평가 역할을 구분하여 설명하겠습니다. SenSys의 24개 유형표를 유지하면서, 본문에 구축·선정 절차와 실제 행동/구조 분포를 추가하고, 항목별 출처와 해석을 artifact로 연결하는 것이 적절합니다.
