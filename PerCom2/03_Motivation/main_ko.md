# Problem and Motivation — 한글 검토본

§1과 §2를 종합하면 과제는 명확하다. 배포 전에 생성된 코드가 사용자의 의도한 행동 명세를 보존하는지 판단하는 관문이 필요하다. 이 절에서는 먼저 우리 환경에서 이러한 관문이 충족해야 하는 요구사항을 정리한다. 이어서 가능한 검사 접근을 살펴보고 LLM judge의 판정 일관성을 평가하여 제안하는 설계로 연결한다.

**배포 관문의 세 가지 요구사항.**

- **R1 (검증 기준).** 우리가 다루는 authoring 환경에서는 요청별 검증 기준이 미리 주어지지 않는다. GPIoT처럼 입출력 테스트 사례가 제공되는 알고리즘 코드 평가는 이를 기준으로 생성 코드를 검사할 수 있다(§2). 반면 여기서 확인해야 할 것은 사용자가 요청한 기기 동작이 시간에 따라 올바르게 발생하는지이며, 요청 자체는 실행해 대조할 수 있는 명세가 아니다. 따라서 요청으로부터 기대 동작을 정의하는 검증 기준을 구성해야 한다.
- **R2 (안정성).** 배포 결정은 이진 판단이다. 같은 명세 아래에서 같은 행동을 하는 두 프로그램은 같은 배포·거부 판정을 받아야 한다. 동일한 프로그램을 반복 평가해도 판정이 일치해야 한다. 동작이 같아도 코드 작성 방식에 따라 판정이 흔들리는 검사기는 개별 판단의 품질과 별개로 유일한 배포 관문으로 사용하기 어렵다.
- **R3 (로컬 검증).** 본 연구는 자동화 요청과 기기 정보가 외부 서비스에 노출되지 않는 환경을 전제로 한다. 이를 위해 VETS는 로컬 언어 모델로 IR과 코드를 생성한다. 생성 결과를 검사하는 과정에서도 이 전제가 유지되어야 하므로, 검증 관문은 클라우드 서비스에 의존하지 않고 로컬에서 실행되어야 한다.

**가능한 검사 접근.** 가장 직접적인 방법은 생성된 코드를 기준 텍스트와 비교하는 것이다. 그러나 §1의 온도 예시처럼 동일한 행동은 구문이 다른 구현으로 표현될 수 있고, 잘못된 구현이 오히려 요청과 비슷하게 보일 수 있다. 대신 생성 모델에 자신의 코드를 검사하고 수정하도록 요청할 수도 있지만, SimuHome~\cite{simuhome}은 자체 수정으로 스케줄링 오류를 복구하는 데 한계가 있음을 보고했다. 코드를 사용자에게 보여주는 방법도 구현 세부사항의 검토를 요구한다. TAP-Debug~\cite{tapdebug}에서는 비전문가가 규칙의 기본 IF(event)와 WHILE(state) 조건조차 자주 잘못 해석했다. 이러한 한계는 텍스트 유사성, 모델의 자체 평가, 사용자의 코드 검사에만 의존하지 않는 행동 검사의 필요성을 보여준다.

**LLM judge**~\cite{llmjudge}. 또 다른 접근은 요청과 코드를 별도의 LLM에 전달하여 서로 부합하는지 검사하는 것이다. 이 방법은 일견 타당해 보이며, 실제로도 사용된다(ChatIoT의 Evaluator~\cite{chatiot}, §2). 따라서 같은 코드를 반복해서 제출할 때와 동작은 그대로 두고 코드 작성 방식을 바꿀 때 모두 judge들이 R2를 충족하는지 평가한다.

코드 표현이 달라져도 판정이 일관되게 유지되는지 살펴보기 위해, 생성 코드 평가(§7)에서 동작은 유지하면서 코드 작성 방식을 바꿀 수 있는 JOI 프로그램 217개를 사용했다. 각 자연어 요청–프로그램 쌍을 Qwen3.5-9B~\cite{qwen35,qwen35fp8}, GPT-5.4-mini~\cite{gpt54mini}, Claude-Sonnet-5~\cite{claudesonnet5}에 세 번씩 제출했다. 언어 문서를 함께 제공했으며, Timeline IR은 judge에 제공하지 않았다. Qwen은 temperature를 0, seed를 0으로 설정했고, GPT는 seed를 42로 고정했다. 다음으로 모든 judge가 각각 다수결 투표(majority vote)로 승인한 원본 52개를 선정하고, 이 원본들의 코드 작성 방식을 바꾸고 Behavioral Explorer(§6)로 동작 보존을 확인한 변형본 168개를 평가했다. 거부율(rewrite rejection rate)은 각 judge가 이 변형본을 사용자 요청을 올바르게 구현하지 못한 코드로 판정한 비율이다.

**표. 변경하지 않은 코드의 판정 불일치.** 원본 217개를 각각 세 번 평가했을 때 세 판정이 모두 같지 않았던 프로그램의 비율이다.

| 지표            | Qwen3.5-9B | GPT-5.4-mini | Claude-Sonnet-5 |
| --------------- | ---------: | -----------: | --------------: |
| 판정 불일치 (%) |        0.0 |         16.6 |             9.7 |

전체 변형본에 대한 거부율은 클라우드 judge인 GPT와 Claude가 각각 10.1%와 6.0%로 Qwen의 20.8%보다 낮았다. 그러나 표에서 보듯 같은 코드를 세 번 제출했을 때, seed를 고정한 GPT에서도 판정 불일치율은 16.6%였으며 Claude는 9.7%였다. 즉, 이 실험에서 변형본에 대한 거부율이 낮더라도 동일 코드에 대한 반복 판정의 일관성까지 확보되지는 않았다.

반면 Qwen은 위 설정에서 변경하지 않은 코드에 대한 반복 판정 불일치율이 0.0%였다. 하지만 동작은 같고 작성 방식만 다른 변형본에서는 전체 거부율이 세 judge 중 가장 높았다. Qwen은 표기나 논리 구조가 달라져도 승인 판정을 대체로 유지했지만, 시간 구조가 달라지면 동일한 동작을 구현한 코드도 자주 거부했다. 시간 구조 변형의 거부율은 64.6%에 달했다. 그림의 세부 유형을 보면, Qwen의 거부율은 루프를 펼친 변형본(UNR)에서 90.9%, 실행 주기를 절반으로 줄이되 본문은 두 번 중 한 번만 실행하는 변형본(PHV)에서 94.1%였다. 같은 코드에서의 반복 일치가 동일한 동작을 구현한 서로 다른 코드 사이의 판정 일치로 이어지지는 않은 것이다.

**그림. 공통으로 승인된 원본 52개의 행동 보존 재작성에 대한 거부율.** 각 유형 아래에는 변환본 수를 표시한다. VAR: 변수명 변경; CMP: 비교식 좌우 교환; UNIT: 시간 단위 변환; GRP: 그룹 조건 표기 변경; BR: 조건 반전·분기 교환; ELS: else 분리; DLY: delay 분할; UNR: 루프 펼치기; PHS: 정수 phase를 Boolean flag로 변경; WPC: wait 전 조건 검사; PHV: 주기 절반·교대 실행.

이 결과는 버그 탐지 정확도가 아니라 판정 일관성에 관한 것이다. 재작성 결과는 공통으로 승인된 집합을 조건으로 한다. GPT와 Claude는 변경하지 않은 코드에서도 판정이 달랐고, 표와 그림의 모집단 및 지표 정의도 다르므로, 이 비율들로 재작성의 추가 효과를 분리할 수는 없다. 시험한 조건에서 이러한 관찰은 안정적인 배포 결정을 이 judge들에만 맡기는 데 한계가 있음을 보여준다. 가능한 모든 LLM 기반 검사기를 배제하는 결과는 아니다.

**설계 방향.** 요구사항과 관찰 결과는 명시적인 행동 기준과 별도의 실행 기반 검사를 가리킨다. R1에 따라 authoring 중 기준을 구성해야 하고, R2에 따라 코드의 표현에 의존하지 않고 행동을 비교해야 하며, R3에 따라 로컬에서 실행되어야 한다. VETS는 Timeline IR(§5)로 자동화의 시간적 제어 흐름을 명시하고, Behavioral Explorer(§6)로 생성 코드를 이 기준과 대조한다. §1에서 설명했듯 이 보장은 확정된 IR이 의도한 자동화를 담고 있다는 가정에 의존한다.
