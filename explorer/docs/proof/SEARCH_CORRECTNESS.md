## 1. 모델과 정리의 전제

검증 모델 M은 고정된 IR·코드·binding·inventory, 정수 시작 시각 t₀,
양의 정수 입력 간격 Δ, 유한 외부 입력 도메인 D₁,…,Dₙ, 유한 초기 GV
도메인 I₁,…,Iₘ으로 이루어진다. 기본 Δ는 100ms다. 도메인은 값뿐 아니라
타입을 가진다. `1`, `1.0`, `true`, `0.0`, `-0.0`의 구분이 유지된다.
센서 범위·초기값의 현실 적합성은 M을 제공하는 측의 책임이다.

입력 이력 u는 각 t₀+kΔ에서 D=∏Dᵢ의 임의 원소를 선택한다. 서로 다른
센서의 동시 변화와 임의 크기의 값 변화를 허용한다. 그 사이 값은 유지된다.
처음부터 모든 I=∏Iⱼ와 모든 u₀를 검사한다. 프로그램의 내부 저장소는
각각 독립적으로 시작·전개한다. 외부 GV 축과 내부 GV의 구분도 M의 일부다.

각 프로그램의 구체 상태는 제어 위치, 변수, GV, 활성 타이머, edge 이력,
종료 상태다. 정수 ms 시각 t에서의 반응 함수 R(P,s,u,t)는 유한한 내부
실행을 거쳐 차단·period 대기·종료 상태와 ACTION 열을 반환한다.
종료 상태는 이후 무행동 흡수 상태다. 동일 시각의 새 입력을 먼저 적용한다.

다음 전제를 명시적으로 둔다.

1. R은 지원 프로그램에서 순수하고 결정적이다. 한 반응이 연료 한도를
   초과하거나 지원 밖 값/문법을 만나면 긍정 판정을 반환하지 않는다.
2. 실행은 반응 시점에 차단 위치까지 진행된다. 다음 입력·활성 타이머
   만료·파생 clock 값 변경 전에는 추가 관찰이나 미래 관련 상태 변경이 없다.
3. 미래 관련 상태는 전부 키에 담긴다. 파서/grounding이 외부 읽기를 정확히
   연결하고, 주어진 D가 사용되는 외부 입력을 빠뜨리지 않는다.
4. 무제한 시간 병합에서는 프로그램이 절대 clock과 실행기 내부 타이머
   레지스터를 읽지 못한다. 실행기 타이머는 정수 ms를 정확히 표현한다.

명시 도메인 경로의 정리는 D에 대한 전수 검증이다. 자동 입력 모델의
대표값과 원래 허용 값 사이의 연결은 [INPUT_COVERAGE.md](INPUT_COVERAGE.md)
§6에서 논증한다. 그 모델 계열이 실제 센서 타입이라는 사실은 별도 전제다.

## 2. 관찰 관계

관찰 O는 순차 호출 그룹의 열이다. 각 그룹 안에서 실제 장치별 ACTION
열을 만들고 장치 식별자로 정렬한다. 같은 장치의 순서, 중복, 대상, 동작,
인자는 보존된다. 서로 다른 호출 그룹의 순서는 바꾸지 않는다.

따라서 독립 장치 ACTION의 순열은 같은 정규형을 가지며, 같은 장치의
서로 다른 순서나 중복 제거는 일반적으로 다른 정규형을 가진다. 구현은
`observation.actions_observation`이다. 이는 선택한 관찰 관계의 정의이며
실제 서비스의 성공/실패나 물리 효과까지 검증한다는 뜻이 아니다.

ACTION의 수치 인자에서 `1`과 `1.0`은 같게 볼 수 있어도, 저장소의 두 값은
병합하지 않는다. 이후 문자열 변환으로 `"1"`과 `"1.0"`을 구별할 수 있기
때문이다. 저장소 키는 `state_key.freeze_state`를 사용한다.

## 3. 이벤트 생략 보조정리

반응 후 시각 t에서 다음 입력 격자, 양쪽 활성 타이머 만료, 필요할 경우
다음 정수 초 경계의 최솟값을 e라 하자. clock 필드들은 정수 초 경계에서만
바뀌므로 매 초 경계를 포함하면 충분하다. 실제 필요한 경계보다 많은
이벤트를 처리하는 것은 축소 효과만 줄인다.

전제 2에서 모든 정수 시각 t<r<e의 입력은 같고, delay/period는 미만료이며,
wait 조건의 외부 값·내부 값·clock 값도 바뀌지 않는다. wait 진입 시 edge
이력 갱신, 지속 타이머의 생성·취소는 이미 현재 반응에서 처리됐다. 따라서
매 ms 실행기의 해당 반응들은 무행동이며 상태가 그대로다. 이 구간을
생략한 뒤 e에서 반응해도 관찰과 후속 상태가 같다.

e가 입력과 타이머의 공통 시각이면 양쪽 실행 모두 새 입력을 먼저 적용한다.
따라서 지속 조건 취소와 만료의 우선순위도 보존한다. 이 논증을 이벤트
개수에 대해 귀납하면 이벤트 실행과 매 ms 실행의 timed ACTION trace가 같다.

구현 대응: `timed.next_time`, 세 실행기의 `next_wakeup_ms`,
`exact_timed_product`의 매 ms 전개. 대상 실행기는 `IrRunner`,
`PauseRunner`, `OneShotRunner`와 종료 wrapper다. 임의의 외부 runner가
같은 메서드 이름을 제공한다는 사실만으로 이 전제를 충족하지 않는다.

## 4. 상태 병합 보조정리

### 유한 시간 범위

bounded 키는 양쪽 구체 저장소, 유지 입력, 절대 시각을 포함한다.
`freeze_state`는 지원되는 저장소 값의 타입·구조를 보존하고, float는
hex 표현으로 부호 있는 0까지 구분한다. 따라서 같은 키의 상태는 같은
미래 관련 데이터와 남은 시간 범위를 갖는다. 전제 1에서 같은 입력의
다음 관찰과 후속 상태가 같다. 미래 반응 횟수에 대한 귀납으로 같은 키의
모든 허용 후속 ACTION trace가 같다.

### 길이 제한 없는 범위

clock 비사용 상태에서 내부 타이머 시각 τ를 정확한 상대값 t−τ로 바꾸고,
입력 위상 (t−t₀) mod Δ를 보존한다. 나머지 저장소는 전부 그대로 둔다.
코드는 초 단위 API 호환을 위해 내부 시각을 `Fraction(ms,1000)`으로 저장하며
밀리초 환산이 정확하다. 반올림한 부동소수점 시각의 동치를 가정하지 않는다.

같은 키의 두 상태 사이 시간차 c는 입력 위상을 보존한다. 전제 4에서
각 활성 타이머의 만료까지 남은 시간은 같고, 입력·내부 값에 대한 조건도
같다. 한 상태의 다음 반응을 다른 상태에서 c만큼 이동하면 동일한 관찰과
다시 같은 키의 후속 상태를 얻는다. 새 타이머 생성도 정확히 c만큼
이동한다. 이는 동일한 입력 선택에 대한 양방향 시뮬레이션을 이룬다.

clock을 읽으면 이 시간 이동을 적용하지 않고 절대 시각을 남긴다.
그래프가 무한하거나 너무 크면 cap에 도달할 수 있으며 동치가 되지 않는다.

## 5. BFS의 입력·후속 상태 포괄성

초기 열거는 I×D의 모든 원소를 실행한다. 귀납적으로 임의의 허용 이력의
현재 상태가 큐에 있거나, §4에서 미래가 같은 대표 상태로 검사됐다고 하자.
다음 이벤트는 §3에 의해 누락이 없다. 입력 격자이면 D 전체를 열거하며,
그 외에는 유지 입력 하나가 유일한 허용 입력이다. 따라서 모든 후속 상태도
실행되거나 미래가 같은 대표 상태로 병합된다. 수학적 귀납으로 모든 유한
허용 입력 이력의 관찰을 포괄한다. 동시에 전이는 실제 허용 입력과 R에서만
생기므로 탐색이 금지된 입력 변경을 새로 만들지 않는다.

구현 대응: `timed_product`의 `combos`, `initial`, `transition`, `queue`,
`seen`. 초기 상태가 하나인 테스트로 이 정리를 대체할 수 없다.

## 6. 판정 정리

위 전제와 보조정리 아래 다음이 성립한다.

- **DIVERGE:** 저장한 초기 GV·시작 시각·부모 경로를 구체 실행기로 재생해
  관찰 차이를 확인하면 M 안의 비동치 증거다. gate는 재생 확인을 요구한다.
- **EQUIV-BOUNDED(H):** cap/실행 오류 없이 큐 처리가 완료되고 차이가 없으면
  모든 I와 모든 허용 입력 이력에서 닫힌 구간 [t₀,t₀+H]의 ACTION이 같다.
- **EQUIV-FIXPOINT:** 시간 제한 없이 유한한 도달 몫 그래프가 닫히고 차이가
  없으면 모든 유한 길이의 허용 입력 이력에서 ACTION이 같다. 무한 이력의
  차이도 어떤 유한 접두사에서 나타나야 하므로 무한 timed trace 역시 같다.
  0 시간 무한 실행은 성공 반응이 아니며, 정상 이벤트 시간은 최소 1ms씩 전진한다.
- **INCONCLUSIVE / REFUSED:** cap, 실행 불능, 지원 밖 프로그램은 위의 동치
  정리를 충족하지 않는다. 일부 BFS만 완료한 결과는 긍정 판정이 아니다.

시간 제한 안에서 종료 상태가 더 빨리 나타나도, 상대편의 후속 ACTION은
계속 비교한다. 종료 플래그 자체의 차이는 이 정리의 관찰 차이가 아니다.

### 과거 런타임 근거 점검 — 선택적 배포 보장

로컬 `sensys/simulators/joi_simulator.py`는 이전 연구용 실행기다. `Delay`는
가상 시각을 전진시키고 반복 루프는 이후 period를 더하지만, periodic
`WaitUntil`은 `_AbortTick`으로 현재 회차를 끝낸다. 이 동작은 새 계약의
차단 위치 재개와 다르므로, 새 period/wait 적합성의 정답 실행기로 쓸 수 없다.
`docs/JOI_SPEC.md`도 period를 재실행/폴링 간격으로 설명할 뿐 기준점을
확정하지 않는다. 확인한 로컬 자료에 실제 JoI 서버 스케줄러의 근거는 없다.
따라서 이 자료로 실제 런타임 일치를 선언하지 않는다.

## 2026-09-08: 관계 추상 상태의 폐쇄

`relational-state-v1`은 기존 구체 상태의 동일성 병합과 별개다. 실제 초기화에서 관계를
세운 뒤 임의 정수 N에 대해 ACTION과 선택 변수 갱신/순서/post 관계를 확인하고,
동일 post 정수 쌍을 새 N으로 일반화한다. 이는 관계를 만족하는 모든 구체 쌍을 포함한다.
기호 조건은 양 분기, 환경 guard는 기존 공동 분할의 전체 입력 곱집합을 전개한다.
정확한 상대 타이머/입력 위상/pc/초기화/종료/보유 입력/나머지 값을 키에 보존한다.
queue 고갈과 모든 전이 의무 완료가 함께 있어야 H 없는 EQUIV-FIXPOINT다.
cap·unsupported·관계 실패는 미완료이며 추상 실패를 구체 DIVERGE로 쓰지 않는다.
