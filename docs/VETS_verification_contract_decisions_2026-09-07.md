## 1. 목표와 작업 우선순위

- 사용자의 최우선 목표는 **논문에서 `formally verifies`라고 말할 수 있도록 Explorer를 개선하고, 그 보장을 유지하는 범위에서 효율을 높이는 것**이다.
- `abstract_draft.txt`의 `formally verifies`를 지금 선제적으로 낮추지 않는다. **9월 11일까지 구현·증명을 최대한 진행하고, 목표에 미달하면 그때 초록을 수정**한다. 현재 문구가 증명 완료를 뜻하지는 않는다.
- **논문 등록은 아직 하지 않았다.** 사용자는 9월 11일까지 등록할 계획이라고 명시했다. 등록 여부를 다시 묻거나 즉시 등록을 반복해서 최우선 작업으로 제안하지 않는다.
- BFS로 **선언된 모델과 탐색 범위 안의 모든 도달 가능한 상태·입력 이력을 포괄하여 IR과 코드의 ACTION을 비교**하는 것이 Explorer의 핵심이다. 개별 샘플이나 한 초기 상태만 검사하는 도구처럼 설명하지 않는다.
- 입력 축소·상태 병합·시간 점프는 그 포괄성을 보존해야 한다. BFS라는 알고리즘 이름이나 유한한 대표값 집합 자체가 포괄성의 증명은 아니다.
- 논의 종료 후의 방향은 합의 기록 → 실제 구현과 차이 확인 → 코드 수정·회귀 테스트 → 증명·재평가다. 이 기록 요청 자체를 코드 수정·실험 실행 완료로 해석하지 않는다.

## 2. 확정한 규칙

### D1. ACTION 관찰과 독립 장치의 순서

- 같은 논리 시각에 수행되는 **독립 장치의 병렬 ACTION은 나열 순서를 무시**한다.
- 대상 장치, 동작, 인자, 발생 시각, 중복 횟수는 보존한다. 명시적인 순차 관계는 보존한다.
- 대표 사례: 하나의 `Switch.On` 호출이 binding으로 거실·주방 조명에 펼쳐졌다면 `[거실.On, 주방.On]`과 `[주방.On, 거실.On]`은 같다.
- 이것은 모든 ACTION을 정렬하거나 집합으로 바꾸라는 뜻이 아니다. 같은 장치의 `On→Off`, 중복 호출, 명시적인 순차 관계를 제거하면 안 된다.
- 서로 다른 태그 집합이 같은 장치에 매칭될 수도 있다. 독립성은 실제 장치 ID로 grounding한 결과와 인과 관계를 기준으로 판단해야 한다.

현재 구현과의 차이: `SUPPORTED_FRAGMENT.md`, `exact_tick.py`의 `_actions`, 기존 순서 회귀 테스트는 tick 내 전체 ACTION 시퀀스 순서를 비교한다. 새로운 관찰 관계를 IR/code 비교, 완전 열거기, 반례 재생에 일관되게 반영해야 한다. 한 호출의 다중 장치 확장에서 생긴 순서와 서로 다른 순차 호출의 순서를 구분할 정보가 필요하다.

### D2. 입력값·입력 이력과 안전한 축소

- float **입력값은 소수 첫째 자리, 즉 0.1 단위로 모델링**한다.
- 선언된 입력 범위 안에서는 각 입력 단계마다 자유로운 값 변화를 허용하고, 여러 센서의 동시 변화도 허용한다. 근거 없는 변화 속도 제한이나 한 번에 한 센서만 변한다는 제한을 두지 않는다.
- 0.1은 값의 정밀도이며 시간 간격이나 최대 변화량이 아니다. `9.0→25.7` 같은 변화도 허용한다.
- IR과 코드 양쪽에서 같은 관찰 행동과 이후 상태(또는 보존이 증명된 상태 표현)를 보장하는 입력만 묶는다.
- 지원 단편 안에서 안전한 입력 축소를 증명하지 못하는 경우, 명시된 유한 도메인이 있으면 해당 값들을 전체 열거한다. 전체 열거를 완료하지 못하면 동치로 처리하지 않는다.
- **이 정책은 아래 D7의 기존 미지원 산술식을 새로 지원한다는 결정이 아니다.**

미결정·구현 전 확인:

- **0.1 단위만으로 유한 도메인이 되지 않는다.** 센서별 최솟값·최댓값, 범위의 출처와 선언 위치는 확정하지 않았다.
- 현재 IR에 센서별 type/domain/precision 선언이 이미 있다고 가정하지 않는다. 기존 v3 평가에는 외부 유한 입력 manifest가 있지만 이것이 IR 자체의 선언이나 모든 연속 입력에 대한 보장은 아니다.
- 도메인 선언을 IR에 추가하기로 합의한 적은 없다. 기존 IR, 외부 manifest, 장치·서비스 모델의 역할을 확인해 최소 변경으로 정해야 한다.
- 입력 정밀도 합의를 모든 산술 중간값·ACTION 인자의 소수 첫째 자리 반올림으로 확대하지 않는다. 임의 반올림은 ACTION 차이를 숨길 수 있다.
- 아래의 정확한 delay 만료 규칙을 적용하면 기존 고정 tick 사이에도 실행이 발생한다. 입력이 들어올 수 있는 시각·관찰되는 시점과 H의 의미는 새 시간 모델에서 연결해 정의해야 한다. 센서 변화가 period 시점에서만 일어난다고 새로 가정하지 않는다.

### D3. delay는 만료 시점에 재개

- `delay(d)`는 시작 시각에서 d만큼 지난 **만료 시점에 바로 다음 문장으로 재개**한다.
- 예: `period=1초`, `delay=1.5초`여도 다음 문장은 1.5초에 실행한다. 2초 tick까지 미루지 않는다.
- 현재 IR 실행기의 "경과 시간이 지연 이상이 되는 첫 tick" 동작은 이 합의와 다르므로 수정 대상이다.
- Explorer는 IR·코드 양쪽의 재개·timer 시점을 고려해야 한다. 시간 점프를 쓰려면 건너뛴 시간의 입력 변화와 ACTION을 놓치지 않는다는 보존 근거가 필요하다.

### D4. period는 회차 종료 후부터 계산

- 실행 흐름: **회차 시작 → wait/delay 대기 → 재개해 나머지 실행 → 회차 종료 → period 대기 → 다음 회차 시작**.
- 한 회차가 0초에 시작해 1.5초에 끝나고 period가 1초이면 다음 회차는 2.5초에 시작한다.
- 고정 시각마다 새 인스턴스를 중첩 실행하는 방식은 채택하지 않는다.
- `period=0` one-shot의 기존 구분을 없애기로 결정한 것은 아니다. wrapper period와 IR cycle.period의 대응도 구현에서 확인해야 한다.

주의: 사용자는 실제 JoI도 이 방식일 가능성이 높다고 판단했으나 확신하지 않았다. **채택한 의미론과 실제 JoI 런타임의 일치는 아직 미확인**이다. wait가 blocking이라는 사실만으로 period의 기준이 증명되지는 않는다. 구현 적합성 평가에서 확인할 항목으로 남긴다.

### D5. 외부 입력과 지속 조건 timer 만료가 같은 시각이면 입력 우선

- 먼저 해당 시각의 외부 입력을 반영한다.
- 유지 조건이 깨진 timer를 취소한 뒤, 나머지 timer의 만료를 처리한다.
- 예: "10초간 움직임이 없으면 소등"에서 정확히 10초에 움직임이 들어오면 지속 조건 timer를 취소하고 소등하지 않는다.
- 이 규칙을 임의의 외부 입력이 무조건 `delay`를 취소한다는 뜻으로 확대하지 않는다. 지속 조건이 붙은 timer의 취소 의미다.

### D6. rising-edge의 첫 관찰

- 자동화 시작 시 이미 조건이 참이면 한 번 발화한다.
- 이후에는 거짓→참 변화에서 재발화한다.
- 매 반복 회차마다 edge 이력을 초기화해 참인 동안 계속 발화시키라는 뜻이 아니다. 첫 시작과 이후 반복을 구분한다.
- 현재 IR 실행기의 시작 시 false latch 방향과 일치한다. 대기·period 구간에서 edge 이력을 언제 관찰·갱신하는지는 실행 모델에 맞춰 확인해야 한다.

### D7. 기존 미지원 표현식 정책 유지

- `joint-guard`, `derived-guard`, `arith-arg`, `observable-counter` 등 **기존 지원 단편 밖 표현식은 탐지 → REFUSED 정책을 유지**한다.
- 사용자 전달 기록상 09-02에 이미 확정된 결정이다. `온도 A > 온도 B`, `온도+습도>80`, `speak(온도*2)`를 미결정 지원 확대 항목으로 다시 열지 않는다.
- 당시 178개 정답쌍 중 관련 실존 2행 `C11_001`, `C14_002`를 논문 제한으로 두기로 했다는 과거 기록을 존중한다. 이 분모는 v3의 388회 생성/311 READY와 다르다.
- 근거: `explorer/SUPPORTED_FRAGMENT.md`, `explorer/features.py`, `explorer/tests/test_soundness.py`, 과거 §9.17–9.18 기록.
- 범위 밖 프로그램을 명확히 거절하는 것은 formal verification과 양립한다. 지원 단편의 포괄성·soundness는 별도로 증명해야 하며, 거절 정책만으로 Speaker 반례가 해결되지는 않는다.
- predicate abstraction/SMT 등을 통한 산술 지원 확대는 이번 필수 작업으로 채택하지 않았다.

### D8. binding은 검증·실행 범위에서 고정

- 자동화 실행 도중 장치 목록이나 binding이 갑자기 바뀌는 상황은 고려하지 않는다.
- 장치의 켜짐/꺼짐 등 상태 변화와 대상 장치 집합 변경을 혼동하지 않는다.
- 초기 센서·장치 상태도 선언된 모델의 탐색 대상에 포함한다. 특정 초기 조명 상태만 검사하는 별도 설계를 제안하지 않는다.
- 같은 초기 환경·외부 입력을 제공하되, IR과 코드의 내부 상태는 각자 전개한다. 내부 상태를 강제로 같게 맞추지 않는다.

### D9. 종료는 탐색 상태이지만 독립적인 관찰 ACTION은 아님

사용자가 판정 규칙 결정을 위임했고, 다음으로 정리했다.

- 종료 여부가 다르다는 이유만으로 바로 `DIVERGE`를 내리지 않는다.
- 종료 상태는 BFS의 미래 관련 상태에 보존한다. 한쪽이 종료해도 다른 쪽의 미래 ACTION을 계속 검사한다.
- 예: one-shot에서 `On 후 종료`와 `On 후 영원히 무행동`은 ACTION trace 기준으로 같을 수 있다. 이를 주장하려면 해당 탐색 범위에서 추가 ACTION이 없다는 근거가 필요하다.
- 반복 실행에서는 종료가 period 대기·다음 회차로 이어진다. `종료 후 다시 On`과 `영원히 대기`는 이후 ACTION 차이로 구분한다.
- `DIVERGE`, `EQUIV-BOUNDED(H)`, `EQUIV-FIXPOINT`, 미지원/`INCONCLUSIVE`를 구분한다. 탐색 cap·미완료는 동치가 아니다.

현재 구현과의 차이: `explorer/exact_tick.py`는 ACTION 또는 `terminated`가 다르면 바로 `DIVERGE`를 반환한다. 이 비교와 종료 이후 전개를 수정하고, Explorer·반례 재생도 같은 계약을 쓰도록 해야 한다.

## 3. 불필요한 논의 정정: 현재 IR에는 병렬 분기가 없다

- 실제 `_STEP_OPS`는 `start_at`, `wait`, `delay`, `read`, `call`, `if`, `cycle`, `break`의 8개다.
- `files/timeline_ir/extractor.md`는 하나의 linear scenario를 정의하고, `explorer/ir_step.py`는 단일 `pc`를 따라 실행한다. `par`/fork 같은 내부 병렬 제어 흐름은 없다.
- 따라서 assistant가 제안했던 **독립 병렬 규칙 간 snapshot–evaluate–merge–commit, 공유 상태 충돌·재진입 정책 논의는 현재 범위에서 제외**했다. 이전 advisor의 병렬 언어 설계를 현재 구현으로 간주하지 않는다.
- 별도로 등록된 여러 시나리오의 상호작용 검증을 새 목표로 추가하지 않는다.
- D1의 한 호출을 여러 독립 장치로 펼칠 때의 순서 무관성은 유효하다. 그것이 내부 병렬 분기 지원을 뜻하지 않는다.

## 4. binding 구조 확인에서 발견한 사항 — 확정 변경과 구분

코드 확인 결과:

- IR은 `Switch.On` 같은 서비스 중심 호출을 쓰며 selector는 별도다.
- `timeline_ir/mapping/adapter.py`는 서비스별 여러 selector와 장치 집합을 만든다.
- `explorer/gate.py`는 IR 측 binding과 후보 코드의 selector를 각각 장치 ID로 grounding하고, 호출을 장치별 ACTION으로 펼친다.
- 라이브 `lowering/run_local_ir.py::_live_binding`은 같은 skill의 장치를 합쳐 모든 등장에 같은 집합을 적용한다. 평가 gate에는 등장 위치별 binding 경로도 있다.
- 따라서 `거실 On → delay → 주방 On`처럼 같은 서비스가 서로 다른 위치에서 다른 대상을 갖는 경우, 라이브와 평가 경로의 대응을 확인해야 한다.

assistant의 제안(사용자가 별도 확정하지 않음): 호출 위치의 고유 ID로 binding을 연결하고, 검증의 기준 명세를 IR+binding으로 명시하는 방법. **호출 ID 문법 추가나 binding 개편이 승인·완료됐다고 기록하지 않는다.** 기존 형식이 보존하는 정보와 누락 가능성을 먼저 확인한다.

## 8. BOOL 입력은 true/false만 (후속 사용자 확정)

사용자는 BOOL에 None이 포함된 것을 지적하고 **true/false만 지원**하도록 지시했다.
이 결정은 과거 nullable BOOL 가정보다 우선한다.

- Catalog BOOL/BOOLEAN 센서·조회 반환 입력은 항상 false/true. 첫 snapshot부터
  유효해야 하며 None을 false로 보정하지 않는다. BOOL 형과 숫자0/1도 구분한다.
- 다른 타입의 결측, 미초기화 로컬 상태, 별도 선언 GV 모델은 일괄 변경하지 않는다.
- 기본 입력 도메인뿐 아니라 명시 domain/직접 탐색/직접 runner 재생에도 적용한다.
- 모든 모션 값이 BOOL이면 `all(Motion == false)`와 `not(any(Motion == true))`는
  같다. `not(all(Motion == true))`는 다른 조건이다.
- formal 근거 완성이 최우선이다. 이 입력 계약의 모든 값/이력을 빠짐없이 검사하는
  것이 목표이며 문법 확대나 미지원 산술식을 다시 여는 것이 필수는 아니다.
- 기존 평가 결과를 덮어쓰지 않고 새 결과에 `strict-two-valued-v1` 정책을 기록한다.
