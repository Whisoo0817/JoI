# Reactive-temporal 자동화의 검증 문제와 Home Assistant의 위치

작성·자료 확인: 2026-09-08. [전체 구성 논의안](VETS_PAPER_STRUCTURE_AND_CLAIMS.md)의 motivation과 도메인 범위를 보강하는 검토다. 사용자 요구에 따라 Home Assistant(HA)를 두 번째 플랫폼 후보로 고려한다. HA 지원·검증·실험이 완료되었다는 기록은 아니다. 초록과 기존 결과는 변경하지 않는다.

자료는 가까운 선행연구와 공식 플랫폼 문서를 대상으로 한 단일 검토다. 체계적 문헌 전수조사나 “관련 연구가 전혀 없다”는 증명이 아니다. 아래에서 문헌으로 확인한 사실, 그에 대한 해석, 앞으로 입증할 제안을 구별한다.

## 1. 문제 정의의 중심

**문제는 실행기가 없다는 것이 아니다. 주어진 입력 이력에서 코드를 실행할 수 있어도, 그 결과가 요구된 행동인지와 다른 허용 이력에서도 명세를 지키는지는 별도로 해결해야 한다.**

스마트홈 자동화의 결과는 단일 반환값으로 끝나지 않는다. 환경 입력에 반응하면서 언제, 어느 기기에, 어떤 인자로, 몇 번 명령을 보내고, 언제 아무 명령도 보내지 않아야 하는지가 행동이다. 긴 실행을 빠르게 재생하는 것과 가능한 실행들을 포괄하는 것은 다르다.

VETS가 다루려는 질문은 다음과 같이 정리할 수 있다.

> 확인된 요청별 시간 명세와 플랫폼용 생성 프로그램이, 같은 허용 초기 환경과 시간별 입력을 받았을 때 같은 기기 명령 이력을 만드는가?

검증기의 인증 보장은 [현재 검증 계약](../explorer/docs/model/VERIFICATION_CONTRACT.md)의 모델·지원 범위·성공 조건에 한정된다. 사용자 의도 해석, 실제 센서의 물리적 정확성, 네트워크 지연 및 다른 자동화와의 간섭까지 자동으로 해결하지 않는다.

## 2. Executor·simulator가 해결하는 것과 남기는 것

| 도구·접근 | 해결하는 질문 | VETS의 목표까지 가려면 남는 일 |
| --- | --- | --- |
| Parser·schema·서비스 검사 | 실행 가능한 형식인가, 호출 대상과 인자가 적법한가? | 적법하지만 잘못된 시간 행동을 구별해야 함 |
| Executor·simulator | 주어진 프로그램·초기 상태·입력 이력에서 무슨 일이 일어나는가? | 그때 무엇이 일어나야 하는지를 정의할 별도 기준이 필요 |
| 실행 trace·debugger | 실제 실행에서 어느 경로를 탔고 왜 그 결과가 나왔는가? | 아직 실행하지 않은 이력의 누락·추가·시간 오류는 별도로 다뤄야 함 |
| 시간 가속·random replay | 긴 시간이나 여러 표본 이력을 현실 시간보다 빠르게 실행할 수 있는가? | 속도가 빨라도 선택하지 않은 입력 이력이 남음 |
| Model checker·symbolic verifier | 모델의 가능한 실행이 지정한 속성 또는 관계를 만족하는가? | 실제 DSL을 충실히 모델링하고 기준 관계·입력·관찰·축소의 정당성을 구성해야 함 |

HA 자체도 자동화의 실행 trace와 부분 테스트를 제공한다. 공식 문서의 `Run actions`는 trigger와 condition을 건너뛰어 action sequence를 실행하며, trace는 선택한 실행의 단계와 시간을 설명한다. 그러므로 이를 전칭적 명세 적합성 검사와 구분해야 한다. [HA testing and troubleshooting](https://www.home-assistant.io/docs/automation/troubleshooting/)

SimuHome은 물리 환경 변화와 workflow scheduling을 포함한 시간 가속 시뮬레이션을 제공한다. 평가에서는 episode의 목표 상태와 특정 시점의 결과를 확인하며, 일부 scheduling 평가에서는 선행 action 이력도 확인한다. 이 연구는 “미래 행동을 실행해서 검사할 수 없다”는 주장에 대한 직접적인 반례다. VETS와의 차이는 시뮬레이션 가능 여부가 아니라, 기준과 검증 공간이다. [SimuHome §3–4.3](https://arxiv.org/html/2509.24282v3)

개념적으로 실행은 `Tr(C; g, u)` 하나를 계산한다. VETS의 목표는 고정 모델 아래 모든 허용 `g, u`에서 `Tr(IR; g, u) = Tr(C; g, u)`인지를 인증하는 것이다. 이 차이는 실행기가 두 개 있어도 사라지지 않는다. 두 실행기에 넣을 입력 이력의 포괄성과 두 trace의 비교 의미가 필요하다. 충분한 모델·기준·탐색을 갖춘 simulator로 이 작업을 하면 그것이 검증기를 구성하는 한 방법이다.

## 3. 도메인에서 실제로 어려운 부분

| 어려움 | 자동화의 구체적인 예 | 필요한 검증 요소 |
| --- | --- | --- |
| 상태와 사건이 다름 | 온도가 높은 동안 매번 켜기와 임계값을 넘을 때 한 번 켜기 | 이전 관찰·edge latch·초기 상태의 의미 |
| 현재 값만으로 과거 지속을 알 수 없음 | 지금 비어 있는 방과 5분 내내 비어 있던 방 | 조건 중단·재시작 이력과 timer 취소 |
| 시간 위치에 따라 조건의 의미가 달라짐 | 실행 시작 때 야간인지, 5분 후 action 시점에 야간인지 | guard 평가 시점, delay 재개 위치, 저장한 값과 새 읽기의 구별 |
| 상태를 가진 반복 | 세 번만 알림, 조건이 다시 발생할 때마다 한 번, 종료 후 재발화 방지 | counter·초기화·업데이트 순서·종료 후 행동 |
| 값이 출력으로 흐름 | 현재 온도를 알리는 코드가 특정 상수만 말함 | 조건의 참/거짓뿐 아니라 ACTION 인자의 값과 출처 보존 |
| 관찰하지 못한 입력 순서가 남음 | 문 열림·닫힘이 timer 만료 직전 또는 직후 발생 | 입력의 값뿐 아니라 순서·시점·timer와의 상호작용 포괄 |
| 같은 최종 상태가 다른 행동을 감춤 | 조명을 한 번 켜든 열 번 켜든 마지막 상태는 on | ACTION 횟수·대상·인자·순서·시간 관찰 |
| primitive의 조합과 runtime 정책 | 대기 중 재트리거를 무시·취소·대기열·병렬로 처리 | 플랫폼 고유 실행 의미. HA 확장에서는 새 검토가 필요 |

위 항목 전체가 VETS만의 새로운 발견은 아니다. 중요성은 **짧고 문법적으로 정상인 생성 코드에도, 요청의 시간 관계와 다른 구현이 생길 수 있고, 그 차이가 특정 이력에서만 관찰된다는 것**이다. 사용자에게 복잡한 코드를 전부 읽게 하거나 한 번 실행 결과를 보여주는 것으로 이 검증 의무를 대체할 수 없다.

입력 축이 유한해도 이력의 수는 커진다. 예를 들어 매 시점 세 Boolean 센서가 자유롭게 변하면 한 snapshot은 8가지이고, 길이 n의 원시 이력은 8^n개다. 이는 단순 열거의 규모를 설명하는 예이며, 모든 이력이 서로 다른 도달 상태를 만든다는 뜻은 아니다. 같은 미래 행동을 갖는 상태·입력을 묶을 수 있는지가 검증 방법의 핵심이다.

### 설명용 사례: 5분 지속과 5분 뒤 재검사

요구: **“방이 연속으로 5분 비어 있으면 플러그를 끈다.”** 시작 전에는 재실 상태이고, 0분에 처음 비었다고 가정한다. 아래는 실행 측정값이 아닌 의미 차이를 설명하는 구성 사례다.

- 구현 A: 비어 있는 상태가 5분 지속되면 끈다. 중간에 재실이면 지속시간을 다시 센다.
- 구현 B: 방이 비면 5분 기다린 후, 그때도 비어 있으면 끈다. 예시에서는 실행 중 새 trigger를 무시한다.

| 입력 이력 | 기준 / 구현 A | 구현 B |
| --- | --- | --- |
| 0분 이후 계속 비어 있음 | 5분에 끔 | 5분에 끔 |
| 4분에 재실, 4분 30초에 다시 비고 이후 계속 비어 있음 | 9분 30초에 끔 | 5분에 끔 |

두 구현은 문법 검사와 첫 번째 simulation을 통과한다. 나중에 보면 플러그도 둘 다 off다. 두 번째 이력을 넣고 action 시각을 기준 명세와 비교해야 차이가 드러난다. 이 사례는 **oracle, 구별 입력 이력, timed observation**의 필요를 함께 보여준다.

HA의 state trigger `for`는 새 상태의 지속시간을 표현하므로 A를 짧게 적는 수단이다. 반면 `delay` 뒤에 현재 상태를 검사하는 조합은 그 사이의 연속성을 스스로 보장하지 않는다. 풍부한 primitive가 있다는 사실과 올바른 primitive·조합을 선택했다는 사실을 구별해야 한다. [HA state trigger](https://www.home-assistant.io/triggers/state/), [HA script syntax](https://www.home-assistant.io/docs/scripts/)

## 4. “왜 아무도 다루지 않았는가”를 어떻게 고쳐야 하나

그 전제는 그대로 사용할 수 없다. 자동화의 시간 검증, 사용자 속성의 형식화, 시뮬레이션, 소스와 생성 코드의 관계 검증에는 선행연구가 있다.

| 가까운 연구 | 확인한 연구 대상 | VETS와 비교할 축 |
| --- | --- | --- |
| [AutoTap](https://hewj.info/papers/autotap.pdf), ICSE 2019 | 사용자 속성을 LTL로 만들고 만족하는 TAP 규칙을 합성·수정 | 사용자 시간 요구의 formalization은 이미 존재. 그 속성들을 만족하는 행동을 허용하는 것과 채택한 명세의 ACTION 이력을 보존하는 것은 다른 계약 |
| [TAPInspector](https://arxiv.org/abs/2102.01468), TIFS 2022 / arXiv preprint | concurrent TAP에서 latency·물리적 상호작용을 모델링하고 safety/liveness 검사 | “TAP는 단순하므로 시간 검증이 필요 없다”는 분류가 틀림. 여러 규칙의 상호작용 검증은 현 VETS보다 넓게 다루는 부분도 있음 |
| [ChatIoT](https://doi.org/10.1145/3678585), IMWUT 2024 | §3.2와 Figure 3의 LLM Evaluator가 생성 TAP의 형식·context·사용자 요청 충족 여부를 검사·수정 | 요청 대비 정확성을 검사하려는 목적 자체는 이미 있음. 그 판정은 LLM 추론이며, 요청별 실행 기준에 대한 전칭적 timed trace 인증을 제시하지 않음 |
| [AwareAuto](https://arxiv.org/html/2408.12687v1) | event/state 구분, branch·delay·dynamic parameter를 포함한 복잡한 자동화 생성과 사용자 상호작용 | 복잡한 명세·확인 인터페이스만으로 신규성을 주장할 수 없음 |
| [SimuHome](https://arxiv.org/html/2509.24282v3) | 목표가 있는 episode에서 시간·환경을 시뮬레이션하고 agent 성과 평가 | 실행을 통한 평가와 요청별 코드의 전칭적 행동 보존을 구분 |
| [CASPER](https://doi.org/10.1080/0144929X.2026.2679590), 2026 | HA에서 구조화한 요청을 바탕으로 생성하고 entity·conflict·direct/indirect chain 검사 | “생성 후 검증이 없다”는 주장을 피해야 함. 확인한 §5.2–5.3의 검사 대상은 요청별 executable reference와 코드의 timed trace 동등성과 다름 |
| [Murphy et al., Combining LLM Code Generation with Formal Specifications and Reactive Program Synthesis](https://arxiv.org/html/2410.19736v1), 2024 preprint | NL→TSL→형식적 reactive synthesis로 제어 코드를 만들고 LLM으로 함수·predicate·wrapper를 구현하거나 전체 코드를 재생성. TSL 제어 보장은 모든 입력 스트림과 함수 해석에 대해 성립 | NL에서 reactive code를 만들면서 형식적 보장을 제공하는 선행연구다. 다만 보장 대상은 TSL이 규정한 제어 관계이며, 최종 LLM 생성 구현의 구체적인 서비스 값·시간별 ACTION을 별도 실행 기준과 비교해 인증하는 절차는 제시하지 않음 |
| [Translation Validation](https://link.springer.com/chapter/10.1007/BFb0054170), TACAS 1998 | 각 번역 결과가 source를 구현하는지 검증. 원 연구도 synchronous Signal→C를 다룸 | reactive program의 source–implementation 관계 검증 자체는 새로운 문제가 아님 |

**이 문헌 분포에 대한 해석**은 다음과 같다. 이는 각 연구자가 해당 문제를 선택하지 않은 동기를 실증한 설명이 아니다.

1. 기본 TAP의 primitive는 trigger 처리 같은 구현 메커니즘을 엔진이 맡게 한다. 사람이 슬롯을 선택하는 상황에서는 별도의 생성 코드에서 메커니즘을 재구현하는 문제가 덜 드러난다. 다만 사용자가 잘못된 규칙을 만드는 문제는 예전부터 있었고 AutoTap도 이를 다뤘다.
2. IoT verification 연구는 위험한 상태·규칙 간 충돌·물리 상호작용 등 중요한 속성을 검증하는 쪽으로 발전했다. 이는 “이 요청을 구현한 바로 이 코드인가”와 다른 질문이며, 서로 대체하는 관계가 아니다.
3. 자연어 생성 연구는 의도 표현·grounding·generation·사용자 수정에, simulator 연구는 episode별 수행 결과에 초점을 두는 경우가 있다. 요청마다 독립적인 executable reference를 확정하고 생성 코드와 허용 이력 전체에서 비교하는 연결이 별도 작업으로 남는다.
4. 기존 translation validation은 출발하는 source의 의미가 주어져 있는 경우를 다룬다. 자연어 authoring에서는 그 기준을 먼저 세워야 하고, 스마트홈 DSL의 시간·서비스·입력 의미를 검증 모델로 연결해야 한다.

현재 검토한 가까운 스마트홈 연구에서는 **요청별 확정 실행 명세를 기준으로, 생성된 플랫폼 코드의 timed ACTION 동등성을 모든 허용 초기 상태·입력 이력에서 인증하는 시스템을 확인하지 못했다.** 이것이 VETS가 주기여로 내세울 구체적인 검증 과제다. 단순히 여러 기존 구성요소를 연결했다는 수준으로 기여를 축소할 이유는 없다. 반대로 “NL→reactive code에 형식적 보장을 제공한 연구가 없다”는 넓은 주장은 Murphy et al. 때문에 사용할 수 없다. 최종 “최초” 문구는 더 넓은 관련연구 확인 전에는 쓰지 않는다.

Property checking과 relational equivalence를 불가능/가능의 대립으로 만들지도 않는다. 두 프로그램의 product model에 mismatch 상태를 정의하면 동등성 문제를 model checker의 속성 검사로 표현할 수 있다. VETS가 해야 할 일은 이 문제를 스마트홈 서비스·시간·값 흐름에 맞게 구성하고, 축소와 인증의 타당성을 보이는 것이다. 또한 partial property가 열등한 것은 아니다. 사용자가 여러 구현 행동을 허용하고 싶다면 property satisfaction이나 refinement가 더 적합할 수 있다. VETS의 exact trace 계약은 확인된 명세가 선택한 행동에 대한 계약이다.

### 주기여는 생성 결과의 행동 검증이다

“구체적 behavior를 검사한다”는 말만으로 신규성을 구분하지 않는다. ChatIoT도 요청 충족을 검사하려고 하며, AutoTap의 사용자 시간 속성도 구체적 행동을 제약한다. 다음 세 축을 함께 명시한다.

1. **검증 기준:** 요청마다 사용자가 확정한 실행 가능한 시간 명세. 고정 안전 정책이나 자연어에 대한 추가 LLM 판단과 구별된다.
2. **검증 대상:** 실제 생성 후보의 관찰 가능한 ACTION 시각·대상·인자·횟수·명시 순서. 제어 구조만 합성하는 것, 선택한 속성을 만족하는 것, 일부 실행에서 목표 상태에 도달하는 것과 계약이 다르다.
3. **보장 범위:** 선언 모델의 모든 허용 초기 상태·입력 이력에서 시간 제한 없는 trace 동등성. 이는 현재 계약의 지원 범위와 인증 완료 조건에 한정된다.

NL→IR 해석에는 사용자 확인이 있고, 형식적 인증은 확정된 IR→생성 코드의 관계에 적용된다. “자연어의 의미를 기계적으로 증명했다”는 뜻으로 전체 과제를 표현하지 않는다. 논문의 상위 기여를 **자연어로 작성하는 스마트홈 자동화의 생성 결과에 대한 형식적 행동 검증**으로 두고, Timeline IR은 요청별 검증 기준을 제공하는 해법, Explorer는 이력 공간을 다루면서 인증을 정당화하는 해법으로 배치한다.

## 5. VETS가 제공할 구체적인 해법

후속 논의의 중심 연결은 **구체적인 행동을 명세하는 operator → 코드 생성 안내와 실행 가능한 검증 기준 → operator 조합의 전체 행동 보존을 검사하는 Explorer**다. [구성안 §1](VETS_PAPER_STRUCTURE_AND_CLAIMS.md#1-출발점과-권고)에 이를 반영했다. 조합된 IR의 기준 의미가 불명확해지는 것이 아니라, 생성 코드가 그 의미를 모든 허용 이력에서 지키는지의 검증이 어려워진다. 개별 operator 테스트를 통과했다는 사실은 조합된 구현의 정확성을 보장하지 않는다. 현재 Explorer를 operator별 증명을 연결하는 compositional verifier로 주장하지 않는다.

| 남는 문제 | VETS의 대응 | 주장 경계 |
| --- | --- | --- |
| 요청별 기대 행동의 계산 기준 | 확인된 Timeline IR을 실행해 같은 입력 이력에 대한 reference 생성 | 자연어 의도 자체의 정답성은 보장하지 않음 |
| 표면적으로 다른 올바른 구현과 그럴듯한 잘못된 구현 구별 | 같은 모델의 timed ACTION 관계로 비교 | 내부 코드 모양·변수명·최종 기기 상태만 비교하지 않음 |
| 이력 공간 폭발과 무한한 실행 시간 | 관찰 보존 입력 표현·상태 병합·무관찰 시간 생략·지원 기호 경로와 인증 완료 조건 | 각 기법의 충분조건과 S를 사용. 단순 sampling이나 오래 실행한 사실을 증명으로 사용하지 않음 |
| 센서값·문자열·조회 반환이 행동 인자로 전파됨 | 사용 위치와 출처를 추적하고, guard 분할만으로 부족하면 전체 값 또는 지원 기호 증명 사용 | 원값 출력·산술까지 임계값 대표만으로 인증하지 않음 |
| 서로 다른 플랫폼의 실행 의미 | 기준 IR의 역할을 유지하고 플랫폼별 frontend·실행·관찰 대응 구성 | 현재 JoI 근거만 존재. HA는 새 대응·지원 범위·검증 근거가 필요 |

이것이 도메인 기여가 될 수 있는 지점이다. “LLM이 틀릴 수 있다”는 동기만으로 충분하지 않고, **지속 조건·반복·서비스 값·정확한 action 시각을 가진 자동화에서 어떤 차이를 보존해야 검사가 타당한지**가 기술 내용에 나타나야 한다. 한편 정수 관계·SMT·도달성 분석이라는 도구 자체의 신규성을 주장하지 않는다.

## 6. TAP, Home Assistant, JoI는 어떻게 배치할 것인가

세 플랫폼을 표현력의 엄격한 포함관계나 난이도의 일렬 순서로 두지 않는다. **시간 메커니즘을 사용자가 구현해야 하는 정도**와 **시간·상태 조합으로 생기는 행동 복잡성**은 별개다.

| 표현 방식 | 메커니즘의 위치 | 남는 오류의 중심 | 논문에서의 역할 |
| --- | --- | --- | --- |
| 기본적인 단일 TAP/ECA 규칙 | 상당 부분 엔진 primitive | 잘못 고른 trigger·condition·action, 여러 규칙 간 상호작용 | 출발점. 직관적인 형식과 정확성 보장을 구별 |
| HA automation/script | event trigger·for·wait·delay·branch·repeat 등의 primitive와 실행 정책 | primitive 선택·배치, 조건 평가 시점, 재트리거와 취소, 저장값·현재값의 혼동 | 의미가 다른 두 번째 backend 후보 |
| 이 프로젝트의 JoI 코드 | 일부 시간 메커니즘을 변수·조건·반복 실행의 idiom으로 구현 | 메커니즘 구현 오류에 위의 조합 오류까지 더해짐 | 주 대상. 코드에 분산된 시간 행동 검증의 필요를 선명하게 보여줌 |

현재 IFTTT 전체를 가장 단순한 한 줄 TAP와 같다고 쓰는 것도 부정확하다. 공식 설명에 여러 action과 사용자 filter code가 있다. 비교 단위는 브랜드 전체가 아니라 **기본 규칙 조각과 실제로 사용하는 실행 구성**이어야 한다. [IFTTT Applets](https://ifttt.com/docs/applets)

HA의 수치 threshold trigger는 경계 진입을 직접 처리하므로 JoI의 수동 edge flag가 필요하지 않은 경우가 있다. 이는 장점으로 인정한다. 그렇다고 HA 프로그램 전체의 정확성을 눈으로 판단할 수 있다는 결론은 나오지 않는다. [HA numeric state trigger](https://www.home-assistant.io/triggers/numeric_state/)

공식 문서에서 확인되는 차이의 예는 다음과 같다.

- `wait_template`는 현재 참이면 진행하지만 `wait_for_trigger`는 이후의 trigger를 기다린다. timeout 후에는 별도 설정이 없으면 실행을 계속한다. `choose`는 처음 만족하는 분기만 실행한다. 이런 primitive들은 서로 교환 가능한 문법이 아니다. [HA script syntax](https://www.home-assistant.io/docs/scripts/)
- 실행 중 새 trigger에 대해 `single`, `restart`, `queued`, `parallel`은 각각 무시·기존 실행 중지 후 재시작·대기열·독립 실행을 선택한다. 동일 action 목록도 모드에 따라 timed trace가 달라질 수 있다. [HA automation modes](https://www.home-assistant.io/docs/automation/modes/)
- trigger의 `for` 대기는 HA 재시작이나 automation reload를 넘겨 보존되지 않는다. 이 사례는 native 의미를 확인해야 하는 이유이며, 현 VETS가 재시작 오류를 검증한다는 근거가 아니다. [HA state trigger](https://www.home-assistant.io/triggers/state/)

### HA를 일반화 대상으로 쓰는 의미

HA의 가치는 JoI보다 어렵다는 것을 보이는 데 있지 않다. **일부 시간 메커니즘이 native primitive로 구현된 플랫폼에서도, 같은 명세 기반 행동 검증 질문이 성립하는지**를 보여주는 데 있다. 간단한 HA 규칙에서는 추가 검증의 필요와 비용 대비 이익이 작을 수 있다. 그 사실을 받아들이고, 복합 시간 행동에서 어떤 공통 문제가 남는지 확인한다. 실제 HA 생성 오류율이나 효용은 아직 측정하지 않았다.

다음 세 종류의 일반화는 구별한다.

1. **표현의 이전:** 같은 행동 명세로 JoI와 HA 프로그램을 만들 수 있음. 이것만으로 코드 정확성은 보장되지 않는다.
2. **검증 방법의 이전:** 같은 기준 IR·관찰 계약과 재사용한 검증 핵심으로 HA 후보도 검사할 수 있음. 새 adapter의 의미 보존과 검증 조건이 필요하다.
3. **실제 HA 실행과의 대응:** 모델이 HA의 지원 기능을 정확히 반영함. 공식 문서·소스 대응과 native 실행/의미론 대조 같은 독립 근거가 필요하다. 물리 기기 전체의 정확성과는 또 다르다.

두 번째 플랫폼의 검증을 주장하려면 YAML을 IR로 되돌린 뒤 그 변환 결과만 비교해서는 부족하다. 변환이 HA의 `for`, wait, mode 의미를 잘못 해석하면 차이를 지울 수 있다. 그런 방식도 가능하지만 변환의 의미 보존 자체가 검증 의무가 된다.

현재 S는 고정된 준비 절차와 알려진 JoI 실행기를 대상으로 한다. **HA를 붙이면 현재 정리가 자동 승계되는 것은 아니다.** 공통 이론으로 일반화하거나 HA 대응 의무를 따로 충족해야 한다. 현재 IR은 단일 시나리오의 순차 실행 범위이므로 HA `parallel`·queue·restart 의미를 전부 지원한다고 선언하지 않는다. 첫 HA 범위는 지원 조각과 초기화·이벤트·재트리거 정책을 정의한 뒤 정한다. 새 trigger를 임의로 입력에서 제거하거나 시작 시 항상 조건이 거짓이라고 숨겨 가정해서도 안 된다.

표현할 일반화 목표는 **“서로 다른 실행 구조를 가진 두 스마트홈 플랫폼의 명시된 조각에 동일한 명세 기반 검증 접근을 적용한다”**가 적절하다. 두 플랫폼을 보였다는 사실만으로 임의 DSL, 모든 HA 기능, 물리 동작 일반화를 주장하지 않는다.

## 7. Motivation과 기존 구성안에 반영할 방향

서론의 출발점을 LLM judge의 실패율에서 다음 순서로 바꾼다.

1. 실제 요청의 시간 관계: 연속 지속, 재발화, 지연 후 조건, 반복 종료와 같은 요구.
2. 짧고 실행 가능한 두 구현이 정상 이력에서는 같은 결과를 내지만, 중단·재개 이력에서는 다른 시각에 action을 내는 사례.
3. 실행기가 설명하는 행동과 명세가 요구하는 행동, 한 번 실행과 허용 이력 전체의 차이.
4. 기존 authoring·property verification·simulation·translation validation이 제공하는 것과, 이 스마트홈 생성 흐름에 연결해야 할 것.
5. VETS의 executable reference와 관찰 보존 인증 방법.
6. JoI는 메커니즘을 코드로 구현하는 주 대상, HA는 풍부한 native primitive를 가진 확장 후보라는 위치.

기존 LLM judge rewrite 실험은 이 문제의 보조 근거로 사용할 수 있다. 판정 flip만으로 source analysis의 일반적 불가능성, simulator의 부족, VETS의 신규성을 증명하지 않는다. 새 motivation에서 필요한 것은 **어떤 이력과 시간 관찰을 빠뜨리면, 실제 요구를 어긴 코드가 멀쩡해 보이는지**다. 실험 프로토콜·표본 수·baseline은 아직 정하지 않는다.

제안하는 문제 문구:

> 스마트홈 자동화는 지속적으로 변하는 입력에 따라 시간에 걸친 기기 명령을 생성한다. 실행기와 시뮬레이터는 주어진 이력에서의 행동을 드러내지만, 그 행동이 요청별 기준을 구현하는지와 선택하지 않은 이력에서도 유지되는지는 별도의 검증 문제다. VETS는 확인된 Timeline IR을 실행 가능한 기준으로 삼아, 지원 실행 모델에서 생성 프로그램의 timed ACTION trace가 그 기준을 보존하는지 인증한다.

## 8. 근거의 접근 범위와 후속 인용 메모

- HA·IFTTT: 위 공식 문서의 해당 기능 설명을 확인했다. HA 문서는 이동·갱신될 수 있으므로 실제 구현·평가에서는 버전과 의미를 고정해야 한다.
- AutoTap: 저자 공개 PDF의 abstract, §II–V와 속성 template를 확인했다. 사용자 요구의 형식화와 전칭 검증이 기존에 없었다는 주장을 반박하는 근거다.
- TAPInspector: 공식 arXiv abstract를 확인했다. 제목·발표 정보는 기존 BibTeX와 연결하되, 상세 알고리즘의 특정 기능 부재를 abstract만으로 단정하지 않았다.
- AwareAuto: arXiv 본문의 §4.2에서 event/state, action 순서·timer·branch를 확인했다. 기존의 복잡한 자동화 표현을 인정하는 근거다.
- SimuHome: arXiv v3 §3–4.3을 확인했다. goal state 및 prerequisite action 검사까지 포함하므로 “최종 상태만 본다”로 과도하게 단순화하지 않는다.
- CASPER: OpenCite DOI 조회로 제목·저자·2026-05-28 정보를 확인했다. 출판사 검색 색인의 §5.2–5.3 본문과 저자 홈페이지의 게재 기록을 확인했다. 출판사 직접 열기와 PDF 다운로드는 실패했으므로 전체 원고를 읽은 독립 검토로 취급하지 않는다. 최종 closest-work 표에 넣기 전 전문을 다시 확인할 후보다.
- Translation Validation: Springer의 원 논문 abstract가 공통 의미 모델, refinement, Signal→C 적용을 명시한다. 더 상세한 reactive compiler의 선행 예로 [Modular Translation Validation of a Full-sized Synchronous Compiler](https://channgo2203.github.io/pdfs/jar15.pdf)의 §3·§6도 확인했다.
- OpenCite의 넓은 Semantic Scholar 검색은 rate limit 후 결과를 반환하지 못했다. 이를 관련연구 부재로 해석하지 않고, 웹의 출판사·arXiv·저자 원문 검색과 기존 corpus를 사용했다.

이 검토로 확정되는 것은 문제 설정에 대한 제안과 인용 근거다. HA adapter·새 실험·포괄적 신규성 조사는 완료되지 않았다.
