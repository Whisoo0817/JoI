# VETS 논문 전체 구성과 핵심 주장 — 논의안

작성: 2026-09-08. 기존 SenSys 제출본의 흐름·주장·실험을 현재 VETS 방향과 대조한 구성 제안이다. 사용자 확정 전 논의안이며, Explorer의 현재 계약·증명·평가를 대체하는 상태 문서가 아니다. 이번 범위는 전체 서사와 핵심 주장까지다. Explorer의 내부 절, 정리·증명·그림의 상세 배치, 최종 Evaluation의 RQ·데이터·baseline·실행 프로토콜은 다음 단계에서 정한다.

2026-09-09 방향 결정: 교수님과 논의한 결과 **LLM-generated와 NL→Timeline IR→확인→LLM lowering→Explorer의 기존 흐름을 유지**한다. 결정론적 IR→JoI compiler는 **future work**로 둔다. 아래 전체 구성과 핵심 서사를 기준으로 방법·증명·평가의 상세 배치를 이어간다.

후속 요구 반영: [도메인 문제와 Home Assistant의 위치](VETS_DOMAIN_PROBLEM_AND_HA_POSITIONING.md)에서 executor·simulator가 있어도 남는 기준/이력 포괄/시간 관찰 문제와 가까운 선행연구를 대조했다. 아래 구성의 motivation은 이 보강을 함께 따른다. HA는 두 번째 플랫폼 후보이며, 현재 JoI 지원·증명 범위를 이미 확장한 것으로 읽지 않는다.

2026-09-09 후속 Flow 대화는 [논의 기록](../skill_result/06_manuscript/flow_discussion_2026-09-09.md)을 따른다. A(연속 부재와 지연 후 재검사)를 서론에, B(저장값과 지연 후 새 읽기)를 방법에 배치하는 방향에 동의했다. 최신 방향은 [세션 인계](../skill_result/SESSION_HANDOFF_2026-09-10.md)를 우선한다.

## 1. 출발점과 권고

제목은 [현재 초록 초안](abstract_draft.txt)의 다음 문구를 기준으로 한다.

> VETS: Verification of LLM-Generated Smart-Home Automation via Executable Timeline Specifications

논문의 중심 질문은 **“생성된 스마트홈 자동화 코드가 사용자 확인을 거친 기준 행동을 구현하는가?”**다. VETS는 확인된 Timeline IR을 실행 가능한 기준으로 삼고, 선언한 실행 모델에서 코드와 기준의 timed ACTION trace 동등성을 검증한다.

**후속 논의의 우선 서사는 실행 가능한 Timeline IR을 중심으로 한 검증 가능한 코드 생성 체계다.** IR은 구체적인 행동 명세로 코드 생성을 안내하고, 그 실행 의미는 생성 결과의 검증 기준을 제공한다. Explorer는 operator들이 조합되어 생기는 전체 시간·상태·값 관계가 생성 코드에서도 보존되는지 검사한다. Verification은 이 구조가 제공하는 핵심 기능이며, Timeline IR과 Explorer를 하나의 방법으로 묶는다. 선행연구 대비 검증 과제는 “요청별 확정 실행 명세에 대한 생성된 플랫폼 코드의 timed ACTION 동등성을 모든 허용 입력 이력에서 인증”하는 것으로 구체화한다. ChatIoT의 LLM 기반 요청 충족 검사와 Murphy et al.의 NL→TSL→reactive synthesis도 존재하므로, 요청별 검사를 처음 시도했다거나 NL→reactive code에 처음 형식적 보장을 제공한다는 넓은 주장은 피한다. 원문 근거와 비교는 위 도메인 문제 문서 §4를 따른다.

### 중심 연결: operator의 실행 의미에서 조합된 코드의 행동 검증으로

**후속 대화에서 유지할 핵심 합의:** operator가 복합적으로 쓰여도 IR의 실행 의미가 정의하는 기준 행동은 명확하다. **어려워지는 것은 생성 코드가 그 기준을 “모든 허용 입력 이력”에서 지키는지 확인하는 것이다.** IR의 실행 가능성으로 기준을 얻는 것과, 가능한 이력 전체에서 구현의 일치를 인증하는 것을 구분한다. “모든 허용”의 범위는 현재 검증 계약의 실행 모델·초기 상태·입력 도메인을 따른다.

중심 방향은 **코드 생성을 위한 구체적인 행동 명세 + operator 실행 의미에 담긴 검증 기준 + 조합된 구현의 전체 행동 보존을 검사하는 Explorer**다. 타이머 시작점·취소 범위·조건 평가 시점·저장값 수명·회차 간 상태 전달이 주요 조합 관계다. 개별 operator 테스트의 성공을 전체 코드의 정확성으로 확대하지 않으며, 현재 Explorer를 operator별 증명을 연결하는 compositional verifier로 부르지 않는다. 이 중심 서사를 유지한 채 다음 단계에서 방법·증명·평가의 상세 배치를 정한다.

1. 자연어에서 후보 IR을 만들 때, event/state·조건 평가 시점·지속과 지연·반복·값의 읽기/저장 등 지원하는 행동 관계를 구체화한다. 후보를 확정하면 코드 생성에 사용할 의미적 기준이 생긴다. 이 단계가 자연어를 항상 올바르게 해석한다는 보장은 아니다.
2. 각 operator는 실행 규칙을 갖는다. 해당 규칙과 제어·저장 상태의 전달 규칙으로 조합된 IR도 실행할 수 있고, 같은 입력 이력에 대한 기준 timed ACTION trace를 계산할 수 있다. operator마다 별도 검증 인증서나 완전한 테스트 묶음이 들어 있다는 뜻은 아니다.
3. 플랫폼 구현에서는 이 의미가 조건문·변수·타이머·반복에 나뉘거나 native primitive로 구현된다. 개별 operator에 대한 테스트를 통과해도, 시간 기준점·변수 수명·조건 범위·읽기 시점이 조합 문맥에서 바뀌면 전체 행동은 틀릴 수 있다.
4. 따라서 IR의 실행 가능성은 기준 문제를 해결하지만, 생성 코드가 모든 허용 입력 이력에서 그 기준을 보존하는지의 문제는 남는다. Explorer는 IR과 코드 양쪽의 제어·시간·값 흐름을 함께 분석하고, 관찰을 보존하는 축소 및 인증 완료 조건으로 이 의무를 다룬다.

설명용 예시는 `READ(x) → DELAY(1분) → CALL(notify, 저장한 x)`다. 지연 뒤에 센서값을 다시 읽어 알리는 후보는 센서가 일정할 때는 기준과 같지만, 대기 중 값이 바뀌면 ACTION 인자가 다르다. 읽기·지연·알림 연산 자체가 유효한 것과, 읽은 값의 수명이 조합에서 보존되는 것은 별개다. 이는 실행 측정값이 아닌 구성 사례다.

**명세 의미의 조합과 검증 증명의 조합을 구별한다.** 현재 Explorer는 operator별 증명만 연결하는 assume–guarantee/compositional verifier가 아니다. 지원하는 조합으로 만들어진 전체 IR–코드 쌍을 분석한다. 임의 병렬 실행·재진입·여러 자동화의 충돌까지 해결했다는 뜻으로 “조합 검증”을 쓰지 않는다. 이 서사는 기여의 연결이며, 표현 및 분석 방법의 선행연구 대비 신규성·이점은 별도 근거가 필요하다.

기존 OVLA의 장점인 실행 가능한 기준 IR과 행동 비교를 유지하면서, 논문의 중심 근거를 **관측한 오류 검출·배포 결과에서 명시적인 동등 인증의 보장과 적용성으로 이동**하는 구성을 권한다. 자연어 의도 해석의 성공, 사용자 확인 능력, 물리 환경의 안전성은 이 동등성 주장이 아니다.

이는 기존 논문에 없던 사용자 확인 경계를 처음 도입한다는 뜻이 아니다. 기존 원고도 Layer A/B와 bounded 보장을 구별했다. 문제는 그 경계에 비해 초록·서론·결론의 안전 배포와 의도 충족 표현이 넓었고, 실제 긍정 판정에는 전칭적 보장이 없었다는 데 있다.

서사 전체는 **“신뢰할 기준이 없는 자연어 자동화 → 확인 가능한 IR로 기준 구성 → 가벼운 결정론적 검사 → 수정·거절을 통한 안전 배포”**였다. 기존 Figure 1의 edge/level 사례는 좋은 출발점이다. 같은 최종 기기 상태에 도달해도 호출 시점과 횟수가 다르면 자동화 행동이 다르다는 문제를 보여준다.

기존 §1의 기여는 네 가지였다.

| 기여 | 원고가 내세운 내용 |
| --- | --- |
| C1 Timeline IR | 하나의 IR을 사용자 확인용 rendering과 기계 검증용 reference로 사용 |
| C2 Deterministic deployment gate | IR→FSM→boundary event→bounded trace 비교 및 counterexample 기반 수정·거절 |
| C3 On-device realization | ≤9B 양자화 생성기와 LLM-free 검사, 로컬 실행 비용 |
| C4 Evaluation | rendering faithfulness, 오류 검출, system safety, 비용·배포 실증 |

기존 §6.4는 `pass ⇒ correct`를 명시적으로 주장하지 않았다. 긍정 판정은 **합성한 시나리오·유한 horizon·시간 tolerance에서 차이를 찾지 못했다**는 뜻이었다. T1은 고정된 IR–코드 쌍에 대한 도구 판정의 동일성이고, T2는 정의한 관찰 모델에서 반례로 뒷받침되는 거절이었다. 현재의 실행 의미 결정론성과 긍정 인증 soundness에 그대로 대응시키면 안 된다.

해석에 특히 중요한 두 세부사항이 있다.

- Mutation survivor 11개 중 8개는 100ms 지연을 시간 tolerance가 허용한 사례이고, 1개는 중복 호출 제거가 차이를 감춘 사례이며, 나머지 2개는 같은 read-modify-write 산술 자동화에 있었다. 따라서 11개를 모두 같은 종류의 탐색 누락으로 해석하거나, 새 관찰 계약에서 같은 정답 label을 그대로 사용하면 안 된다. 근거: PDF p.10, §8.2.
- 배포 358쌍 가운데 원고는 356쌍의 모든 replay 일치를 보고하고, 2쌍은 action group이 horizon 밖으로 밀린 것을 허용 가능한 window artifact로 해석했다. 이를 모든 trace의 정확한 일치로 요약하면 안 된다. 근거: PDF p.11, §8.3.

[원래 리뷰](review.txt)의 공통 지적은 사용자 확인 가정, bounded 검사 대비 넓은 안전성 표현, compiler 대안, 단일 플랫폼 대비 일반화, 재현성이었다. 사용자 확인 경계를 명시하는 것으로 연구 범위를 정할 수는 있지만, 그것이 기존 usability 우려를 실험적으로 해결한 것은 아니다.

## 4. 지금 달라진 부분과 서사에 주는 영향

현재 기준은 [검증 계약](../explorer/docs/model/VERIFICATION_CONTRACT.md), [통합 증명](../explorer/docs/proof/PROOF_OBLIGATIONS.md), [평가 요약](../explorer/docs/paper/EVALUATION.md)다. 과거 설계 문서의 parallel/merge 제안, finite-H 제한, 미완료 TODO를 현 구현에 적용하지 않는다.

## 5. 새 논문의 핵심 주장 제안

논문 전체를 묶는 문장은 다음과 같다.

> VETS uses executable timeline specifications to guide smart-home automation code generation and define its behavioral reference, then soundly certifies that generated implementations preserve the specified behavior across supported operator compositions under a declared execution model.

### C1 — 실행 가능한 시간 명세로 코드 생성과 행동 검증의 기준을 함께 제공한다

Timeline IR은 지원하는 이벤트·상태·시간 관계와 순차 제어를 명시해 플랫폼 코드 생성에 사용할 구체적인 행동 기준을 제공한다. 각 operator와 그 조합의 실행 규칙은 같은 명세를 검증 기준으로도 사용할 수 있게 한다. 고정된 모델·초기 상태·입력 이력에서 반응 결과가 유일하며, 유한 반응·시간 진행 조건을 충족하는 실행은 유일한 기준 trace를 제공한다. 따라서 코드 표면이나 최종 기기 상태 대신 동일한 입력에서 발생해야 하는 ACTION의 시각·대상·인자·순서·횟수를 기준으로 삼을 수 있다.

근거는 실행 계약과 D다. 단일 연산자뿐 아니라 지원 구문의 조합에 대한 실행 의미를 설명하되, 임의 병렬 자동화·시나리오 간 상호작용·전체 스마트홈 표현력을 주장하지 않는다. 독립적인 언어 설계 논문으로 확대하지 않고, 행동 검증을 가능하게 하는 기준 명세로 제시한다. 사용자 확인은 자연어 해석의 정답성을 입증하지 않는다.

### C2 — 인증에 성공한 코드의 기준 대비 행동 동등성을 보장한다

지원 검사를 통과하고 H 없는 인증 절차를 완료한 준비된 IR–코드 쌍은, 고정된 실행 모델의 **모든 허용 초기 상태와 입력 이력에서 시간 제한 없이 같은 timed ACTION trace**를 낸다.

이것이 주된 기술 주장이다. 전제와 수식의 유일한 기준은 검증 계약의 S다. “모든 입력”은 고정된 binding·시작 시각·catalog/domain·입력 변화 모델 안의 입력을 뜻한다. 임의의 프로그램을 반드시 판정하거나, 모든 실제 동등 프로그램을 인증한다는 역방향은 포함하지 않는다. 자원 초과·지원 밖·증명 미완료는 인증 성공이 아니다.

근거는 통합 증명의 경로별 보존 논증과 공통 귀납이다. 선언 모델과 고정 인증 알고리즘에 대한 수작업 증명이며, 프런트엔드·실행기 대응과 solver의 신뢰 기반을 명시한다. 전체 소스의 기계 검증이나 실제 JoI 서버·물리 기기까지의 정확성으로 확대하지 않는다.

### C3 — 이 검증이 생성 코드에 유용하고 실행 비용을 감당할 수 있다

평가로 지지해야 할 주장은 IR의 표현 범위와 NL→IR의 의미 정확성, 생성 코드에서의 조합 오류 및 인증 적용 범위, 관찰을 보존하는 입력·시간·상태 축소의 비용 효과다. 중간 표현 덕분에 생성 정확성이 개선된다고 주장하려면 비교 근거가 추가로 필요하다. 사용자 연구 없이도 독립 기준을 가진 과제로 평가할 수 있지만, 생성된 IR 자체를 NL 정답으로 삼거나 IR–코드 동등성을 NL→code 성공으로 계산하지 않는다. 상세 비교군·실험 순서는 다음 단계에서 정한다.

**C3의 최종 강도·수치는 아직 확정하지 않는다.** 현재 선택된 결과는 기존 과제를 개발 중 재평가한 exploratory 근거이며, 초록의 과거 bounded 성능 수치는 현 구현을 평가한 값이 아니다. 구체적인 일반화·정확도·속도 향상 주장은 다음 평가 계획과 감사 결과에 따라 정한다. 관찰 보존은 이론 의무이고, 감소량·지연시간·적용률은 실험 의무다.

| ID | 역할·근거 방식 | 이번 단계의 취급 | 근거 / 미충족 부분 |
| --- | --- | --- | --- |
| C1 | 기준 명세와 의미론, 주로 이론·설계 | 모델 범위를 붙여 핵심 주장으로 제안 | 검증 계약의 D와 통합 증명. 표현 범위의 corpus 근거는 별도로 설계 |
| C2 | 긍정 인증의 soundness, 이론 | 모델·성공 조건·신뢰 기반을 붙여 핵심 주장으로 제안 | 검증 계약의 S와 통합 증명. 기존 테스트나 판정 건수로 증명을 대체하지 않음 |
| C3 | 적용성·비용, 경험적 | 평가 목표로 유지, 정량 결론 보류 | 평가 요약과 연결 감사의 exploratory 범위. 최종 평가 설계·같은 버전의 근거 필요 |

논문의 contribution 목록은 **(1) 코드 생성과 행동 검증에 공통 기준을 제공하는 executable Timeline IR 기반 체계, (2) 지원 operator 조합의 전체 행동 보존을 인증하는 Behavioral Explorer, (3) 표현·생성·검증의 적용 범위와 오류·비용 근거**로 묶는 것이 적절하다. 세 번째는 실증적 뒷받침이며, 실험을 수행했다는 사실 자체를 알고리즘의 신규성으로 쓰지 않는다. 모델 검사·도달성 탐색·결정론적 반응 의미 자체가 새롭다고 주장하지 않는다. 외부 선행연구 대비 신규성 문구는 원문 인용 검토를 거쳐야 하며, 이번 기존 원고 대조만으로 “최초”를 확정하지 않는다.

## 6. Introduction에서 전개할 논리

1. 스마트홈 자동화의 정확성은 시간에 걸친 행동에 있다. edge와 level, sustain과 delay, 반복의 종료 차이는 문법적으로 유효한 코드에도 숨어 있을 수 있다. 기존 Figure 1에 더해, 연속 5분 지속과 5분 뒤 재검사가 평범한 이력에서는 같고 중간 재실 이력에서는 달라지는 사례로 실행만으로 충분하지 않은 이유를 설명한다. 구체 사례는 위 도메인 문제 문서를 따른다.
2. 이를 검증하려면 입력 이력마다 기대 행동을 계산할 수 있는 기준이 필요하다. 자연어의 비형식성, 코드 표면의 유사성, 최종 기기 상태만으로는 그 기준을 대신하기 어렵다.
3. VETS는 자연어에서 후보 Timeline IR을 만들고 확인 후 기준으로 고정한다. operator와 조합의 실행 의미가 구체적인 코드 생성 지침과 행동 검증 기준을 함께 제공한다. 이 경계에서부터 검증 명제를 정의한다. 잘못된 IR을 확인할 가능성은 남는다.
4. operator 조합에서 생기는 시간 기준점·조건 범위·저장값 수명 때문에, 개별 operator의 테스트나 몇 개 전체 실행의 성공으로 생성 코드의 행동 보존을 결론낼 수 없다. 실행 가능한 기준은 있으나 다양한 입력 이력·지속 상태·타이머가 만드는 탐색 공간이 남는다. 모델 검사와 reactive translation validation의 선행연구를 인정하고, 전체 IR–코드 쌍의 의미를 보존하며 검사하는 기술적 의무를 설명한다.
5. Behavioral Explorer는 선언한 모델에서 행동 비교에 필요한 차이를 보존하며 탐색·기호 검증을 수행한다. 생략의 정당성과 인증 완료 조건을 통해 S를 제시한다.
6. 모델 결정론성과 인증 soundness는 증명으로, 구현의 부합·적용 범위·비용은 실험으로 뒷받침한다. 최종 정량 문장은 새 평가에 맞춘다.

본 논문은 **LLM이 생성한 코드가 확정된 기준 행동을 구현하는지 검사하는 것**을 다룬다. IR→코드에는 LLM lowering을 사용하며, 결정론적 compiler의 구현과 비교는 future work로 둔다.

또한 `source-code-based verification`을 모든 정적·형식적 코드 분석의 한계라는 뜻으로 설명하지 않는다. 논문의 실제 대조는 **표면적인 코드 비교·비형식적 판단과, 정의된 실행 의미에 대한 행동 검증**이다. 기존 LLM judge 실험도 보조 동기로만 사용하고 모든 judge 방식의 불가능성을 주장하지 않는다.

| 8 | Related Work | 기준 명세·검증 대상·행동 관찰·보장 범위에서 관련 접근과 무엇이 다른가? | 기존 §2 자료를 재검토해 재구성. 서론에는 가까운 연구와 차이만 간결히 배치 |

기존 Implementation 절은 별도 주기여로 두기보다 시스템·방법·평가 설정 중 필요한 곳에 통합하는 방향을 권한다. 구조별 prompt routing, 소형 모델 선택, repair loop는 중심 질문을 설명하는 데 필요한 만큼만 남긴다. 상세 구현 배치는 다음 단계에서 정한다.

## 9. 초록과의 정합성 및 다음 단계의 경계

현재 title과 abstract의 **문제 → executable Timeline IR → 사용자 확인 → Behavioral Explorer → 비용·판정 평가**라는 순서는 이 구성의 출발점으로 유지한다. 초록 원문은 이번 작업에서 수정하지 않는다.

- `formally verifies`는 C2와 연결한다. 지원 모델·인증 완료 조건·신뢰 기반을 본문에서 밝혀야 한다. bounded verification도 형식 검증일 수 있으며, H 제거만으로 formal이라는 용어가 정당해지는 것은 아니다.
- `executable ground truth`는 확인 후 채택한 **기준 명세**라는 뜻이다. 자연어 의도의 참값이 확인되었다는 뜻으로 확대하지 않는다.
- `critical temporal boundaries and input values`는 관찰 보존의 설명으로 풀어야 한다. 조건 경계만 대표하면 충분하다고 쓰면 원값이 ACTION으로 흐르는 사례를 놓친다. [과거 Speaker 반례 설명](VETS_formal_verification_scope_and_explorer_revision.md)의 문제 제기는 이 구별을 잘 보여주며, 그 문서의 당시 미완료 상태는 현 상태가 아니다.
- 311쌍·32단계·73.4%·52.1ms는 [과거 v3 bounded 결과](../skill_result/05_experiment_plan/results/E3/heldout-gemma-v3-h32/abstract-result-wording.md)의 수치다. 특히 73.4%는 그중 동치 쌍에서의 전이 평가 감소다. 현 H 없는 구현의 정확도·비용 수치로 옮기지 않는다. 최종 초록 결과는 합의한 시점에 최종 평가와 정합화한다.

다음 단계에서는 이 골격을 기준으로 C1–C3에 필요한 Explorer 방법·정리·구현 근거를 배치하고, Evaluation 질문·분모·버전·baseline·독립성·비용 측정 범위를 구체화한다. 현재 평가의 숫자는 계속 [생성된 평가 요약](../explorer/docs/paper/EVALUATION.md)에서만 관리한다.

## 10. 상세 배치 전 추가 논의: 의미 선택, 이름, feedback

2026-09-08 추가 질문에 대한 **권고 및 연구 후보**다. 이름 변경이나 새 repair 기여를 확정한 내용이 아니며, 아래 진단·일반화 기능이 현재 Explorer에 구현되어 있다는 뜻도 아니다.

### 10.1 TAP와 Timeline IR: 행동 의미를 선택하고 조합하는 표현

두 표현 모두 자연어 요구를 정해진 의미를 가진 구성요소로 구체화하는 역할을 할 수 있다. 다만 모든 스마트홈 행동을 완성된 목록으로 열거한 뒤 하나를 고르는 것으로 설명하지 않는다. 지원하는 행동·시간 관계의 어휘, 매개변수, 조합 규칙을 제공하고, 그 안에서 하나의 실행 명세를 구성하는 것이다. 기기·서비스 catalog는 가능한 호출을, IR의 실행 의미는 그 호출이 언제 어떤 값으로 발생하는지를 규정한다.

구체화할 축은 event/state, 연속 지속/무조건 지연, 조건 평가 시점, 타이머 시작점과 취소 범위, 저장값/현재값, 반복과 종료 등이다. 지원하지 않는 조합을 이 목록만으로 지원한다고 선언하지 않으며, 초기 상태·동시각 입력/타이머 순서 같은 모델 규칙도 함께 의미를 결정한다. 잘 정의된 IR을 골랐다는 사실은 원래 의도를 올바르게 선택했다는 보장이 아니다.

기본 단일 TAP 규칙은 trigger와 action, 필요하면 condition의 선택을 구조화한다. Timeline IR은 시간·제어·값 관계를 명시적으로 조합하는 표현으로 설명한다. TAP 확장이나 여러 규칙과 보조 상태를 포함한 전체 체계에 대한 엄격한 표현력 포함관계는 아직 주장하지 않는다. [AwareAuto §4.2](https://arxiv.org/html/2408.12687v1#S4.SS2)는 이미 event/state 조건, action 순서·timer·branch를 TA-pair로 구조화한다. 따라서 복잡한 규칙 표현 자체에 더해, 같은 실행 의미가 생성 지침과 코드의 검증 기준으로 이어지는 점이 중심이다.

IR을 확정하면 하나의 고정 trace가 생기는 것이 아니라, **각 허용 초기 상태와 입력 이력에 대한 기준 timed ACTION trace를 계산하는 의미**가 정해진다. 이후 어려운 문제는 생성 구현이 그 기준을 모든 허용 이력에서 보존하는지다.

### 10.2 이름: 현재는 Timeline IR 유지 권고

현재 title의 Executable Timeline Specifications와 Timeline IR, Behavioral Explorer의 관계는 일관된다. Timeline IR은 시간·상태 관계를 표현하는 명세이고, Behavioral Explorer는 그 명세와 코드가 입력 이력에 따라 만드는 행동을 탐색한다. 동일한 접두사를 사용할 필요는 없다.

첫 정의에서 Timeline IR을 "an executable IR for reactive and temporal automation behavior"로 설명하는 방안을 권한다. Timeline은 사전 고정한 단일 스케줄이 아니라 입력에 따라 발생하는 시간 행동을 뜻한다고 명시한다. Behavioral IR은 행동 범위가 넓다는 장점이 있지만 시간 의미가 이름에서 사라진다. Reactive Timeline IR은 오해를 줄이는 대안이나, 지금 이름을 바꿔야 할 기술적 필요는 없다. 논문 표기는 현재 abstract의 **Behavioral Explorer**로 통일하는 것이 자연스럽다. 코드·제목·초록의 이름은 변경하지 않았다.

### 10.3 Feedback: 조합 관계의 불일치를 수정 지침으로 연결하는 후보

후보 주장은 **재생 가능한 반례를 명세와 구현의 시간·제어·값 의존 관계에 연결하여, 생성 코드가 보존하지 못한 관계를 수정 지침으로 제공한다**는 것이다. IR의 역할을 생성 지침·검증 기준·진단 기준으로 이어갈 수 있다.

현재 [Divergence와 replay](../explorer/verification/product.py)는 초기 상태·시각·입력 이력과 양쪽 ACTION 차이 및 재생 확인을 위한 기반을 제공한다. 이 자료 구조 자체가 IR operator 역추적이나 근본 원인 진단을 구현하는 것은 아니다. [files/feedback_edit.md](../files/feedback_edit.md)는 사용자의 자연어 명령 편집용 prompt이며, 여기서 제안한 검증 반례 feedback과 다르다.

| 후보 | 구체적 내용 | 기여를 주장하려면 필요한 근거 |
| --- | --- | --- |
| IR 의미와 대응하는 반례 설명 | 초기 상태와 필요한 입력 변화, 첫 관찰 불일치, 기대/실제 ACTION, 관련 IR operator와 시간·제어·값 의존 관계를 제공 | 실행·분석에서 얻은 근거와 설명의 대응, raw trace보다 나은 수정 성과 |
| 원인 후보의 역추적 | 불일치 ACTION에서 값의 읽기 시점, 저장, 타이머 시작/취소, 분기와 대기 관계를 거슬러 분석 | 관찰 불일치 위치와 수정 위치를 구별. 누락 ACTION의 경우 실제 실행되지 않은 코드 경로도 고려. IR–코드 1:1 줄 대응을 가정하지 않음 |
| 실패 입력 이력 집합의 설명 | 한 수치 사례를 넘어 같은 실패를 만드는 값·시간 제약을 도출. 예: 지연 전 읽은 값과 지연 후 값이 다를 때 | 단일 witness에서 범위 전체 실패를 추정하지 않음. 일반화 영역을 검증하거나 가설로 명시. 서로 다른 입력 epoch와 값 상관관계를 보존 |
| 반례 선택과 누적 재사용 | 중복 이력 대신 서로 다른 의존 관계의 실패를 선택하고, 기존 반례를 다음 후보의 빠른 검사에 재사용 | 추출·선택 비용을 포함한 이점. 수정 코드의 새 guard·읽기·timer 때문에 이전 partition이나 인증 결과를 자동 재사용하지 않음 |

설명용 예: `READ(x) → DELAY(1분) → CALL(notify, 저장한 x)`에서 후보가 지연 후 다시 읽는 경우, 0초에 x=20, 30초부터 x=25인 이력은 60초 ACTION 인자 차이를 만든다. 유용한 설명은 "20 대신 25"에서 끝나지 않고 **READ에서 얻은 값이 DELAY를 넘어 CALL까지 전달되어야 하는 관계**를 지목한다. `x_at_read ≠ x_at_call`이라는 실패 집합은 해당 후보와 도달 경로를 분석해 정당화해야 한다. 이는 측정된 오류 사례가 아닌 연구 방향 설명이다.

반례의 사건을 줄여도 동일한 불일치가 재현되는지 확인해야 하며, 짧은 반례가 항상 좋은 설명이라는 가정은 피한다. 역추적된 의존 관계는 원인 후보일 수 있고 유일한 잘못된 줄이라는 증거가 아닐 수 있다. 생성 코드의 주석이나 LLM이 주장한 IR 대응만으로 진단을 확정하지 않는다.

선행연구 대비 "반례를 LLM에 주어 수정" 자체는 기여로 충분하지 않다. [VeCoGen §III-D](https://arxiv.org/html/2411.19275v1)는 compiler/verifier feedback으로 C 코드를 반복 수정한다. [ExVerus §1](https://arxiv.org/html/2603.25810v1)은 구체적 반례로 LLM의 Verus proof 수정을 안내하며, 낮은 수준의 검증 결과에서 원래 프로그램 의미를 복원하는 어려움도 다룬다. [Explainable Reactive Synthesis](https://arxiv.org/abs/2012.14582)는 reactive implementation의 수정과 설명에 counterexample trace를 사용한다. 이 세 연구와 대상·진단 표현·보장·수정 효과를 대조해야 하며, 포괄적 신규성 검토는 아직 완료하지 않았다.

우선순위 권고는 **재생 가능한 반례 → IR 의존 관계와 대응하는 설명 → 검증 가능한 실패 집합 일반화** 순이다. 초기 비교는 동일한 실패 코드·기준 IR·모델·수정 예산에서 단순 실패 판정, raw counterexample, IR 대응 설명, 집합 제약 추가의 효과를 분리하는 것이 적합하다. "LLM이 이해하기 쉽다"는 주장은 설명의 유창함보다 최종 인증 성공률·수정 회수·총비용·새로 유발한 실패로 평가한다. 이는 아직 최종 Evaluation 프로토콜이 아니다.

Feedback loop에서는 기준 IR을 고정하고 코드를 수정한다. 반례를 통과시키는 수정과 모든 허용 이력에 대한 동등 인증은 별개이므로, 최종 수락에는 수정된 IR–코드 쌍의 전체 검증이 필요하다. 명세 수정이 필요하면 별도 의도 결정 단계로 돌아간다. 현재는 이 방향을 주기여를 강화할 후보로 두며, 독립 기여로 올릴지는 방법과 비교 근거를 확보한 뒤 정한다.
